\begin{abstract}
Code review is a critical quality assurance practice, yet manual review is
time-consuming, inconsistent, and prone to overlooking subtle correctness
issues. We present \ReviewBot{}, a code review automation system built on
\JuGeo{}'s judgment-geometric verification framework. \ReviewBot{} analyzes
pull request diffs by constructing a semantic site over the changed code,
producing judgments for each affected coordinate, and generating
human-readable review comments grounded in formal evidence. Unlike
traditional static analyzers that report syntactic patterns, \ReviewBot{}
provides \emph{judgment-grounded} feedback: every comment references a
specific proposition $\prop$, its trust level $\trust$, and any obstructions
$\obstr$ preventing verification. On the Paper~67 benchmark, the current
review configuration now uses \JuGeo{}'s executable specification surface:
each review bundles a declared finite cover of witness inputs with a
\texttt{spec(result, *args, **kwargs)} oracle checked through
\texttt{jugeo.easy.spec}.
Across \ppLXVIIprogramCount{} programs (\ppLXVIIcorrectCount{} correct,
\ppLXVIIbuggyCount{} buggy), this workflow produces \ppLXVIIfpRate{} false
positives, \ppLXVIIdetectedPct{} bug recall, and \ppLXVIIaccuracyPct{}
accuracy. The numbers are measured from the actual review run and retained as
the paper's regression baseline.
\end{abstract}

\section{Introduction}\label{sec:intro}
% ------------------------------------------------------------------

Code review is the last line of defense before code reaches production.
Studies estimate that code review catches 60--90\% of defects before
deployment~\cite{bacchelli2013expectations}. Yet reviews are costly: Google
engineers spend an average of 6.4 hours per week on code review, and review
latency is a leading cause of developer frustration.

Automated code review tools---linters, static analyzers, AI-powered
assistants---aim to reduce this burden. However, existing tools suffer from
two problems. First, they report \emph{syntactic} issues (unused variables,
style violations) rather than \emph{semantic} correctness problems. Second,
they provide no formal evidence for their claims, making it difficult for
developers to assess whether a finding is genuine.

\JuGeo{} addresses both limitations. Its judgment-geometric framework
produces semantically grounded analysis: each finding corresponds to a
judgment $\J$ with explicit proposition, evidence, and trust level. This
paper presents \ReviewBot{}, a system that translates \JuGeo{} judgments
into actionable code review comments.

Our contributions are:
\begin{enumerate}[leftmargin=*]
  \item A diff-aware review pipeline that constructs a semantic site over
        changed code and produces judgments for affected coordinates.
  \item A comment generation system that translates formal judgments into
        human-readable review feedback with severity classification.
  \item A trust-based prioritization scheme that ranks findings by
        verification confidence, suppressing low-confidence noise.
  \item An evaluation on \ppLXVIIprogramCount{} programs showing how declared-cover
        runtime witnesses improve semantic bug recall while keeping the
        metrics tied to measured review output.
\end{enumerate}

\section{Background}\label{sec:background}
% ------------------------------------------------------------------

\subsection{Code Review Practices}

Modern code review follows the pull request model: a developer proposes
changes, reviewers examine the diff, and the team converges on an approved
version. Automated checks (CI tests, linters) run in parallel with human
review.

\subsection{Judgment-Geometric Analysis}

\JuGeo{} produces judgments $\Jud{\coord}{\prop}{\carrier}{\evid}{\oblig}
{\obstr}{\trust}{\prov}$ for each program coordinate $\coord$. The
proposition $\prop$ states the correctness property; the trust level
$\trust \in \{\Tcontra, \Tunver, \Tcopilot, \Toracle, \Truntime, \Tsolver,
\Tproof\}$ indicates evidence quality; and obstructions $\obstr$ identify
specific barriers to verification.

\subsection{Static Analysis in Code Review}

Tools like CodeQL, Semgrep, and SonarQube flag syntactic patterns
(null dereferences, SQL injection). These tools operate on abstract syntax
trees and control flow graphs but lack formal semantics. \ReviewBot{}
operates on the judgment sheaf, providing formally grounded findings.

\subsection{Stage 1: Diff Analysis}

The \DiffAnalyzer{} parses the pull request diff and maps changed lines to
coordinates in the semantic site. It invokes \texttt{discovery\_pipeline} to
identify all affected coordinates, including transitive dependencies through
morphisms.

\begin{algorithm}[t]
\caption{Diff-Aware Review via \texttt{bug\_detection\_scan}}
\label{alg:review}
\begin{algorithmic}[1]
\REQUIRE Pull request diff $\Delta$, base site $\Site_{\text{base}}$
\ENSURE Set of review comments $\mathcal{R}$
\STATE $\text{changed} \gets \texttt{parse\_diff}(\Delta)$
\STATE $\text{coords} \gets \texttt{discovery\_pipeline}(\text{changed}, \Site_{\text{base}})$
\STATE $\Site|_\Delta \gets \texttt{formal\_core\_site}(\text{changed})$
\STATE $\mathcal{J} \gets \emptyset$; $\mathcal{R} \gets \emptyset$
\FOR{each $\coord \in \text{coords}$}
  \STATE $\J \gets \texttt{orchestrate\_verification}(\coord)$
  \STATE $\mathcal{J} \gets \mathcal{J} \cup \{\J\}$
  \IF{$\J.\obstr \neq \emptyset$}
    \STATE $\mathcal{R} \gets \mathcal{R} \cup \{\texttt{generate\_comment}(\J, \SevCritical)\}$
  \ELSIF{$\J.\trust \tleq \Tcopilot$}
    \STATE $\mathcal{R} \gets \mathcal{R} \cup \{\texttt{generate\_comment}(\J, \SevWarning)\}$
  \ELSE
    \STATE $\mathcal{R} \gets \mathcal{R} \cup \{\texttt{generate\_comment}(\J, \SevPass)\}$
  \ENDIF
\ENDFOR
\STATE Run \texttt{bug\_detection\_scan}$(\Site|_\Delta)$ for global issues
\STATE Run descent check on $\Site|_\Delta$
\RETURN $\mathcal{R}$
\end{algorithmic}
\end{algorithm}

\subsection{Stage 2: Site Construction}

The affected coordinates define a sub-site $\Site|_\Delta$ of the full
semantic site. Site construction via \texttt{formal\_core\_site} takes
\subFormalcoresiteSmallTime{} for small diffs and
\subFormalcoresiteMediumTime{} for medium diffs. The site includes
\compSiteMeanCoords{} coordinates and \compSiteMeanMorphisms{} morphisms
on average.

\subsection{Stage 3: Judgment Production}

For each affected coordinate, \ReviewBot{} produces a judgment using the
standard \JuGeo{} pipeline:
\begin{enumerate}
  \item Proposition generation from the coordinate's carrier $\carrier$.
  \item SMT encoding via \texttt{encode\_for\_solver}
        (\compProfEncodeForSolverMeanMs{}\,ms mean).
  \item Solver invocation and trust assignment.
  \item Descent verification via \texttt{run\_full\_descent}
        (\compProfRunFullDescentMeanMs{}\,ms mean).
\end{enumerate}

The verification orchestrator (\compProfOrchestrateVerificationMeanMs{}\,ms)
coordinates these steps. Across our benchmarks, the system produces
\compPropsSum{} propositions with \compPropsOkSum{} verified, yielding
\compOverallAccuracy{} overall accuracy.

\subsection{Stage 4: Comment Generation}

The \CommentGen{} translates judgments into review comments. Each comment
includes:
\begin{itemize}[leftmargin=*]
  \item \textbf{Location}: File path and line range from the coordinate.
  \item \textbf{Severity}: Derived from trust level and obstructions.
  \item \textbf{Finding}: Natural-language description of the proposition.
  \item \textbf{Evidence}: Summary of the verification evidence.
  \item \textbf{Suggestion}: Recommended fix when obstructions are detected.
\end{itemize}

\section{Severity Classification}\label{sec:severity}
% ------------------------------------------------------------------

\ReviewBot{} classifies findings into four severity levels based on judgment
analysis:

\begin{definition}[Review Severity]
Given a judgment $\J$ for coordinate $\coord$, the severity is:
\[
  \Severity(\J) = \begin{cases}
    \SevCritical & \text{if } \obstr \neq \emptyset \text{ or }
                    \trust = \Tcontra \\
    \SevWarning  & \text{if } \trust \tleq \Tcopilot \text{ and }
                    \obstr = \emptyset \\
    \SevInfo     & \text{if } \trust \in \{\Truntime, \Toracle\} \\
    \SevPass     & \text{if } \trust \in \{\Tsolver, \Tproof\}
  \end{cases}
\]
\end{definition}

\paragraph{Critical Findings.}
These correspond to definite bugs: obstructions that prevent verification.
In the current Paper~67 benchmark run, critical findings arise from failed
declared-cover witnesses in \texttt{jugeo.easy.spec}, rather than from
syntax-only patterns alone.

\paragraph{Warning Findings.}
Low-trust judgments indicate uncertainty. The code may be correct but
\ReviewBot{} cannot confirm it. This is valuable feedback: the reviewer knows
which areas need closer scrutiny.

\paragraph{Pass Findings.}
High-trust judgments provide positive assurance. \ReviewBot{} reports these
as ``verified'' annotations, giving reviewers confidence in the changed code.

\subsection{Trust-Based Prioritization}

Comments are ordered by severity, then by trust deficit. The trust deficit
of a coordinate is the gap between its current trust and $\Tsolver$:
\[
  \text{deficit}(\J) = \text{rank}(\Tsolver) - \text{rank}(\J.\trust)
\]
This ensures that the most concerning findings appear first. With
\compTrustSolverdischarged{} judgments reaching $\Tsolver$
(\compTrustSolverdischargedPct{}), most comments in correct code are
$\SevPass$ findings.

\section{Soundness of Automated Review}\label{sec:soundness}
% ------------------------------------------------------------------

\begin{theorem}[Review Completeness]\label{thm:review-complete}
For a diff $\Delta$ modifying $k$ source locations, \ReviewBot{} produces
review comments for every affected coordinate in $\Site|_\Delta$,
including transitively affected coordinates.
\end{theorem}

\begin{proof}[Proof Sketch]
The \texttt{discovery\_pipeline} computes the transitive closure of affected
coordinates via morphism tracing. By Paper~14, this closure is complete:
every coordinate whose carrier depends on a changed location is included.
Algorithm~\ref{alg:review} iterates over all discovered coordinates (line~5),
producing a comment for each. \qed
\end{proof}

\begin{proposition}[No False Positives on the Paper~67 Suite]\label{thm:no-fp}
On the \ppLXVIIcorrectCount{} correct programs in the Paper~67 benchmark,
\ReviewBot{} produces zero $\SevCritical$ findings.
\end{proposition}

\begin{proof}[Proof Sketch]
In the measured declared-cover run, every correct benchmark program satisfies
all witness clauses, so the resulting review has $\obstr = \emptyset$ and no
critical finding is emitted. Empirically this yields
\ppLXVIIfpCount{} false positives across \ppLXVIIcorrectCount{} correct
programs. \qed
\end{proof}

\begin{corollary}[Benchmark Bug Detection on Paper~67]
On the \ppLXVIIbuggyCount{} buggy programs in the Paper~67 benchmark,
\ReviewBot{} produces at least one $\SevCritical$ finding for each buggy
variant.
\end{corollary}

\section{Lean 4 Proof Sketch}\label{sec:lean}

\begin{lstlisting}[language=lean,basicstyle=\small\ttfamily,
  keywordstyle=\bfseries,frame=single,xleftmargin=1em]
-- Review severity as a judgment-derived classification
inductive Severity where
  | critical  -- obstructions present
  | warning   -- low trust, no obstructions
  | info      -- moderate trust
  | pass      -- solver or proof level
  deriving DecidableEq, Ord

-- Severity from judgment
def classify_severity (J : Judgment) : Severity :=
  if J.obstructions.nonempty then .critical
  else if J.trust <= TrustLevel.copilot then .warning
  else if J.trust <= TrustLevel.oracle then .info
  else .pass

-- Review comment structure
structure ReviewComment where
  coord : Coord
  severity : Severity
  proposition : Prop
  evidence_summary : String
  suggestion : Option String

-- Review completeness
theorem review_completeness
    (S : Site) (delta : Set S.Obj)
    (affected : SubSite S)
    (h_aff : affected = compute_affected S delta)
    (comments : List ReviewComment)
    (h_gen : comments = generate_comments affected)
    : forall U, U \in affected.objects ->
      exists c \in comments, c.coord = U := by
  intro U hU
  rw [h_gen]
  exact generate_comments_complete affected U hU

-- Zero false positives on correct code
theorem zero_false_positives
    (P : Program)
    (h_correct : is_correct P)
    (S : Site)
    (h_site : S = formal_core_site P)
    (comments : List ReviewComment)
    (h_review : comments = review_bot P)
    : forall c \in comments,
      c.severity != Severity.critical := by
  intro c hc
  have h_no_obs := correct_no_obstructions h_correct h_site
  rw [h_review] at hc
  exact severity_not_critical_of_no_obs h_no_obs c hc

-- Bug detection guarantee
theorem bug_detection
    (P : Program)
    (h_buggy : has_semantic_bug P)
    (comments : List ReviewComment)
    (h_review : comments = review_bot P)
    : exists c \in comments,
      c.severity = Severity.critical := by
  obtain \langle coord, h_bug_at \rangle := h_buggy
  have h_obs := bug_produces_obstruction h_bug_at
  exact critical_from_obstruction h_review h_obs
\end{lstlisting}

\section{Implementation}\label{sec:implementation}
% ------------------------------------------------------------------

\ReviewBot{} is implemented as a GitHub App that listens for pull request
events and posts review comments via the GitHub API. The implementation
comprises approximately 1{,}500 lines of \Python{}.

\paragraph{Diff Parsing.}
The diff parser extracts changed hunks and maps them to source locations.
It handles renames, deletions, and additions, computing the minimal set of
affected files.

\paragraph{Judgment Pipeline.}
The core pipeline reuses the \JuGeo{} verification engine. Key subsystem
timings for review-scale inputs:
\begin{itemize}[leftmargin=*]
  \item Site construction: \subFormalcoresiteSmallTime{} (small),
        \subFormalcoresiteMediumTime{} (medium),
        \subFormalcoresiteLargeTime{} (large).
  \item Specification satisfaction: \subSpecificationsatisfactionSmallTime{}
        (small), \subSpecificationsatisfactionMediumTime{} (medium).
  \item Encoding: \subEncodeforsolverSmallTime{} (small),
        \subEncodeforsolverMediumTime{} (medium).
  \item Orchestration: \subOrchestrateverificationSmallTime{} (small),
        \subOrchestrateverificationMediumTime{} (medium).
\end{itemize}

\paragraph{Comment Rendering.}
Review comments are rendered in GitHub-flavored Markdown with:
\begin{itemize}[leftmargin=*]
  \item Severity badges (color-coded).
  \item Proposition in natural language with formal notation in expandable
        details blocks.
  \item Trust level indicator showing the evidence quality.
  \item Suggested fix (when applicable) as a code suggestion block.
\end{itemize}

\paragraph{Caching.}
\ReviewBot{} caches judgments for unchanged coordinates using the same
content-addressed scheme described in Paper~38 and Paper~65. This avoids
re-verifying unmodified code on subsequent pushes to the same pull request.

\section{Python API and Integration}\label{sec:python-api}

\ReviewBot{} exposes a \Python{} API that allows programmatic review of

\subsection{Core Review API}

The current public JuGeo API does not expose a dedicated
\texttt{ReviewSession} class. Instead, the Paper~67 workflow is assembled

\begin{lstlisting}[style=jugeo-python]
from jugeo.easy import bugs, spec

def review_python_source(source: str, review_spec: dict) -> dict:
    """Run the Paper 67 declared-cover review workflow."""
    review = spec(source, review_spec)
    findings = bugs(source)
    return {
        "verdict": "verified" if review.satisfied else "obstructed",
        "trust_level": review.trust_level,
        "mode": review.mode,
        "propositions": len(review.clauses),
        "passed": sum(1 for clause in review.clauses if clause["pass"]),
        "obstructions": list(review.obstructions),
        "bug_count": len(findings),
        "bugs": list(findings),
    }
\end{lstlisting}

This is the user-facing workflow exercised by
\texttt{experiments/exp67\_code\_review\_automation.py}. In the measured
Paper~67 run, the declared-cover review achieves \ppLXVIIrecall{} recall and
\ppLXVIIaccuracyPct{} accuracy with \ppLXVIIfpCount{} false positives.

\subsection{Diff Analysis and Coordinate Mapping}

The \DiffAnalyzer{} module provides fine-grained control over how changed
lines map to semantic coordinates, including transitive dependency tracing
via the discovery pipeline (\subDiscoverypipelineSmallTime{} for small
inputs).

\begin{lstlisting}[style=jugeo-python]
from jugeo.review.diff import DiffAnalyzer
from jugeo.discovery import DiscoveryPipeline
from jugeo.types import Coord, Morphism

def trace_affected_coordinates(diff_text, site):
    """Map diff hunks to coordinates with transitive closure."""
    analyzer = DiffAnalyzer()
    hunks = analyzer.parse_hunks(diff_text)

    # Direct mapping: changed lines -> coordinates
    direct_coords = set()
    for hunk in hunks:
        coords = site.coords_for_lines(
            file_path=hunk.file_path,
            start=hunk.new_start,
            end=hunk.new_start + hunk.new_count,
        )
        direct_coords.update(coords)

    # Transitive closure via morphism tracing
    pipeline = DiscoveryPipeline(site)
    all_affected = pipeline.transitive_closure(
        seeds=direct_coords,
        morphism_types=[
            Morphism.RESTRICTION,
            Morphism.TRANSPORT,
            Morphism.INCLUSION,
        ],
    )

    return all_affected, direct_coords
\end{lstlisting}

The transitive closure step is essential for review completeness
(Theorem~\ref{thm:review-complete}). By tracing all three morphism
types---\compMorphRestriction{} restriction, \compMorphTransport{}
transport, and \compMorphInclusion{} inclusion morphisms---the analyzer
ensures that changes propagating through module boundaries are captured.

\subsection{Batch Review with Trust Aggregation}

For reviewing multiple files or an entire repository, the batch API
aggregates trust across coordinates and produces a summary report.

\begin{lstlisting}[style=jugeo-python]
from jugeo.review import BatchReviewer, TrustAggregator
from jugeo.trust import TrustLevel

def batch_review_repository(repo_path, severity_threshold="WARNING"):
    """Review all source files and aggregate trust statistics."""
    reviewer = BatchReviewer(repo_path)
    aggregator = TrustAggregator()

    results = reviewer.review_all()

    for file_result in results:
        for comment in file_result.comments:
            aggregator.record(
                coord=comment.coord,
                trust=comment.judgment.trust,
                has_obstruction=bool(comment.judgment.obstructions),
            )

    summary = aggregator.summarize()
    # summary.trust_distribution: dict mapping TrustLevel -> count
    # summary.obstruction_rate: float
    # summary.mean_trust_rank: float

    critical = [
        c for r in results for c in r.comments
        if c.severity == "CRITICAL"
    ]
    return summary, critical
\end{lstlisting}

The batch API processes each file through the standard pipeline. On the
Paper~67 benchmark, the declared-cover workflow completes in
\ppLXVIItimeTotal{} total wall-clock time with \ppLXVIItimeMean{} per
program, making small-batch review practical.

\section{Sheaf-Theoretic Foundations for Code Review}\label{sec:sheaf-theory}
% ------------------------------------------------------------------

This section develops the formal sheaf-theoretic framework underlying
\ReviewBot{}'s review pipeline. We show that code review can be modeled
as a descent problem on the judgment sheaf, and that review completeness
and soundness follow from standard sheaf-theoretic properties.

\subsection{The Review Sheaf}

\begin{definition}[Review Presheaf]\label{def:review-presheaf}
Let $\Site$ be the semantic site of a program $P$ with objects $\Ob(\Site)$
and morphisms $\Mor(\Site)$. The \emph{review presheaf}
$\ReviewJudg : \Site^{\mathrm{op}} \to \mathbf{Set}$ assigns to each
coordinate $\coord \in \Ob(\Site)$ the set of review judgments:
\[
  \ReviewJudg(\coord) = \bigl\{\,
    \J = \Jud{\coord}{\prop}{\carrier}{\evid}{\oblig}{\obstr}{\trust}{\prov}
    \;\big|\;
    \prop \in \mathrm{Props}(\coord),\;
    \trust \in \Talg
  \,\bigr\}
\]
For each morphism $f : \coord' \to \coord$, the restriction map
$\res_f : \ReviewJudg(\coord) \to \ReviewJudg(\coord')$ restricts
judgments to the sub-coordinate, preserving trust via the attenuation
operator: $\res_f(\J).\trust = \tatten(\J.\trust, f)$.
\end{definition}

\begin{definition}[Diff Sub-Site]\label{def:diff-subsite}
Given a diff $\Delta$ modifying source locations $L_1, \ldots, L_k$, the
\emph{diff sub-site} $\Site|_\Delta$ is the full sub-site of $\Site$ on
the set of objects:
\[
  \Ob(\Site|_\Delta) = \bigl\{\,
    \coord \in \Ob(\Site)
    \;\big|\;
    \exists\, i.\; \carrier(\coord) \cap L_i \neq \emptyset
  \,\bigr\}^{\mathrm{cl}}
\]
where the closure $(-)^{\mathrm{cl}}$ is taken under morphism tracing:
if $\coord \in \Ob(\Site|_\Delta)$ and $f : \coord' \to \coord$ is a
morphism in $\Site$, then $\coord' \in \Ob(\Site|_\Delta)$.
\end{definition}

\begin{proposition}[Sub-Site Finiteness]\label{prop:subsite-finite}
For any diff $\Delta$ with $|\Delta| = k$ changed locations, the sub-site
$\Site|_\Delta$ has at most $O(k \cdot |\Mor(\Site)|)$ objects.
\end{proposition}

\begin{proof}[Proof Sketch]
Each changed location maps to at most one coordinate directly. The
transitive closure follows morphisms, each of which is traversed at most
once. Since $\Site$ is finite (all programs have finitely many coordinates),
the closure terminates. The bound follows from the morphism count: across
our benchmarks, \compSiteMeanMorphisms{} mean morphisms per site. \qed
\end{proof}

\subsection{Review as Descent}

The key insight connecting sheaf theory to code review is that a
\emph{consistent review} corresponds to a \emph{descent datum} on the
review presheaf.

\begin{definition}[Review Descent Datum]\label{def:review-descent}
A \emph{review descent datum} for the diff sub-site $\Site|_\Delta$ is a
family $\{\J_\coord\}_{\coord \in \Ob(\Site|_\Delta)}$ of judgments such
that for every morphism $f : \coord' \to \coord$ in $\Site|_\Delta$:
\[
  \res_f(\J_\coord) = \J_{\coord'}
\]
That is, the restriction of a judgment along any morphism agrees with the
judgment at the target coordinate.
\end{definition}

\begin{theorem}[Review Consistency via Descent]\label{thm:review-descent}
If the review presheaf $\ReviewJudg$ satisfies the sheaf condition on
$\Site|_\Delta$, then any review descent datum $\{\J_\coord\}$ glues to a
unique global section $\J_{\mathrm{global}} \in \ReviewJudg(\Site|_\Delta)$,
and the review is \emph{internally consistent}: no two comments for
overlapping coordinates can give contradictory severity assessments.
\end{theorem}

\begin{proof}[Proof Sketch]
By the sheaf condition, compatible local sections glue uniquely. If two
coordinates $\coord, \coord'$ overlap (\ie{}, share a common sub-coordinate
$\coord''$ via morphisms $f : \coord'' \to \coord$ and
$g : \coord'' \to \coord'$), then the descent condition forces
$\res_f(\J_\coord) = \J_{\coord''} = \res_g(\J_{\coord'})$. Since
severity is determined by trust and obstructions (Definition~1 in
Section~\ref{sec:severity}), and trust attenuation is monotone, the
severity assessments at $\coord$ and $\coord'$ are consistent at their
overlap. The gluing axiom produces the unique global section. \qed
\end{proof}

\begin{corollary}[No Contradictory Reviews]\label{cor:no-contradiction}
\ReviewBot{} never produces two comments for the same code location where
one asserts $\SevPass$ and another asserts $\SevCritical$.
\end{corollary}

\subsection{Trust Cohomology and Review Obstructions}

The cohomological perspective reveals when a review \emph{cannot} produce
a globally consistent assessment.

\begin{definition}[Review Cohomology]\label{def:review-cohomology}
The \emph{first review cohomology group} $\Hcoh{1}(\Site|_\Delta,
\ReviewJudg)$ classifies the obstructions to gluing local review judgments
into a global review. When $\Hcoh{1}(\Site|_\Delta, \ReviewJudg) = 0$,
every compatible family of local reviews extends to a global review.
\end{definition}

\begin{theorem}[Obstruction Interpretation]\label{thm:obstruction-cohomology}
A nonzero element $[\alpha] \in \Hcoh{1}(\Site|_\Delta, \ReviewJudg)$
corresponds to a collection of coordinates whose judgments are locally
sound but globally incompatible. This occurs precisely when the diff
introduces an inconsistency that manifests only through transitive
dependencies.
\end{theorem}

\begin{proof}[Proof Sketch]
The \v{C}ech complex $\Cech(\Site|_\Delta, \ReviewJudg)$ computes
$\Hcoh{1}$ via alternating differences on overlaps. A nonzero cocycle
$\alpha_{ij} \in \ReviewJudg(\coord_i \cap \coord_j)$ means that
$\res_{f_i}(\J_i) \neq \res_{f_j}(\J_j)$ on the overlap
$\coord_i \cap \coord_j$. Concretely, this arises when a change in
coordinate $\coord_i$ alters the semantics that $\coord_j$ depends on
transitively, but $\coord_j$'s local verification does not detect the
incompatibility. In benchmarks, $\Hcoh{1} = 0$ for all \expTotalPrograms{}
correct programs (\expHOneZero{} zero-cohomology confirmations). \qed
\end{proof}

\section{Advanced Review Algorithms}\label{sec:algorithms}
% ------------------------------------------------------------------

Beyond the core review pipeline (Algorithm~\ref{alg:review}), \ReviewBot{}
employs specialized algorithms for incremental review, severity propagation,
and trust-aware comment ranking.

\subsection{Incremental Review}

When a developer pushes additional commits to a pull request, \ReviewBot{}
performs incremental review by computing the delta between the previous
and current sub-sites.

\begin{algorithm}[t]
\caption{Incremental Review via Site Delta}
\label{alg:incremental}
\begin{algorithmic}[1]
\REQUIRE Previous sub-site $\Site|_{\Delta_1}$, new diff $\Delta_2$,
         cached judgments $\mathcal{J}_{\text{cache}}$
\ENSURE Updated review comments $\mathcal{R}'$
\STATE $\text{new\_coords} \gets
       \texttt{discovery\_pipeline}(\Delta_2) \setminus
       \Ob(\Site|_{\Delta_1})$
\STATE $\text{invalidated} \gets \{\coord \in \Ob(\Site|_{\Delta_1})
       \mid \exists f : \coord' \to \coord,\;
       \coord' \in \text{new\_coords}\}$
\STATE $\text{reuse} \gets \Ob(\Site|_{\Delta_1}) \setminus
       \text{invalidated}$
\STATE $\Site|_{\Delta_1 \cup \Delta_2} \gets
       \texttt{formal\_core\_site}(\text{new\_coords} \cup
       \text{invalidated})$
\STATE $\mathcal{R}' \gets \emptyset$
\FOR{each $\coord \in \text{new\_coords} \cup \text{invalidated}$}
  \STATE $\J \gets \texttt{orchestrate\_verification}(\coord)$
  \STATE $\mathcal{J}_{\text{cache}}[\coord] \gets \J$
  \STATE $\mathcal{R}' \gets \mathcal{R}' \cup
         \{\texttt{generate\_comment}(\J, \Severity(\J))\}$
\ENDFOR
\FOR{each $\coord \in \text{reuse}$}
  \STATE $\mathcal{R}' \gets \mathcal{R}' \cup
         \{\texttt{generate\_comment}(
           \mathcal{J}_{\text{cache}}[\coord],
           \Severity(\mathcal{J}_{\text{cache}}[\coord]))\}$
  \COMMENT{reuse cached judgment}
\ENDFOR
\RETURN $\mathcal{R}'$
\end{algorithmic}
\end{algorithm}

\begin{theorem}[Incremental Correctness]\label{thm:incremental}
Algorithm~\ref{alg:incremental} produces the same review comments as a
full re-review via Algorithm~\ref{alg:review} on the combined diff
$\Delta_1 \cup \Delta_2$.
\end{theorem}

\begin{proof}[Proof Sketch]
Coordinates in the reuse set have carriers disjoint from $\Delta_2$, so
their judgments are unchanged (by carrier locality, Paper~00). Invalidated
coordinates are re-verified, producing fresh judgments. New coordinates
receive fresh judgments. The union of these three sets equals
$\Ob(\Site|_{\Delta_1 \cup \Delta_2})$ by construction. \qed
\end{proof}

\subsection{Severity Propagation Algorithm}

When an obstruction is detected at coordinate $\coord$, \ReviewBot{}
propagates severity information along morphisms to identify all
transitively affected coordinates.

\begin{algorithm}[t]
\caption{Severity Propagation via Morphism Graph}
\label{alg:severity-prop}
\begin{algorithmic}[1]
\REQUIRE Sub-site $\Site|_\Delta$, initial judgments $\mathcal{J}$
\ENSURE Propagated severity map $\sigma : \Ob(\Site|_\Delta) \to
        \{\SevCritical, \SevWarning, \SevInfo, \SevPass\}$
\STATE Initialize $\sigma(\coord) \gets \Severity(\J_\coord)$
       for all $\coord$
\STATE $\text{worklist} \gets \{\coord \mid
       \sigma(\coord) = \SevCritical\}$
\WHILE{$\text{worklist} \neq \emptyset$}
  \STATE Remove $\coord$ from worklist
  \FOR{each morphism $f : \coord' \to \coord$ in $\Site|_\Delta$}
    \IF{$\sigma(\coord') \neq \SevCritical$ and
        $\sigma(\coord') \neq \SevWarning$}
      \STATE $\sigma(\coord') \gets \SevWarning$
      \COMMENT{propagate concern}
      \STATE Add $\coord'$ to worklist
    \ENDIF
  \ENDFOR
\ENDWHILE
\RETURN $\sigma$
\end{algorithmic}
\end{algorithm}

Severity propagation ensures that a reviewer sees warnings on all
coordinates that depend on a buggy coordinate, even if those coordinates
individually verify successfully. The propagation terminates in
$O(|\Ob(\Site|_\Delta)| + |\Mor(\Site|_\Delta)|)$ time, which is
dominated by the morphism count (\compMorphTotal{} total morphisms
across the full benchmark).

\subsection{Trust-Aware Comment Ranking}

The final ranking algorithm orders comments by a composite score combining
severity, trust deficit, and coordinate centrality.

\begin{definition}[Review Priority Score]\label{def:priority}
For a judgment $\J$ at coordinate $\coord$ in sub-site $\Site|_\Delta$,
the \emph{review priority score} is:
\[
  \mathrm{priority}(\J, \coord) =
    w_s \cdot \mathrm{sev\_rank}(\Severity(\J)) +
    w_d \cdot \mathrm{deficit}(\J) +
    w_c \cdot \mathrm{deg}(\coord)
\]
where $\mathrm{sev\_rank}(\SevCritical) = 4$,
$\mathrm{sev\_rank}(\SevWarning) = 3$,
$\mathrm{sev\_rank}(\SevInfo) = 2$,
$\mathrm{sev\_rank}(\SevPass) = 1$;
$\mathrm{deficit}(\J) = \mathrm{rank}(\Tsolver) - \mathrm{rank}(\J.\trust)$;
and $\mathrm{deg}(\coord)$ counts morphisms incident to $\coord$.
Weights default to $w_s = 10$, $w_d = 2$, $w_c = 1$.
\end{definition}

The priority score ensures that critical findings at highly connected
coordinates (which affect many other parts of the code) are surfaced first.
With \compTrustSolverdischarged{} judgments reaching $\Tsolver$
(\compTrustSolverdischargedPct{}), the majority of comments in correct
code receive low priority scores, keeping the review focused on genuine
concerns.

\section{Worked Example}\label{sec:worked-example}
% ------------------------------------------------------------------

We walk through a complete \ReviewBot{} review of two programs: a correct
\texttt{factorial} implementation and a buggy variant
\texttt{factorial\_off\_by\_one}.

\subsection{Correct Program: \texttt{factorial}}

Consider the standard recursive factorial:
\begin{lstlisting}[language=Python,basicstyle=\small\ttfamily,frame=single,
  xleftmargin=1em,numbers=left]
def factorial(n):
    if n <= 1:
        return 1
    return n * factorial(n - 1)
\end{lstlisting}

\ReviewBot{} processes this program through the pipeline:

\paragraph{Stage 1: Diff Analysis.}
The \DiffAnalyzer{} identifies the function body as the changed region,
producing coordinates for the base case, recursive case, and the function
signature.

\paragraph{Stage 2: Site Construction.}
The sub-site $\Site|_\Delta$ contains \ppLXVIIrevfactorialProps{}
coordinates with associated propositions: (i)~base case correctness
($n \leq 1 \Rightarrow \texttt{factorial}(n) = 1$), (ii)~recursive
structure preservation, (iii)~termination via decreasing argument, and
(iv)~non-negativity of the result for $n \geq 0$.

\paragraph{Stage 3: Judgment Production.}
Verification completes in \ppLXVIIrevfactorialTime{} with verdict
\ppLXVIIrevfactorialVerdict{}. All \ppLXVIIrevfactorialProps{} propositions
receive judgments with $\trust \tgeq \Tsolver$, producing $\obstr = \emptyset$.

\paragraph{Stage 4: Comment Generation.}
Since all judgments are $\SevPass$, \ReviewBot{} generates
\ppLXVIIrevfactorialProps{} positive-assurance comments:
\begin{quote}
\small
\textbf{[\SevPass{}]} \texttt{factorial} at line 2--4: Base case
verified. $\texttt{factorial}(n) = 1$ when $n \leq 1$. Trust: $\Tsolver$.
\end{quote}

\subsection{Buggy Program: \texttt{factorial\_off\_by\_one}}

Now consider the buggy variant with an off-by-one error:
\begin{lstlisting}[language=Python,basicstyle=\small\ttfamily,frame=single,
  xleftmargin=1em,numbers=left]
def factorial(n):
    if n <= 1:
        return 1
    return n * factorial(n)  # Bug: should be n-1
\end{lstlisting}

\paragraph{Stage 1--2.} The diff analysis and site construction proceed
identically, producing \ppLXVIIrevfactorialoffbyoneProps{} coordinates.

\paragraph{Stage 3: Judgment Production.}
Verification completes in \ppLXVIIrevfactorialoffbyoneTime{} with verdict
\ppLXVIIrevfactorialoffbyoneVerdict{}. The termination proposition
fails: the recursive call \texttt{factorial(n)} does not decrease the
argument, producing an obstruction $\obstr = \{\text{non-decreasing
recursive argument}\}$. The trust level drops to $\Tcontra$ for the
termination judgment.

\paragraph{Stage 4: Comment Generation.}
\ReviewBot{} generates a $\SevCritical$ comment:
\begin{quote}
\small
\textbf{[\SevCritical{}]} \texttt{factorial} at line 4: \textbf{Infinite
recursion detected.} The recursive call \texttt{factorial(n)} does not
decrease the argument $n$. Expected: \texttt{factorial(n-1)}.
Trust: $\Tcontra$. Obstruction: non-terminating recursion.
\end{quote}

\section{Related Work}\label{sec:related}
% ------------------------------------------------------------------

\paragraph{Automated Code Review.}
Amazon CodeGuru~\cite{codeguru} and DeepCode~\cite{deepcode} use machine
learning to suggest improvements. These tools lack formal guarantees: their
findings may be incorrect. \ReviewBot{} grounds every finding in a formal
judgment with explicit trust level.

\paragraph{Static Analysis Integration.}
CodeQL~\cite{codeql} provides query-based analysis over code databases.
While expressive, CodeQL queries must be manually written and maintained.
\ReviewBot{} derives findings automatically from the judgment sheaf.

\paragraph{Formal Review.}
The seL4 verification project~\cite{klein2009sel4} uses formal verification
in a review-like process. Our approach is lighter-weight, targeting pull
request review rather than full system verification.

\paragraph{Diff-Aware Analysis.}
Facebook Infer~\cite{calcagno2015infer} performs compositional analysis
that can be applied incrementally to changed files. Like \ReviewBot{},
Infer focuses on changed code; unlike \ReviewBot{}, Infer's analysis
is not grounded in a judgment-theoretic framework with explicit trust
levels. Our incremental review algorithm
(Algorithm~\ref{alg:incremental}) achieves similar efficiency gains
through site delta computation.

\paragraph{Trust and Confidence in Analysis.}
Probabilistic program analysis~\cite{cousot2012probabilistic} and
Bayesian bug detection~\cite{kremenek2003z} assign confidence scores
to findings. These approaches use statistical models without formal
trust semantics. \JuGeo{}'s trust algebra $\Talg$ provides a lattice
structure with well-defined operations ($\tjoin$, $\tatten$,
$\tpromote$, $\tdemote$) that enables compositional trust reasoning.

\paragraph{Sheaf-Theoretic Program Analysis.}
The application of sheaf theory to software analysis has been explored
in the context of information integration~\cite{goguen1992sheaf} and
database schema merging. Our contribution is the specific application
to code review, where the sheaf condition provides review consistency
(Theorem~\ref{thm:review-descent}) and cohomology detects transitive
incompatibilities (Theorem~\ref{thm:obstruction-cohomology}).

\paragraph{AI-Assisted Review.}
Large language models have been applied to code review comment
generation~\cite{li2022codereviewer}. While LLM-based tools can
produce fluent comments, they lack formal grounding: an LLM may
hallucinate a bug that does not exist or miss a real one. \ReviewBot{}
combines formal verification with natural-language generation, ensuring
that every comment is backed by a judgment with explicit evidence.

\section{Conclusion}\label{sec:conclusion}
% ------------------------------------------------------------------

\ReviewBot{} demonstrates how judgment-geometric verification can be adapted
to automated review workflows. Every review comment is grounded in a formal
judgment with explicit proposition, evidence, and trust level, and the
severity classification remains a useful design for presenting those results.
On the current Paper~67 corpus, the executable-specification workflow detects
\ppLXVIIdetected{} of \ppLXVIIbuggyCount{} buggy variants while preserving
zero false positives across the \ppLXVIIcorrectCount{} correct programs,
yielding \ppLXVIIaccuracyPct{} accuracy, \ppLXVIIprecision{} precision, and
\ppLXVIIrecall{} recall at a mean runtime of \ppLXVIItimeMean{} per program.
Because the benchmark is intentionally small and hand-constructed, we treat it
as a regression suite for the declared-cover review path rather than as a
claim of broad real-world review completeness.

The sheaf-theoretic framework of Section~\ref{sec:sheaf-theory} provides
a principled foundation: review consistency follows from the sheaf
condition (Theorem~\ref{thm:review-descent}), incremental review
correctness from carrier locality (Theorem~\ref{thm:incremental}), and
transitive bug detection from cohomological obstruction analysis
(Theorem~\ref{thm:obstruction-cohomology}). The \Python{} API
(Section~\ref{sec:python-api}) makes these capabilities accessible
to developers and CI/CD systems.

The case study across \ppLXVIIprogramCount{} programs
(Section~\ref{sec:case-study}) therefore serves mainly as a regression suite:
future systems should preserve these measured results while validating the
workflow on broader and more realistic review corpora.

Future work includes integrating \ReviewBot{} with additional code hosting
platforms, supporting multi-language review via cross-language site
construction, improving proposition generation for buggy diffs, and
fine-tuning comment generation for domain-specific review norms.
