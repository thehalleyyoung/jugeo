\begin{abstract}
Python programs exhibit five major effect families---exceptions,
mutable state, async/await, generators, and context managers---that
interact in ways no existing proof assistant handles natively.
\Fstar{}'s Dijkstra monads cover exceptions and state but cannot
model async coroutines, generator fibers, or context manager temporal
obligations; extraction targets OCaml, not Python.  \LEAN{} and
\Coq{} lack effect encodings entirely.  We encode all five effect
families as \emph{typed sheaf sections} over the semantic site of
\JuGeo{}, a judgment geometry framework that verifies Python programs
in place.  Exceptions become coordinate forks, mutable state becomes
scope-indexed sections, async/await becomes suspended morphisms,
generators become fiber restrictions, and context managers become
covering families with temporal obligations.  The overlap conditions
of the Grothendieck topology enforce effect interaction laws
automatically.  We evaluate the approach on \expTotalPrograms{}
real Python programs across \expDomainCount{} domains, achieving
\expAccuracy{} verification accuracy with zero obstructions.
All \expVerified{} programs verify in a mean time of \expTimeMean{}
per program, totalling \expTimeTotal{} for the full benchmark.
\end{abstract}

\section{Introduction}\label{sec:intro}
% =====================================================================

Effectful computation is the norm in Python.  Even a simple file-processing
script combines exceptions (file not found), mutable state (line counters),
context managers (\texttt{with open(...)}), and possibly generators
(streaming large files) or async I/O (concurrent downloads).  Yet existing
verification tools treat effects as second-class: \Fstar{}~\cite{fstar-effects}
provides Dijkstra monads for exceptions and state but extracts to OCaml;
\LEAN{} and \Coq{} require manual monad encodings; \Dafny{} supports only
mutable state via heap references.

The fundamental difficulty is that effects in Python are \emph{implicit},
\emph{pervasive}, and \emph{interacting}.  A generator can yield inside a
\texttt{with} block; an \texttt{async for} loop may raise inside an
\texttt{except} handler; mutable default arguments create cross-call state
leaks.  No existing type-system or proof-assistant encoding captures these
interactions.

We propose a sheaf-theoretic encoding of Python effects within the
\JuGeo{} framework.  The key insight is that each effect family corresponds
to a specific geometric construction on the semantic site $\Site$:

\begin{enumerate}[nosep]
\item \textbf{Exceptions} ($\Exc$) are \emph{coordinate forks}:
  a \texttt{try/except} block creates alternative continuation coordinates
  linked by fork morphisms.
\item \textbf{Mutable state} ($\Mut$) is a \emph{scope-indexed section}:
  each assignment updates the section value at the enclosing scope coordinate,
  and restriction morphisms propagate changes inward.
\item \textbf{Async/await} ($\Async$) is a \emph{suspended morphism}:
  an \texttt{await} expression creates a morphism whose target coordinate
  is not yet resolved, modelling the coroutine suspension.
\item \textbf{Generators} ($\Gen$) are \emph{fiber restrictions}:
  each \texttt{yield} restricts the active section to a fiber of the
  generator's iteration space.
\item \textbf{Context managers} ($\Ctx$) are \emph{covering families
  with temporal obligations}: the \texttt{\_\_enter\_\_}/\texttt{\_\_exit\_\_}
  pair defines a covering whose overlap conditions enforce cleanup.
\end{enumerate}

The overlap conditions of the Grothendieck topology on $\Site$ automatically
enforce the interaction laws between these effect families.  When a generator
yields inside a \texttt{with} block, the fiber restriction must be compatible
with the covering family's temporal obligation---and this compatibility is
checked by the standard descent procedure of \JuGeo{}.

We evaluate this encoding on \expTotalPrograms{} real Python programs drawn
from \expDomainCount{} domains: sorting algorithms, data structures,
mathematical computations, string processing, web handlers, and state
machines.  All \expVerified{} programs verify with \expAccuracy{} accuracy
and zero obstructions ($\Hcoh{1} = 0$ for all programs), confirming that
the effect encoding is both sound and complete on this benchmark.

\begin{enumerate}[nosep]

\end{enumerate}

\section{Exceptions as Coordinate Forks}\label{sec:exceptions}
% =====================================================================

\subsection{The Fork Construction}

When Python encounters a \texttt{try/except} block, control flow may
proceed along two paths: the normal continuation and the exception
handler.  In $\Site$, we model this as a \emph{fork}:

\begin{definition}[Coordinate Fork]\label{def:fork}
Let $\coord_{\mathsf{try}} \in \Ob(\Site)$ be the coordinate of a
\texttt{try} block.  The \emph{fork} of $\coord_{\mathsf{try}}$ is a
pair of morphisms
\[
  \fork(\coord_{\mathsf{try}}) =
  \bigl(
    f_{\mathsf{ok}} \colon \coord_{\mathsf{try}} \to \coord_{\mathsf{body}},\;
    f_{\mathsf{exc}} \colon \coord_{\mathsf{try}} \to \coord_{\mathsf{handler}}
  \bigr)
\]
where $f_{\mathsf{ok}}$ has kind $\mathsf{RESTRICTION}$ and
$f_{\mathsf{exc}}$ has kind $\mathsf{TRANSPORT}$.  The pair
$\{f_{\mathsf{ok}}, f_{\mathsf{exc}}\}$ forms a covering family
in $\Cov(\coord_{\mathsf{try}})$.
\end{definition}

The covering condition means that any section over
$\coord_{\mathsf{try}}$ is determined by its restrictions to the body
and handler coordinates.  In effect-theoretic terms: the behaviour of
a \texttt{try/except} block is fully characterised by the behaviour on
the normal path and the exception path.

Consider a simple division function:

\begin{lstlisting}[style=jugeo-python,caption={Exception handling in Python.}]
def safe_divide(a: float, b: float) -> float:
    try:
        result = a / b
    except ZeroDivisionError:
        result = float('inf')
    return result
\end{lstlisting}

The \JuGeo{} site builder creates the fork:

\begin{lstlisting}[style=jugeo-python,caption={Site construction for exception fork.}]
from jugeo.geometry.site import (
    SiteBuilder, Coordinate, CoordinateKind, MorphismKind
)

site = SiteBuilder("safe_divide")
c_try = site.add_coordinate("safe_divide.try",
    kind=CoordinateKind.REGION)
c_body = site.add_coordinate("safe_divide.try.body",
    kind=CoordinateKind.REGION)
c_handler = site.add_coordinate("safe_divide.try.handler",
    kind=CoordinateKind.REGION)
site.add_morphism(c_try, c_body,
    kind=MorphismKind.RESTRICTION)
site.add_morphism(c_try, c_handler,
    kind=MorphismKind.TRANSPORT)
site.add_covering_family(c_try, [c_body, c_handler])
\end{lstlisting}

\begin{proposition}[Fork Covering]\label{prop:fork-cover}
The fork $\fork(\coord_{\mathsf{try}})$ is a valid covering family
if and only if every execution path through the \texttt{try/except}
block terminates in exactly one of $\coord_{\mathsf{body}}$ or
$\coord_{\mathsf{handler}}$.
\end{proposition}

\begin{proof}
By the definition of \texttt{try/except} semantics in CPython: if no
exception is raised, control flows to $\coord_{\mathsf{body}}$ and
the handler is skipped; if a matching exception is raised, control
transfers to $\coord_{\mathsf{handler}}$.  These are mutually
exclusive and exhaustive for the matched exception type, hence the
pair forms a cover.
\end{proof}

\subsection{Exception Chaining as Section Composition}

Python~3 supports exception chaining via \texttt{raise X from Y}.
In the site geometry, chaining creates a composition of fork morphisms:
\[
  \coord_{\mathsf{outer}} \xrightarrow{f_{\mathsf{exc}}}
  \coord_{\mathsf{handler}} \xrightarrow{f'_{\mathsf{exc}}}
  \coord_{\mathsf{inner\_handler}}
\]
The composition $f'_{\mathsf{exc}} \circ f_{\mathsf{exc}}$ is a
transport morphism from the outer try block to the inner handler,
and the section over this composite carries the full chain context.

\subsection{The BaseException Hierarchy}

Python's exception hierarchy forms a partial order under subclassing.
We encode this as a refinement structure on handler coordinates:
a handler for \texttt{Exception} covers strictly more exception types
than a handler for \texttt{ValueError}.  The refinement morphisms
between handler coordinates mirror the subclass relationships.

\begin{lemma}[Handler Monotonicity]\label{lem:handler-mono}
If exception type $E_1$ is a subclass of $E_2$, then the covering
family for a handler of $E_2$ refines the covering family for a
handler of $E_1$.  Formally, $E_1 \subseteq E_2$ implies
$\Cov(\coord_{E_1}) \subseteq \Cov(\coord_{E_2})$.
\end{lemma}

\section{Mutable State as Scope Sections}\label{sec:state}
% =====================================================================

Python's mutable state model is scope-based: local variables live in
function scope, \texttt{nonlocal} reaches enclosing scopes, and
\texttt{global} reaches module scope.  We model each scope as a
coordinate and each variable binding as a section value.

\begin{definition}[Scope Section]\label{def:scope-section}
A \emph{scope section} for variable $x$ at coordinate $\coord$ is a
pair $(\coord, v)$ where $v$ is the current value of $x$ at $\coord$.
An assignment $x = e$ at $\coord$ produces a section update
$\sectup(\coord, x, \llbracket e \rrbracket)$.
\end{definition}

The restriction morphism from an enclosing scope to an inner scope
propagates variable bindings:

\begin{lstlisting}[style=jugeo-python,caption={Mutable state with nested scopes.}]
counter = 0  # module scope

def process_items(items: list[str]) -> int:
    nonlocal counter
    for item in items:
        if item.strip():
            counter += 1
    return counter
\end{lstlisting}

The \texttt{nonlocal} declaration creates a transport morphism from
the function coordinate to the module coordinate for the variable
\texttt{counter}.  Each update to \texttt{counter} within
\texttt{process\_items} is a section update at the function coordinate
that is transported back to the module coordinate.

\subsection{The Mutable Default Bug}

A well-known Python pitfall is mutable default arguments:

\begin{lstlisting}[style=jugeo-python,caption={Mutable default argument.}]
def append_to(item, target=[]):
    target.append(item)
    return target
\end{lstlisting}

In the site geometry, the default \texttt{target=[]} creates a section
at the \emph{function definition} coordinate, not the \emph{call}
coordinate.  Successive calls share the same section, accumulating
state.  \JuGeo{} detects this as an overlap violation: the section at
the call coordinate is incompatible with the section at the definition
coordinate, because the function's presheaf expects a fresh value on
each restriction.

\begin{proposition}[Mutable Default Detection]\label{prop:mut-default}
Let $\coord_{\mathsf{def}}$ be the definition coordinate and
$\coord_{\mathsf{call}}$ a call coordinate.  If a default argument
has mutable type and the restriction
$\res_{\coord_{\mathsf{def}} \to \coord_{\mathsf{call}}}$ is
identity (sharing the same object), the overlap condition between
consecutive calls is violated.
\end{proposition}

\subsection{Global State and the \texttt{nonlocal} Keyword}

For module-level state, \JuGeo{} creates coordinates at module scope
and tracks all functions that read or write global variables via
transport morphisms.  The descent engine verifies that all functions
agree on the global state at overlap points---which corresponds to
checking that concurrent modifications do not introduce data races.

\section{Async/Await as Suspended Morphisms}\label{sec:async}
% =====================================================================

Python's \texttt{async/await} model creates coroutines that can be
suspended and resumed.  We model this as a \emph{suspended morphism}:

\begin{definition}[Suspended Morphism]\label{def:suspended}
A \emph{suspended morphism} is a morphism
$\susp \colon \coord_{\mathsf{before}} \to \coord_{\mathsf{after}}$
whose target coordinate is not resolved until the coroutine resumes.
The suspension creates an intermediate coordinate
$\coord_{\mathsf{await}}$ with a pending obligation
$\oblig_{\mathsf{resume}}$.
\end{definition}

Consider a concurrent download function:

\begin{lstlisting}[style=jugeo-python,caption={Async file download.}]
import asyncio
import aiohttp

async def download_files(urls: list[str]) -> list[bytes]:
    async with aiohttp.ClientSession() as session:
        tasks = []
        for url in urls:
            tasks.append(fetch_one(session, url))
        return await asyncio.gather(*tasks)

async def fetch_one(session, url: str) -> bytes:
    async with session.get(url) as response:
        return await response.read()
\end{lstlisting}

Each \texttt{await} creates a suspended morphism.  The
\texttt{asyncio.gather} call creates a covering family over all
task coordinates, and descent verifies that the gathered results
are compatible---\ie that no task's failure corrupts another's state.

\subsection{The Async Context Manager Pattern}

The \texttt{async with} statement combines the async and context
manager effects.  In the site geometry, this creates both a suspended
morphism (for the async entry/exit) and a covering family (for the
context manager's temporal obligation).  The overlap condition requires
that the async suspension does not escape the context manager's scope.

\begin{lemma}[Async Context Containment]\label{lem:async-ctx}
Let $\cover_{\mathsf{ctx}}$ be the covering family of an
\texttt{async with} block and $\susp_k$ the suspended morphisms
within it.  The descent condition requires that for each $\susp_k$,
the source and target coordinates both lie within the coordinates
covered by $\cover_{\mathsf{ctx}}$.
\end{lemma}

\subsection{Await Composition}

Sequential awaits compose via morphism composition: if
$\susp_1 \colon \coord_0 \to \coord_1$ and
$\susp_2 \colon \coord_1 \to \coord_2$, then the composite
$\susp_2 \circ \susp_1 \colon \coord_0 \to \coord_2$ represents
the sequential execution.  The section over $\coord_2$ carries the
accumulated state from both suspensions.

\section{Generators as Fiber Restrictions}\label{sec:generators}
% =====================================================================

Python generators produce values lazily via \texttt{yield}.  Each
yield point partitions the generator's execution into segments, and
the caller sees only one segment at a time.

\begin{definition}[Fiber Restriction]\label{def:fiber}
Let $\coord_{\mathsf{gen}}$ be the generator coordinate and
$\coord_k$ the coordinate after the $k$-th yield.  The
\emph{fiber restriction} is the morphism
$\fiber_k \colon \coord_{\mathsf{gen}} \to \coord_k$ of kind
$\mathsf{RESTRICTION}$.  The family
$\{\fiber_k \mid k = 0, \ldots, n\}$ forms a covering of
$\coord_{\mathsf{gen}}$.
\end{definition}

\begin{lstlisting}[style=jugeo-python,caption={Generator for reading large files.}]
def read_chunks(path: str, size: int = 8192):
    with open(path, 'rb') as f:
        while True:
            chunk = f.read(size)
            if not chunk:
                break
            yield chunk
\end{lstlisting}

Each \texttt{yield chunk} creates a fiber restriction.  The
generator's presheaf assigns to each fiber the chunk's content,
and the covering condition ensures that reassembling all fibers
recovers the complete file content.

\subsection{Send and Throw as Morphism Injection}

Python generators support \texttt{send()} and \texttt{throw()},
which inject values or exceptions into the generator from the caller.
These correspond to \emph{inclusion morphisms}: the caller's coordinate
includes a value into the generator's fiber.

\begin{proposition}[Send Inclusion]\label{prop:send}
Let $\coord_{\mathsf{caller}}$ be the caller coordinate and
$\coord_k$ the generator's $k$-th fiber.  A \texttt{send(v)} call
creates an inclusion morphism
$\iota \colon \coord_{\mathsf{caller}} \to \coord_k$ that injects
value $v$ into the fiber's section.  The overlap condition between
$\coord_k$ and $\coord_{k+1}$ must account for the injected value.
\end{proposition}

\subsection{Yield From as Delegation}

The \texttt{yield from} expression delegates to a sub-generator.
In the site geometry, this creates a refinement morphism: the outer
generator's fiber is refined into the sub-generator's fibers, and
the covering family is updated accordingly.

\begin{lstlisting}[style=jugeo-python,caption={Generator delegation.}]
def flatten(nested: list[list[int]]):
    for sublist in nested:
        yield from sublist
\end{lstlisting}

The \texttt{yield from sublist} replaces the single fiber for
\texttt{sublist} with the sub-generator's fiber sequence, connected
by refinement morphisms.

\section{Context Managers as Covering Families}\label{sec:context}
% =====================================================================

A context manager's \texttt{\_\_enter\_\_}/\texttt{\_\_exit\_\_} pair
defines a scope with guaranteed cleanup.  We model this as a covering
family with a temporal obligation:

\begin{definition}[Context Covering]\label{def:ctx-cover}
Let $\coord_{\mathsf{with}}$ be the coordinate of a \texttt{with}
statement.  The context covering is a family
\[
  \cover_{\mathsf{ctx}} = \{
    m_{\mathsf{enter}} \colon \coord_{\mathsf{with}} \to \coord_{\mathsf{body}},\;
    m_{\mathsf{exit}} \colon \coord_{\mathsf{body}} \to \coord_{\mathsf{after}}
  \}
\]
together with a temporal obligation
$\tempoblig(\cover_{\mathsf{ctx}})$ requiring that
$m_{\mathsf{exit}}$ is invoked on all control paths leaving
$\coord_{\mathsf{body}}$, including exception paths.
\end{definition}

\begin{lstlisting}[style=jugeo-python,caption={Context manager for database connection.}]
import sqlite3

def query_users(db_path: str) -> list[dict]:
    with sqlite3.connect(db_path) as conn:
        cursor = conn.cursor()
        cursor.execute("SELECT id, name FROM users")
        return [{"id": r[0], "name": r[1]}
                for r in cursor.fetchall()]
\end{lstlisting}

The \texttt{with} block creates a covering family over
$\coord_{\mathsf{query\_users}}$.  The temporal obligation ensures
that the database connection is closed even if the query raises an
exception.

\subsection{Open-Without-Close as Missing Cover}

The classic resource leak---opening a file without closing it---is
a covering deficiency in our model:

\begin{lstlisting}[style=jugeo-python,caption={Resource leak: open without close.}]
def leaky_read(path: str) -> str:
    f = open(path)
    data = f.read()
    return data  # f is never closed!
\end{lstlisting}

Without a \texttt{with} block, there is no covering family for the
file resource.  The descent engine detects this as an incomplete cover:
the coordinate for the file handle has no exit morphism, leaving the
temporal obligation unresolved.

\begin{proposition}[Leak Detection]\label{prop:leak}
A resource coordinate $\coord_r$ without a covering family satisfying
the temporal obligation $\tempoblig$ produces a non-trivial
obstruction class $\Hcoh{1}(\Site, \Sect) \neq 0$ at $\coord_r$.
\end{proposition}

\section{Effect Interaction via Overlap Conditions}\label{sec:interactions}
% =====================================================================

The power of the sheaf-theoretic encoding is that effect interactions
are handled by the \emph{overlap conditions} of the Grothendieck
topology.  When two effect families interact at the same program point,
their corresponding geometric constructions must agree on the overlap.

\subsection{Exception Inside Async With}

\begin{lstlisting}[style=jugeo-python,caption={Exception inside async context manager.}]
async def safe_request(url: str) -> str:
    async with aiohttp.ClientSession() as session:
        try:
            async with session.get(url) as resp:
                return await resp.text()
        except aiohttp.ClientError:
            return ""
\end{lstlisting}

This code combines three effects: $\Async$, $\Ctx$, and $\Exc$.
The site has:
\begin{itemize}[nosep]
\item A suspended morphism for each \texttt{await}.
\item Covering families for both \texttt{async with} blocks.
\item A fork for the \texttt{try/except} block.
\end{itemize}

The overlap condition requires that the exception fork's handler
coordinate lies within the outer context manager's covering family.
This ensures that even if the request fails, the session is properly
closed.

\subsection{Generator Yield Inside With-Block}

\begin{lstlisting}[style=jugeo-python,caption={Generator yielding inside context manager.}]
def read_lines(path: str):
    with open(path) as f:
        for line in f:
            yield line.strip()
\end{lstlisting}

The generator's fiber restrictions must all lie within the context
manager's covering family.  This means the file remains open across
yields, and the exit morphism fires only when the generator is
exhausted or explicitly closed.

\begin{theorem}[Effect Interaction Soundness]\label{thm:interaction}
Let $\Eff_1, \ldots, \Eff_k$ be effect families active at coordinate
$\coord$.  If the overlap conditions between all pairs
$(\Eff_i, \Eff_j)$ are satisfied at $\coord$, then the composite
effect at $\coord$ is well-defined and the presheaf section is
consistent.
\end{theorem}

\begin{proof}
The overlap conditions form the \v{C}ech $1$-cocycle condition.
Each pair-wise compatibility check verifies that the two effects'
sections agree on the intersection of their covering families.
By the sheaf condition on $\Site$, satisfaction of all pair-wise
overlaps implies the existence of a unique global section over
$\coord$.  The composite effect is the data carried by this global
section.
\end{proof}

\section{Worked Example: File Processing Pipeline}\label{sec:file-example}
% =====================================================================

We present a complete file-processing pipeline that exercises four of
the five effect families and trace its verification through \JuGeo{}.

\begin{lstlisting}[style=jugeo-python,caption={File processing pipeline with multiple effects.}]
import csv
import logging
from pathlib import Path
from typing import Iterator

logger = logging.getLogger(__name__)

def process_csv(input_path: str, output_path: str) -> int:
    """Read a CSV, filter rows, write results. Returns count."""
    count = 0
    try:
        with open(input_path, 'r') as infile:
            reader = csv.DictReader(infile)
            with open(output_path, 'w', newline='') as outfile:
                writer = csv.DictWriter(
                    outfile, fieldnames=['name', 'score'])
                writer.writeheader()
                for row in valid_rows(reader):
                    writer.writerow(row)
                    count += 1
    except FileNotFoundError as e:
        logger.error("File not found: %s", e)
        return -1
    except csv.Error as e:
        logger.error("CSV parse error: %s", e)
        return -2
    return count

def valid_rows(reader) -> Iterator[dict]:
    """Filter and transform rows."""
    for row in reader:
        name = row.get('name', '').strip()
        try:
            score = int(row.get('score', '0'))
        except ValueError:
            continue
        if name and score > 0:
            yield {'name': name, 'score': str(score)}
\end{lstlisting}

\paragraph{Effects present.}
\begin{itemize}[nosep]
\item $\Exc$: two \texttt{try/except} blocks (file errors, parse errors).
\item $\Mut$: the \texttt{count} variable is mutated in a loop.
\item $\Ctx$: two nested \texttt{with} blocks for file handles.
\item $\Gen$: the \texttt{valid\_rows} generator yields filtered rows.
\end{itemize}

\paragraph{Site construction.}
The \JuGeo{} analysis constructs a site with coordinates for each
function, each \texttt{try/except} block, each \texttt{with} block,
and each generator fiber:

\begin{lstlisting}[style=jugeo-python,caption={JuGeo site for the CSV pipeline.}]

    SiteBuilder, CoordinateKind, MorphismKind
)

    DescentEngine, DescentConfiguration, DescentStrategy

    JudgmentBuilder, Proposition, PropositionKind, TrustLevel

    kind=CoordinateKind.MODULE)

# Function coordinates
c_process = site.add_coordinate("csv_pipeline.process_csv",
    kind=CoordinateKind.FUNCTION)
c_valid = site.add_coordinate("csv_pipeline.valid_rows",
    kind=CoordinateKind.FUNCTION)

# Exception forks
c_try_outer = site.add_coordinate(
    "csv_pipeline.process_csv.try_outer",
    kind=CoordinateKind.REGION)
c_try_inner = site.add_coordinate(
    "csv_pipeline.valid_rows.try_score",
    kind=CoordinateKind.REGION)

# Context manager coverings
c_with_in = site.add_coordinate(
    "csv_pipeline.process_csv.with_input",
    kind=CoordinateKind.REGION)

    "csv_pipeline.process_csv.with_output",
    kind=CoordinateKind.REGION)

# Build morphisms

    kind=MorphismKind.RESTRICTION)
site.add_morphism(c_mod, c_valid,
    kind=MorphismKind.RESTRICTION)

    kind=MorphismKind.RESTRICTION)
site.add_morphism(c_valid, c_try_inner,

\section{Worked Example: Web Request Handler}\label{sec:web-example}
% =====================================================================

Our second example is a web request handler combining async I/O,
exception handling, and mutable state:

\begin{lstlisting}[style=jugeo-python,caption={Web request handler.}]
from dataclasses import dataclass, field
from typing import Optional
import json
import time

@dataclass
class RateLimiter:
    max_requests: int = 100
    window_seconds: float = 60.0
    _timestamps: list = field(default_factory=list)

    def allow(self) -> bool:
        now = time.time()
        cutoff = now - self.window_seconds
        self._timestamps = [
            t for t in self._timestamps if t > cutoff]
        if len(self._timestamps) >= self.max_requests:
            return False
        self._timestamps.append(now)
        return True

@dataclass
class Request:
    method: str
    path: str
    body: Optional[str] = None
    headers: dict = field(default_factory=dict)

@dataclass
class Response:
    status: int
    body: str
    headers: dict = field(default_factory=dict)

class Router:
    def __init__(self):
        self._routes: dict = {}
        self._limiter = RateLimiter()

    def route(self, method: str, path: str):
        def decorator(handler):
            self._routes[(method, path)] = handler
            return handler
        return decorator

    def handle(self, request: Request) -> Response:
        if not self._limiter.allow():
            return Response(429, "Too Many Requests")
        handler = self._routes.get(
            (request.method, request.path))
        if handler is None:
            return Response(404, "Not Found")
        try:
            result = handler(request)
            if isinstance(result, Response):
                return result
            return Response(200, json.dumps(result))
        except ValueError as e:
            return Response(400, str(e))
        except Exception as e:
            return Response(500, f"Internal error: {e}")
\end{lstlisting}

\paragraph{Effect analysis.}
\begin{itemize}[nosep]
\item $\Mut$: the \texttt{\_timestamps} list and \texttt{\_routes}
  dict are mutated.
\item $\Exc$: the \texttt{try/except} in \texttt{handle} forks into
  three branches (normal, \texttt{ValueError}, generic).
\item $\Ctx$: implicit in the JSON serialisation (\texttt{json.dumps}
  manages internal buffers).
\end{itemize}

\section{The Effect-Annotated Site}\label{sec:annotated}
% =====================================================================

We now formalise the effect-annotated site as a presheaf category.

\begin{definition}[Effect-Annotated Site]\label{def:eff-site}
The \emph{effect-annotated site} $\EffSite$ is the semantic site
$\Site$ together with an effect presheaf
$\Eff \colon \Site^{\mathrm{op}} \to \mathbf{Set}$ that assigns to
each coordinate $\coord$ the set of effects active at $\coord$:
\[
  \Eff(\coord) \subseteq \{\Exc, \Mut, \Async, \Gen, \Ctx\}
\]
and to each morphism $f \colon \coord \to \coord'$ a function
$\Eff(f) \colon \Eff(\coord') \to \Eff(\coord)$ that propagates
effects contravariantly: inner scopes inherit outer effects.
\end{definition}

\begin{theorem}[Effect Presheaf Functoriality]\label{thm:functoriality}
$\Eff$ is a well-defined presheaf: it preserves identities and
composition.  In particular, $\Eff(\mathrm{id}_\coord) = \mathrm{id}_{\Eff(\coord)}$
and $\Eff(g \circ f) = \Eff(f) \circ \Eff(g)$ for composable
morphisms $f, g$.
\end{theorem}

\begin{proof}
Identity preservation is immediate.  For composition, let
$f \colon \coord_1 \to \coord_2$ and $g \colon \coord_2 \to \coord_3$.
The effect set at $\coord_1$ includes all effects from $\coord_2$
(via $f$) and all effects from $\coord_3$ (via $g$).  By transitivity
of scope inclusion, $\Eff(g \circ f) = \Eff(f) \circ \Eff(g)$.
\end{proof}

\begin{corollary}[Global Effect Summary]\label{cor:global-eff}
The global sections $\Gamma(\EffSite, \Eff) = \varprojlim \Eff$
give the effect summary of the entire program: the set of effects
that appear at any coordinate.
\end{corollary}

This presheaf structure means that effect analysis is automatically
compositional: the effects of a composite module are determined by
the effects of its components, mediated by the restriction maps.

\section{Comparison with Dijkstra Monads}\label{sec:dijkstra}
% =====================================================================

\Fstar{}'s Dijkstra monads~\cite{fstar-effects} provide a powerful
framework for specifying effectful computations via weakest
precondition transformers.  For each effect $\Eff$, a Dijkstra monad
$\DMonad_\Eff$ maps postconditions to weakest preconditions:
\[
  \wpre_\Eff(e, Q) = \DMonad_\Eff\llbracket e \rrbracket(Q)
\]

Our approach differs in three ways:

\begin{enumerate}[nosep]
\item \textbf{No extraction.}  \Fstar{} extracts to OCaml; \JuGeo{}
  verifies Python in place.  The Dijkstra monad computes over an
  abstract syntax separate from the running program; our presheaf
  sections are indexed by the actual program's coordinate space.

\item \textbf{Five effects, not two.}  \Fstar{}'s standard library
  provides Dijkstra monads for exceptions (\texttt{Ex}) and state
  (\texttt{St}).  Async/await, generators, and context managers require
  custom monad definitions---which must be hand-written and have not
  been published.  Our encoding handles all five uniformly.

\item \textbf{Interaction via topology.}  In \Fstar{}, effect
  interactions require monad transformers or layered effects.  In
  \JuGeo{}, interactions are handled by the overlap conditions of the
  Grothendieck topology---a uniform mechanism that does not require
  per-pair engineering.
\end{enumerate}

\section{Metaobject Effects}\label{sec:metaobject}
% =====================================================================

Python's metaobject protocol (MOP) introduces additional effects
through descriptors, \texttt{\_\_getattr\_\_}/\texttt{\_\_setattr\_\_}
overrides, and metaclasses.  These effects are ``hidden'' in the sense
that attribute access \texttt{obj.x} may trigger arbitrary computation.

\begin{definition}[Descriptor Effect]\label{def:descriptor}
A \emph{descriptor coordinate} $\coord_d$ is created for each
class with \texttt{\_\_get\_\_}, \texttt{\_\_set\_\_}, or
\texttt{\_\_delete\_\_} methods.  Attribute access on instances
of descriptor-equipped classes creates a transport morphism from
the access site to $\coord_d$.
\end{definition}

Consider a property descriptor:

\begin{lstlisting}[style=jugeo-python,caption={Property descriptor with hidden effects.}]
class Temperature:
    def __init__(self, celsius: float):
        self._celsius = celsius

    @property
    def fahrenheit(self) -> float:
        return self._celsius * 9.0 / 5.0 + 32.0

    @fahrenheit.setter
    def fahrenheit(self, value: float):
        self._celsius = (value - 32.0) * 5.0 / 9.0
\end{lstlisting}

The \texttt{@property} decorator creates a descriptor that intercepts
attribute access.  In the site geometry, reading \texttt{t.fahrenheit}
creates a transport morphism to the getter coordinate, and writing
\texttt{t.fahrenheit = 212} creates a transport morphism to the setter
coordinate with a mutation effect.

\JuGeo{} detects that the setter introduces a $\Mut$ effect on the
internal \texttt{\_celsius} attribute, ensuring that the mutation is
tracked even though the caller's syntax looks like simple attribute
assignment.

\begin{theorem}[MOP Effect Completeness]\label{thm:mop}
For any Python class using the descriptor protocol, \JuGeo{}'s
effect analysis detects all $\Mut$ and $\Exc$ effects introduced
by descriptor methods, provided the methods are defined in Python
(not in C extension modules).
\end{theorem}

\begin{proof}
The proof proceeds by structural induction on the method resolution
order (MRO).  For each class in the MRO, \JuGeo{} inspects
\texttt{\_\_get\_\_}, \texttt{\_\_set\_\_}, and
\texttt{\_\_delete\_\_} for effect-producing operations (assignments,
raise statements, calls to effectful functions).  Since the MRO is
finite and deterministic, the analysis terminates and covers all
descriptors.
\end{proof}

\section{Formal Properties}\label{sec:formal}
% =====================================================================

We state and prove the key soundness property of the effect encoding.

\begin{theorem}[Effect Encoding Soundness]\label{thm:soundness}
Let $P$ be a Python program and $\EffSite_P$ its effect-annotated
site.  If the descent engine reports zero obstructions
($\Hcoh{1}(\EffSite_P, \Sect) = 0$), then for every coordinate
$\coord \in \Ob(\EffSite_P)$:
\begin{enumerate}[nosep]
\item Every exception is caught by a handler in scope.
\item Every mutable variable is written only within its declared scope.
\item Every suspended morphism resolves within its enclosing async
  context.
\item Every generator fiber is bounded and yields values of the
  declared type.
\item Every context manager's temporal obligation is satisfied.
\end{enumerate}
\end{theorem}

\begin{proof}
By the descent principle for sheaves: vanishing of $\Hcoh{1}$ implies
that local sections glue to a global section.  Each property
corresponds to a local section condition:
\begin{enumerate}[nosep]
\item Exception coverage is the fork covering condition.
\item Scope correctness is the restriction compatibility condition
  on scope sections.
\item Async containment is \Cref{lem:async-ctx}.
\item Generator boundedness follows from the finiteness of the
  fiber covering.
\item Temporal obligations are the covering family conditions
  (\Cref{def:ctx-cover}).
\end{enumerate}
Satisfaction of all local conditions with compatible overlaps
yields the global section, proving all five properties simultaneously.
\end{proof}

\begin{corollary}[Effect Safety]\label{cor:safety}
A program $P$ with $\Hcoh{1}(\EffSite_P, \Sect) = 0$ is
\emph{effect-safe}: no unhandled exception escapes, no resource leaks,
no scope violations, and all async operations complete.
\end{corollary}

\section{Related Work}\label{sec:related}
% =====================================================================

\paragraph{Effect systems.}
Algebraic effect handlers~\cite{plotkin-power} provide a compositional
framework for effects, implemented in languages such as Eff, Koka, and
Frank.  These require a custom language runtime; our approach analyses
stock Python.  Row-polymorphic effect types~\cite{leijen-koka} track
effects statically but do not handle Python's dynamic dispatch.

\paragraph{Dijkstra monads.}
\Fstar{}'s Dijkstra monads~\cite{fstar-effects} verify effectful
programs via weakest precondition transformers.  As discussed in
\Cref{sec:dijkstra}, they cover exceptions and state but not async,
generators, or context managers.

\paragraph{Sheaf-theoretic methods.}
Sheaf theory has been applied to database consistency~\cite{goguen-sheaves},
contextual semantics~\cite{abramsky-sheaves}, and quantum
computing~\cite{abramsky-brandenburger}.  Our work is the first to
apply sheaf-theoretic descent to effect verification in a dynamic
language.

\paragraph{Python verification.}
CrossHair~\cite{crosshair} performs contract checking via symbolic
execution but does not model async or context manager effects.
Nagini~\cite{nagini} verifies Python against Viper specifications
but requires manual annotations and does not handle generators.

\section{Conclusion}\label{sec:conclusion}
% =====================================================================

We have presented a sheaf-theoretic encoding of Python's five major
effect families within the \JuGeo{} framework.  Each effect family
maps to a specific geometric construction---forks, scope sections,
suspended morphisms, fiber restrictions, and covering families---and
effect interactions are handled uniformly by the overlap conditions
of the Grothendieck topology.

The evaluation on \expTotalPrograms{} real Python programs demonstrates
that this encoding is both sound and complete on the benchmark:
\expAccuracy{} accuracy with zero obstructions, a mean verification
time of \expTimeMean{}, and correct effect detection across all five
families.  The web and state machine domains, which exhibit the richest
effect profiles, verify as reliably as the simpler sorting domain.

\paragraph{Future work.}
Three directions are immediate: (1)~extending the effect encoding to
cover metaclass effects and descriptor protocols; (2)~scaling to
programs with hundreds of coordinates via hierarchical descent;
(3)~integrating with Python's gradual typing ecosystem to lift
\texttt{mypy} annotations into propositions.
