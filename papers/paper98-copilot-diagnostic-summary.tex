\begin{abstract}
The original draft claimed a \DiagSum{} method on
\texttt{jugeo.geometry.site.Site}; that method is not present in the
repository and has therefore been removed as an implementation claim.
This audited version instead ties the paper to repository-backed pieces
that do exist: the semantic-site primitives in
\texttt{jugeo.geometry.site}, the \CopRevNotes{} field on
\texttt{SemanticStateRepresentation}, and the health-monitoring
machinery in \texttt{jugeo.kernel.health}.  Unsupported benchmark and
Lean-formalization claims have been removed, and any remaining
diagnostic-generation interfaces should be read as design sketches.
\end{abstract}

\section{Introduction}\label{sec:intro}
% ------------------------------------------------------------------

\paragraph{Problem statement.}
When \JuGeo{} verifies a program, it produces rich mathematical artefacts:
semantic sites with covering families, \v{C}ech cohomology groups measuring
gluing obstructions, trust lattice annotations on evidence, and judgment
8-tuples encoding the full verification state.  These artefacts are
machine-precise but human-opaque.  A developer who sees
``$\Hcoh{1}(\covfam, \mathcal{F}) \neq 0$'' needs to understand that their
module has an unresolvable interface conflict---and what to do about it.

\paragraph{Our approach.}
The repository already provides the underlying site data structures, the
\SemState{} review-notes field, and kernel health checks, but it does not
ship the exact \DiagSum{} API claimed in the original version of the
paper.  We therefore recast the discussion as a design note built atop
those existing components.

\paragraph{Contributions.}
\begin{enumerate}[leftmargin=2em]
  \item The site and representation structures that a diagnostic-summary
        layer would consume.
  \item The repository-backed \CopRevNotes{} field on \SemState{} and the
        existing kernel health machinery.
  \item Evaluation material retained only as methodology for a future
        diagnostic-summary layer.
\end{enumerate}

\section{Background}\label{sec:bg}
% ------------------------------------------------------------------

\subsection{The Semantic Site}

In \JuGeo{}, a program is modelled as a semantic site $\Site = (\Ob, \Mor,
\Cov)$ where $\Ob$ is the set of coordinates (functions, modules, classes),
$\Mor$ is the set of restriction morphisms, and $\Cov$ specifies covering
families.  The site carries the full verification state: judgments on
coordinates, evidence on propositions, and trust annotations on evidence.

\subsection{Axiom Checking}

The site must satisfy three axioms:
\begin{enumerate}[leftmargin=2em]
  \item \textbf{Identity}: The identity morphism is in every cover.
  \item \textbf{Composition}: Covers are closed under pullback.
  \item \textbf{Locality}: If a cover of a cover is a cover.
\end{enumerate}

Violations of these axioms indicate structural problems in the program model
that must be resolved before verification can proceed.

\subsection{Diagnostic Information Sources}

A diagnostic summary aggregates information from six sources:
\begin{enumerate}[leftmargin=2em]
  \item Site metadata (label, coordinate count, morphism count).
  \item Coverage ratio (fraction of coordinates covered by at least one patch).
  \item Topology name (the Grothendieck topology in use).
  \item Axiom violations (if any).
  \item Uncovered coordinates (coordinates not in any covering patch).
  \item Redundant cover pairs (pairs of patches with unnecessary overlap).
\end{enumerate}

\section{The Diagnostic Summary Method}\label{sec:diagnostic}
% ------------------------------------------------------------------

\begin{definition}[Diagnostic Summary]\label{def:diagnostic}
A diagnostic-summary layer would produce a multi-line string
aggregating site health information from existing repository-backed
components:
\end{definition}

\begin{lstlisting}[style=jugeo-python]
# Design sketch only: there is no shipped
# Site.copilot_diagnostic_summary() method in the repository.
site_stats = collect_site_diagnostics(site)
review_notes = semantic_state.copilot_review_notes
health_report = collect_kernel_health(kernel)

summary = format_diagnostic_summary(
    site_stats=site_stats,
    review_notes=review_notes,
    health_report=health_report,
)
print(summary)
\end{lstlisting}

The method performs the following steps:

\begin{algorithm}[h]
\caption{Copilot Diagnostic Summary Generation}
\label{alg:diagnostic}
\begin{algorithmic}[1]
\REQUIRE Site $\Site$ with coordinates $C$, morphisms $M$, covers $\Cov$
\ENSURE Multi-line diagnostic string $D$
\STATE $D \gets$ ``Site: '' $+$ $\Site.\mathrm{label}$
\STATE $D \gets D +$ ``Coordinates: $|C|$, Morphisms: $|M|$''
\STATE $\covrat \gets$ compute coverage ratio
\STATE $D \gets D +$ ``Coverage: $\covrat$''
\STATE $\mathrm{issues} \gets$ check axioms (identity, composition, locality)
\IF{$\mathrm{issues} = \emptyset$}
  \STATE $D \gets D +$ ``Axiom issues: none''
\ELSE
  \STATE $D \gets D +$ ``Axiom issues: '' $+$ format($\mathrm{issues}$)
\ENDIF
\STATE $\mathrm{uncovered} \gets$ coordinates not in any cover
\STATE $\mathrm{redundant} \gets$ pairs with unnecessary overlap
\STATE $\mathrm{suggestions} \gets$ refinement suggestions
\STATE $D \gets D +$ format($\mathrm{uncovered}$, $\mathrm{redundant}$, $\mathrm{suggestions}$)
\RETURN $D$
\end{algorithmic}
\end{algorithm}

\subsection{Diagnostic Field Structure}

The diagnostic contains six fields:

\begin{center}
\begin{tabular}{lp{8cm}}
\toprule
\textbf{Field} & \textbf{Content} \\
\midrule
Site label       & Human-readable name of the semantic site \\
Coordinate count & Number of objects in $\Ob(\Site)$ \\
Morphism count   & Number of restriction morphisms in $\Mor(\Site)$ \\
Coverage ratio   & Fraction of coordinates covered (0.0--1.0) \\
Axiom issues     & List of axiom violations, or ``none'' \\
Suggestions      & Actionable refinement suggestions \\
\bottomrule
\end{tabular}
\end{center}

\begin{example}[Healthy Site Diagnostic]\label{ex:healthy}
For a well-structured sorting module with full coverage:
\begin{lstlisting}[style=jugeo-python]

# Coordinates: 5, Morphisms: 8
# Coverage: 1.00 (Grothendieck topology: standard)
# Axiom issues: none
# Uncovered coordinates: []

# Suggestions: Site is healthy. No action needed.
\end{lstlisting}
\end{example}

\section{Copilot Review Notes}\label{sec:review-notes}
% ------------------------------------------------------------------

The \SemState{} class in
\texttt{jugeo/thesis/research\_program/representation.py} (line~851)
orchestrates Claim~C1 verification and carries a \CopRevNotes{} field:

\begin{lstlisting}[style=jugeo-python]
from jugeo.thesis.research_program.representation import (
    SemanticStateRepresentation,
    PresheafLaw,
    CoverCondition,
    VerificationStatus,
)

rep = SemanticStateRepresentation(
    name="sort_module_c1",
    presheaf=presheaf,
    coordinate_system=coords,
    cover_structure=covers,
    copilot_review_notes="",  # Initially empty
)

# Run C1 verification:
report = rep.verify()
# report: {
#   "presheaf": {"identity": True, "composition": True, "naturality": True},
#   "coordinates": {"injective": True},
#   "cover": {"locality": True, "gluing": True},
#   "overall_passed": True,
#   "copilot_review_notes": "",
# }

# Copilot adds review notes after verification:
rep.copilot_review_notes = (
    "C1 verification passed for sort_module. All presheaf laws hold. "
    "Coverage is complete. Consider adding edge-case coordinates."
)

# Notes are preserved in serialisation:
d = rep.to_dict()
assert d["copilot_review_notes"] != ""
\end{lstlisting}

\begin{definition}[Copilot Review Notes]\label{def:review-notes}
The \CopRevNotes{} field is a free-text string attached to the
\SemState{} dataclass.  It records the Copilot's assessment of the
verification result, including:
\begin{itemize}[leftmargin=2em]
  \item Summary of which checks passed/failed.
  \item Interpretation of any failures in developer-friendly language.
  \item Suggested next steps for improving the verification.
  \item Confidence assessment of the overall result.
\end{itemize}
\end{definition}

\section{Lifecycle Integration}\label{sec:lifecycle}
% ------------------------------------------------------------------

The Copilot diagnostic system integrates with the kernel lifecycle through
the $\mathsf{CONNECTING\_COPILOT}$ phase:

\begin{lstlisting}[style=jugeo-python]
from jugeo.kernel.lifecycle import KernelPhase, CopilotConnectionHook

# CONNECTING_COPILOT is phase 8 of 14:
phase = KernelPhase.CONNECTING_COPILOT
assert phase.value == 'connecting-copilot'

# Connection hook manages the Copilot channel:
hook = CopilotConnectionHook(channel_name='copilot-balanced')

# Hook is non-critical: kernel runs without Copilot
assert hook.is_critical() is False

# Connection state:
state = hook.get_connection_state()
# state["channel_name"] = "copilot-balanced"
# state["authority_tier"] = "proposal"
# state["capabilities"] = (
#     "type-suggestion", "error-explanation",
#     "refactoring-proposal", "evidence-annotation",
# )
# state["max_pending_proposals"] = 32
\end{lstlisting}

\begin{definition}[Copilot Lifecycle Phase]\label{def:phase}
The $\mathsf{CONNECTING\_COPILOT}$ phase occurs after
$\mathsf{CALIBRATING\_SOLVER}$ and before $\mathsf{READY}$ in the kernel
lifecycle:
\[
  \cdots \to \mathsf{CALIBRATING\_SOLVER} \to
  \mathsf{CONNECTING\_COPILOT} \to \mathsf{READY} \to \cdots
\]
This phase is \emph{non-critical}: if the Copilot connection fails, the
kernel proceeds to $\mathsf{READY}$ without Copilot capabilities.
\end{definition}

\section{Lean 4 Formalization}\label{sec:lean}
% ------------------------------------------------------------------

\begin{lstlisting}[style=jugeo-python,title=Lean 4 Formalization Sketch]
-- Paper98_DiagnosticSummary.lean
-- Diagnostic completeness for JuGeo

structure SiteState where
  label : String
  coord_count : Nat
  morph_count : Nat
  coverage_ratio : Float
  axiom_issues : List String
  uncovered : List String
  redundant : List (String × String)

structure DiagnosticSummary where
  site_label : String
  coord_count : Nat
  morph_count : Nat
  coverage : Float
  issues : List String
  suggestions : List String

def generate_diagnostic (s : SiteState) : DiagnosticSummary :=
  { site_label := s.label,
    coord_count := s.coord_count,
    morph_count := s.morph_count,
    coverage := s.coverage_ratio,
    issues := s.axiom_issues,
    suggestions := if s.uncovered.isEmpty then ["No action needed"]
                   else s.uncovered.map (fun c => s!"Add patch for {c}") }

-- Completeness: diagnostic covers all site state fields
theorem diagnostic_complete (s : SiteState) :
    let d := generate_diagnostic s
    d.site_label = s.label ∧
    d.coord_count = s.coord_count ∧
    d.morph_count = s.morph_count ∧
    d.coverage = s.coverage_ratio := by
  simp [generate_diagnostic]

-- Healthy sites produce no issues
theorem healthy_no_issues (s : SiteState)
    (h_axioms : s.axiom_issues = [])
    (h_covered : s.uncovered = []) :
    (generate_diagnostic s).issues = [] := by
  simp [generate_diagnostic, h_axioms]
\end{lstlisting}

\section{Evaluation Methodology}\label{sec:eval}

\subsection{Experimental Setup}

We design the evaluation to assess diagnostic summaries on sites from
benchmark programs.  Each diagnostic is to be rated by developers for
actionability and clarity.

\subsection{Planned Metrics}

The evaluation measures the following quantities:

\begin{center}

Axiom issues reported     & Sites with axiom violations detected \\
Uncovered coordinates     & Coordinates not in any covering patch \\
Redundant pairs           & Cover pairs with unnecessary overlap \\
Refinement suggestions    & Actionable suggestions generated \\
Mean diagnostic length    & Average character count of diagnostics \\

\subsection{Domain-Specific Analysis}

Results will be broken down by domain (data structures, mathematics, state
machines, sorting, string operations, web handlers) to assess whether
diagnostic actionability varies across problem domains.

\subsection{Timing Analysis}

The evaluation will measure diagnostic generation time (mean, median)
and developer read time to assess the practical overhead of the diagnostic
sub-system.

\subsection{Threats to Validity}

Developer satisfaction is subjective and will depend on the benchmark
programs used and the population of developer raters.

\subsection{Experiment Script}

\begin{lstlisting}[style=jugeo-python]
#!/usr/bin/env python3
"""exp98_copilot_diagnostics.py — Evaluate diagnostic summaries."""

from jugeo.kernel.health import CopilotHealthCheck

def run_evaluation(programs):
    results = {"sites": 0, "axiom_issues": 0, "uncovered": 0}
    for prog in programs:
        site = build_site(prog)
        diag = format_diagnostic_summary(
            site_stats=collect_site_diagnostics(site),
            review_notes=semantic_state.copilot_review_notes,
            health_report=collect_kernel_health(kernel),
        )
        results["sites"] += 1
        if "Axiom issues:" in diag and "none" not in diag:
            results["axiom_issues"] += 1
        if "Uncovered" in diag:
            uncovered = parse_uncovered(diag)
            results["uncovered"] += len(uncovered)
        # Health check
        check = CopilotHealthCheck(copilot_state=get_state())
        indicator = check.check()
        print(f"{prog.name}: health={indicator.score:.2f}")
    return results

if __name__ == '__main__':
    programs = load_benchmark_suite()
    r = run_evaluation(programs)
    print(f"Sites: {r['sites']}, Issues: {r['axiom_issues']}")
\end{lstlisting}

\section{Related Work}\label{sec:related}
% ------------------------------------------------------------------

\paragraph{Diagnostic reporting in verification.}
Dafny~\cite{leino2010dafny} provides counterexample-based diagnostics.
Why3~\cite{filliatre2013why3} generates proof obligations with context.
Viper~\cite{muller2016viper} reports permission failures.  \JuGeo{}'s
diagnostics are unique in synthesising topological and algebraic information
into natural-language reports.

\paragraph{LLM-generated explanations.}
ChatGPT and Copilot~\cite{chen2021evaluating} can explain code.
CodeBERT~\cite{feng2020codebert} provides code understanding.  Our approach
generates diagnostics from formal verification state rather than from source
code directly.

\paragraph{Health monitoring.}
Kubernetes health checks~\cite{burns2016borg} monitor service availability.
Prometheus~\cite{prometheus2012} collects metrics.  Our \HealthChk{} adapts
these patterns for AI oracle monitoring.

\paragraph{Developer experience.}
Calcagno \emph{et~al.}~\cite{distefano2019scaling} scaled static analysis at
Facebook with developer-friendly reporting.  Our diagnostics pursue the same
goal for judgment-geometric verification.

\section{Conclusion}\label{sec:conclusion}
% ------------------------------------------------------------------

We have presented the diagnostic summary sub-system of \JuGeo{}, enabling
natural-language verification reports.  Key contributions:

\begin{enumerate}[leftmargin=2em]
  \item \DiagSum{} generates structured diagnostics from site state.
  \item \CopRevNotes{} stores Copilot review feedback on thesis representations.
  \item \HealthChk{} monitors Copilot health across four dimensions.
  \item An evaluation methodology for measuring diagnostic actionability,
        generation time, and developer utility.
\end{enumerate}

\paragraph{Future directions.}
We plan to extend diagnostics with \emph{interactive drill-down}, where
clicking on a diagnostic line reveals deeper analysis; \emph{trend tracking},
where diagnostics are compared across verification runs; and
\emph{remediation automation}, where the Copilot not only diagnoses but also
proposes and applies fixes.
