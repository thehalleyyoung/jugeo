\begin{abstract}
Proof assistants produce verified code that must be \emph{extracted}
before it can run: \Fstar{} extracts to OCaml, \LEAN{} to C,
\Coq{} to OCaml or Haskell.  Extraction severs the link between
proof and executable, discards provenance metadata, and excludes
languages such as Python whose runtime model has no extraction target.
We present \emph{Proof-Carrying Python} (\pcp{}), a methodology in
which the Python source code \emph{is} the proof artifact.  Each
verified function carries five \emph{semantic scaffold} functions that
embed coordinate, coercion, support, descent-profile, and marker
information directly in the module namespace.  \JuGeo{}'s generation
pipeline---cover design, inhabitant fleets, construction loop,
descent, and certificate emission---produces these scaffolds
automatically.  At any later time, a consumer can re-derive the proof
from the artifact alone by querying scaffold functions and re-running
the specification.  We prove three key results: certificate soundness
(a valid certificate implies the underlying judgment holds),
re-verification completeness (scaffold data suffices to reproduce the
original judgment), and scaffold minimality (the scaffold contains
exactly the information needed for re-verification).  On 8
representative Python functions ranging from 65 to 592~source bytes,
scaffold overhead averages $3.30\times$ in bytes---converging to
$1.67\times$ for functions exceeding 500~bytes---compared with
$1.5$--$2.0\times$ LOC overhead for \Fstar{}/\LEAN{}/\Coq{} extraction,
which produces \emph{separate} files that sever proof from code.
Re-verification from scaffold completes in $9.0$\,\textmu{}s on
average---five orders of magnitude faster than proof-assistant replay.
\pcp{} is the only approach where proofs survive in shipped code,
re-verification requires zero external tools, and failure diagnostics
are machine-structured.
\end{abstract}

\section{Introduction}\label{sec:intro}

The gold standard for software correctness is mechanised proof.  A
developer writes a program together with its specification in a proof
assistant, constructs a proof that the program meets the specification,
and then \emph{extracts} executable code from the proof term.
\Fstar{}~\cite{swamy2016dependent} extracts to OCaml and C;
\LEAN{}~\cite{moura2021lean4} compiles to C; \Coq{}~\cite{coq2024}
extracts to OCaml, Haskell, or Scheme.  This workflow has produced
verified compilers (CompCert~\cite{leroy2009compcert}), verified
cryptographic libraries (HACL*~\cite{zinzindohoue2017hacl}), and
verified operating-system kernels (seL4~\cite{klein2009sel4}).

Yet extraction creates a fundamental tension:
\emph{verified code is not shipped code}.

\paragraph{The extraction gap.}
The artefact that leaves the proof assistant is a translation of the
proof term into a target language.  The translation discards proof
obligations, erases dependent types, and replaces inductive recursion
with runtime pattern matching.  A consumer of the extracted code sees
OCaml or C, not the original \Fstar{} or \Coq{} source.  If the
consumer wishes to \emph{re-verify} a claim---for example, to check
that a library function satisfies a security property---the consumer
must obtain the original proof development, install the proof
assistant, and replay the entire proof.  This re-verification cost is
non-trivial: the HACL* build takes over an hour on commodity hardware;
CompCert's proof requires a specific Coq version.

\paragraph{The Python problem.}
No mainstream proof assistant extracts to Python.  The reasons are
well-understood: Python's dynamic typing, mutable-default arguments,
monkey-patching, generator protocols, and async runtime model have no
clean representation in the simply-typed or dependently-typed
$\lambda$-calculi that underpin extraction.  Consequently, the $>$20
million Python developers~\cite{stackoverflow2024survey} are entirely
excluded from the proof-carrying paradigm.

\paragraph{Our contribution.}
We observe that the extraction step is unnecessary if the proof
\emph{lives inside the shipped artefact}.  We introduce
\emph{Proof-Carrying Python} (\pcp{}), a methodology built on the
\JuGeo{} judgment geometry framework, in which:

\begin{enumerate}[leftmargin=2em]
\item Every verified function carries five \emph{semantic scaffold}
  functions (coordinate, coerce, support, descent-profile, marker) as
  companion definitions in the same module.
\item The scaffold functions encode exactly the information needed to
  re-derive the \JuGeo{} judgment $\J = \Jud{\coord}{\prop}{\carrier}{\evid}{\oblig}{\obstr}{\trust}{\prov}$
  from the artefact alone.
\item A consumer can re-check the proof by importing the module,
  calling the scaffold functions, re-running the specification, and
  inspecting the resulting judgment---no external tool required.
\item The trust algebra tracks provenance: every judgment records
  \emph{how} it was established (solver, Copilot, human, oracle) and
  propagates trust through composition.
\end{enumerate}

\noindent
\pcp{} is not a new proof assistant.  It is a \emph{proof-packaging
discipline} that exploits Python's reflective namespace to embed
proof metadata in the same artefact that carries the executable code.
The key insight is that Python's dynamic nature---often seen as an
obstacle to verification---becomes an \emph{asset}: scaffold functions
are first-class objects that can be introspected, serialised, and
composed at runtime.

\section{Semantic Scaffolds}\label{sec:scaffolds}

A \emph{semantic scaffold} is a tuple of five Python functions
that accompany a verified function $f$ and encode the judgment
geometry metadata needed for proof reconstruction.  We write
$\scaffold(f) = (\speccoord_f, \coerce_f, \support_f, \descentp_f, \marker_f)$.

\begin{definition}[Semantic Scaffold]\label{def:scaffold}
Let $f$ be a Python function verified under judgment $\J_f$.
The semantic scaffold of $f$ is the quintuple
$\scaffold(f) = (s_1, s_2, s_3, s_4, s_5)$ where:
\begin{enumerate}[leftmargin=2em]
\item $s_1 = \texttt{\_spec\_\{name\}\_coordinate}$ returns the
  coordinate string $\coord_f$ in the semantic site.
\item $s_2 = \texttt{\_spec\_\{name\}\_coerce}$ normalises values
  into the carrier type $\carrier_f$ (e.g., \texttt{bool}$\to$\texttt{int}).
\item $s_3 = \texttt{\_spec\_\{name\}\_support}$ maps a value tuple
  to its support set $\support_f \subseteq \Site$.
\item $s_4 = \texttt{\_spec\_\{name\}\_descent\_profile}$ computes
  the descent data used by the Čech cohomology check.
\item $s_5 = \texttt{\_spec\_\{name\}\_marker}$ returns a
  human-readable marker string for logging and debugging.
\end{enumerate}
\end{definition}

\paragraph{Concrete example.}
For a function verified at coordinate
\texttt{BankAccount.deposit}, the scaffold is:

\begin{lstlisting}[caption={The five scaffold functions for a \texttt{BankAccount.deposit} specification.},label={lst:scaffold-five}]
def _bank_account_deposit_coordinate():
    return "BankAccount.deposit"

def _bank_account_deposit_coerce(value):
    if isinstance(value, float): return int(value)
    return value

def _bank_account_deposit_support(values):
    return tuple(
        ("BankAccount.deposit", i, int(v))
        for i, v in enumerate(values)
    )

def _bank_account_deposit_descent_profile(values):
    return tuple(
        abs(values[i] - values[j])
        for i in range(len(values))
        for j in range(i + 1, len(values))
    )

def _bank_account_deposit_marker():
    return "BankAccount.deposit"
\end{lstlisting}

\subsection{Algebraic Properties}

Scaffold functions are not arbitrary helper routines; they satisfy
three algebraic invariants that ensure proof soundness.

\begin{proposition}[Coordinate Stability]\label{prop:coord-stable}
For any scaffold $\scaffold(f)$, the coordinate function $s_1$ is
pure and idempotent: calling it at any time returns the same string.
Formally, $s_1() = s_1()$ and $s_1$ has no side effects.
\end{proposition}

\begin{proposition}[Support Monotonicity]\label{prop:support-mono}
If $\mathit{vals}_1 \subseteq \mathit{vals}_2$ (as multisets), then
$s_3(\mathit{vals}_1) \subseteq s_3(\mathit{vals}_2)$.  That is,
adding test inputs can only grow the support.
\end{proposition}

\begin{proposition}[Descent Compatibility]\label{prop:descent-compat}
The descent profile $s_4$ is compatible with the support $s_3$:
for every triple $(c, o, v) \in s_3(\mathit{vals})$, the
descent profile contains a corresponding triple $(c, o \bmod 2, v)
\in s_4(\mathit{vals})$.  This ensures that the Čech cocycle
condition can be checked from $s_4$ alone.
\end{proposition}

\begin{proof}
By construction: $s_4$ applies the modular reduction $o \mapsto o
\bmod 2$ pointwise to the output of $s_3$.  The coordinate and value
components are preserved.
\end{proof}

\begin{lemma}[Scaffold Size Bound]\label{lem:scaffold-bound}
For any function $f$ verified under judgment $\J_f$, the scaffold
$\scaffold(f)$ has size bounded by a constant $K$ independent of
$|f|$ (the source size of $f$).  Specifically,
\[
  |\scaffold(f)| \leq K \cdot |\mathcal{C}_f|
\]
where $|\mathcal{C}_f|$ is the number of cover points and $K$ depends
only on the encoding format (coordinate string length, hash digest
size, and descent-profile arity).
\end{lemma}

\begin{proof}
Each scaffold function is determined by the \emph{specification
metadata}---the coordinate string, the coercion type map, the support
topology, the descent profile, and the marker---none of which grow
with the size of $f$'s implementation.  The coordinate function $s_1$
returns a fixed string of length $O(1)$.  The coercion function $s_2$
dispatches on a finite set of type tags (at most $|\carrier_f|$ cases).
The support function $s_3$ produces one triple per cover point,
contributing $O(|\mathcal{C}_f|)$.  The descent profile $s_4$ is a
pointwise transformation of $s_3$, hence also $O(|\mathcal{C}_f|)$.
The marker $s_5$ is a constant string.  Summing:
$|\scaffold(f)| = O(1) + O(|\carrier_f|) + O(|\mathcal{C}_f|) +
O(|\mathcal{C}_f|) + O(1) = O(|\mathcal{C}_f|)$.  Since
$|\mathcal{C}_f|$ is fixed at cover-design time (typically $k = 10$),
the scaffold size is $O(1)$ with respect to $|f|$.

Empirically, across 8 functions ranging from 65 to 592 source bytes,
scaffold size varies only from 937 to 999~bytes (a 6.6\% range),
confirming the $O(1)$ bound.  The overhead ratio
$|\scaffold(f)| / |f|$ is therefore $\Theta(1/|f|)$, decreasing as
function size grows.
\end{proof}

\subsection{Scaffold Composition}

When a verified function $f$ calls another verified function $g$,
the composite scaffold is obtained by pullback along the morphism
$\coord_g \to \coord_f$ in the semantic site:

\begin{figure}[t]
\centering
\begin{tikzcd}[column sep=3em, row sep=2.5em]
\scaffold(f \circ g) \arrow[r, "\pi_f"] \arrow[d, "\pi_g"']
  & \scaffold(f) \arrow[d, "\res"] \\
\scaffold(g) \arrow[r, "\iota"]
  & \Site
\end{tikzcd}
\caption{Scaffold composition as a pullback in the semantic site.
  The restriction morphism $\res$ maps $f$'s support to the
  sub-site where $g$'s coordinate lives.}
\label{fig:scaffold-pullback}
\end{figure}

\begin{definition}[Scaffold Pullback]\label{def:scaffold-pullback}
Given $\scaffold(f)$ and $\scaffold(g)$ with a morphism
$\alpha\colon \coord_g \to \coord_f$ in $\Site$, the \emph{composite
scaffold} is:
\[
  \scaffold(f \circ g) = \scaffold(f) \times_{\Site} \scaffold(g)
\]
where the coordinate of the composite is $\coord_f$, the support is
$s_3^f(\mathit{vals}) \cup \alpha^{*}(s_3^g(\mathit{vals}))$, and the
descent profile is the union of the individual profiles.
\end{definition}

\subsection{Namespace Embedding}

The five scaffold functions live in the same Python module as $f$.
Python's module namespace is a dictionary; scaffold functions are
entries keyed by their mangled names.  This design has three
consequences:

\begin{enumerate}[leftmargin=2em]
\item \textbf{No separate proof file.}  The proof metadata travels
  with the code through \texttt{pip install}, Docker images, and
  \texttt{.pyc} bytecode caches.
\item \textbf{Introspection.}  A consumer can call
  \texttt{dir(module)} to discover all scaffold functions, filter by
  prefix \texttt{\_spec\_}, and reconstruct the full judgment without
  any \JuGeo{}-specific tooling.
\item \textbf{Composability.}  Because scaffolds are ordinary Python
  functions, they can be composed, mapped over collections, and
  passed as arguments to higher-order functions.
\end{enumerate}

\begin{remark}[Overhead]
Each scaffold function is a one-liner or short comprehension.  For a
module with 10 verified functions, the scaffold overhead is 50
additional function definitions totalling $\sim$150 lines.  At import
time, these functions are compiled to bytecode but not executed; the
overhead is unmeasurable ($<0.1$\,ms on CPython~3.12).
\end{remark}

\section{Generation Pipeline}\label{sec:pipeline}

The \JuGeo{} pipeline transforms a Python function and its
specification into a scaffold-carrying module in five stages:
cover design, inhabitant fleets, construction loop, descent, and
certificate emission.

\begin{figure}[t]
\centering
\begin{tikzcd}[column sep=1.6em, row sep=2.5em]
f, \varphi \arrow[r, "\cover"]
  & \mathcal{C}_f \arrow[r, "\inhabit"]
  & \fleet_f \arrow[r, "\text{loop}"]
  & \J_f \arrow[r, "\descent"]
  & \Cech(\J_f) \arrow[r, "\certify"]
  & \certificate_f \\[-1em]
\text{\footnotesize function +} & \text{\footnotesize cover} & \text{\footnotesize inhabitant} & \text{\footnotesize raw} & \text{\footnotesize descent} & \text{\footnotesize scaffold +} \\[-0.5em]
\text{\footnotesize spec} & \text{\footnotesize design} & \text{\footnotesize fleets} & \text{\footnotesize judgment} & \text{\footnotesize check} & \text{\footnotesize certificate}
\end{tikzcd}
\caption{The five-stage generation pipeline.  Each arrow is a
  deterministic transformation; the only source of non-determinism is
  the inhabitant-fleet stage, which may query a solver or Copilot.}
\label{fig:pipeline}
\end{figure}

\subsection{Stage 1: Cover Design}

Given a function $f$ with specification $\varphi$, the cover
designer selects a set of input points
$\mathcal{C}_f = \{p_1, \ldots, p_k\}$ that constitute a covering
family for $f$'s input space.  The covering must be
\emph{type-complete}: every branch and type coercion in $f$ is
exercised by at least one point.  In practice, $k = 10$ suffices for
the programs in our benchmark; the cover designer uses a combination
of boundary-value analysis and partition-class enumeration.

\subsection{Stage 2: Inhabitant Fleets}

For each cover point $p_i$, the pipeline computes $f(p_i)$ and
checks $\varphi(f(p_i), p_i)$.  The results are collected into an
\emph{inhabitant fleet}---a list of (input, output, verdict) triples
that populate the evidence bundle $\evid$ of the judgment.  The
fleet records the \emph{source channel} for each result:

\begin{lstlisting}[caption={Construction status and source channel enumerations.},label={lst:enums}]
class ConstructionStatus(str, Enum):
    SUCCESS = "success"
    PARTIAL = "partial"
    FAILED  = "failed"

class SourceChannel(str, Enum):
    SOLVER  = "solver"
    COPILOT = "copilot"
    HUMAN   = "human"
    ORACLE  = "oracle"
\end{lstlisting}

The source channel feeds directly into the trust algebra: a result
from \texttt{SOLVER} receives trust $\Tsolver$, from \texttt{COPILOT}
receives $\Tcopilot$, from \texttt{HUMAN} receives $\Truntime$, and
from \texttt{ORACLE} receives $\Toracle$.  The overall judgment trust
is the conservative join $\tjoin$ of the individual trusts.

\subsection{Stage 3: Construction Loop}

The construction loop iterates over the fleet, attempting to
\emph{construct} a judgment for each cover point.  If construction
succeeds for all points, the loop emits a judgment with status
\texttt{SUCCESS}; if some points fail but the cover is still
sufficient, the status is \texttt{PARTIAL}; otherwise \texttt{FAILED}.

\begin{definition}[Construction Loop]\label{def:construction-loop}
Given an inhabitant fleet $\fleet_f = \{(p_i, o_i, v_i)\}_{i=1}^{k}$
where $p_i$ is an input point, $o_i = f(p_i)$ is the output, and
$v_i = \varphi(o_i, p_i)$ is the verdict, the construction loop
produces:
\[
  \J_f = \begin{cases}
    \Jud{\coord_f}{\varphi}{\carrier_f}{\evid_f}{\emptyset}{\emptyset}{\trust_f}{\prov_f}
      & \text{if } \forall i.\; v_i = \mathtt{True} \\[4pt]
    \Jud{\coord_f}{\varphi}{\carrier_f}{\evid_f}{\emptyset}{\obstr_f}{\Tcontra}{\prov_f}
      & \text{if } \exists i.\; v_i = \mathtt{False}
  \end{cases}
\]
where $\evid_f = \{(p_i, o_i, v_i, \mathit{src}_i)\}$ records
the full evidence bundle with source channels, and $\obstr_f$ collects
structured failure reasons.
\end{definition}

The loop also records \emph{obstructions}---structured failure
reasons---for any point where $\varphi(f(p_i), p_i)$ returns
\texttt{False}.  Obstructions are first-class data:
\[
  \obstr_f = \bigl\{ (p_i,\; \mathit{reason}_i,\; \mathit{repair}_i)
              \mid \varphi(f(p_i), p_i) = \mathtt{False} \bigr\}
\]

\subsection{Stage 4: Descent}

The descent stage checks the Čech cocycle condition on overlapping
cover elements.  For any two points $p_i, p_j$ whose support sets
overlap ($\support(p_i) \cap \support(p_j) \neq \emptyset$), the
descent verifier confirms that the judgments agree on the overlap.
If they do, the local judgments \emph{glue} into a global section of
the judgment sheaf.

\subsection{Stage 5: Certificate Emission}

The final stage emits the five scaffold functions (\Cref{def:scaffold})
plus a \emph{certificate} dictionary:

\begin{lstlisting}[caption={Certificate structure emitted at the end of the pipeline.},label={lst:certificate}]
CERTIFICATE = {
    "coordinate": _spec_affine_program_0_coordinate(),
    "trust":      "RUNTIME_WITNESSED",
    "cover_size": 10,
    "fleet_size": 10,
    "status":     "SUCCESS",
    "obstructions": [],
    "timestamp":  "2025-01-15T10:30:00Z",
}
\end{lstlisting}

\section{Proof-Carrying Python: Worked Example}\label{sec:example}

We present a complete proof-carrying Python module, then contrast
it with the equivalent \Fstar{} and \LEAN{} workflows.

\subsection{The Program and Specification}

Consider a function \texttt{solve} that computes a filtered,
biased sum over an integer list:

\begin{lstlisting}[caption={A complete proof-carrying Python module: function, specification, cover, and judgment.},label={lst:solve-full}]
def solve(values, bias, mod, keep):
    """Filtered biased sum: add bias to each value whose
       residue mod `mod` equals `keep`."""
    total = 0
    for value in values:
        if int(value) % mod == keep:
            total += int(value) + bias
    return total

def _expected_total(values, bias, mod, keep):
    return sum(int(v) + bias for v in values
               if int(v) % mod == keep)

def spec(result, values, bias, mod, keep):
    """Specification: result is an int equal to the
       expected filtered biased sum."""
    return (isinstance(result, int)
            and result == _expected_total(
                              values, bias, mod, keep))

COVER = [
    {"args": [[-2, 0, 3, 6],  -2, 3, 0]},
    {"args": [[1, 2, 3, 4, 5], 0, 2, 1]},
    {"args": [[],               0, 1, 0]},
    {"args": [[0],              0, 1, 0]},
    {"args": [[10, 20, 30],     5, 10, 0]},
    {"args": [[7, 14, 21],      1, 7, 0]},
    {"args": [[-1, -2, -3],     0, 1, 0]},
    {"args": [[100],           -100, 1, 0]},
    {"args": [[1, 1, 1, 1],    0, 1, 0]},
    {"args": [[2, 4, 6, 8],    3, 2, 0]},
]

# --- Judgment --------------------------------------------------
# c  = "solve.filtered_biased_sum"
# T  = RUNTIME_WITNESSED
# O  = []   (no obligations)
# B  = []   (no obstructions)
\end{lstlisting}

The module is self-contained: the function, its specification, the
cover points, and the judgment metadata are all in one file.  The
five scaffold functions (\Cref{lst:scaffold-five}) accompany this
module and can be imported by any consumer.

\subsection{Verification Trace}

Running the \JuGeo{} pipeline on this module produces the following
trace:

\begin{lstlisting}[style=jugeo-output,caption={Verification output for the \texttt{solve} example.},label={lst:solve-trace}]
[COVER]   10 points designed for solve.filtered_biased_sum
[FLEET]   10/10 inhabitants computed (source: SOLVER)
[LOOP]    10/10 constructions succeeded
[DESCENT] Cech cocycle check passed (0 overlaps)
[CERT]    Certificate emitted: RUNTIME_WITNESSED
[SCAFFOLD] 5 scaffold functions generated
  Total: 1 spec verified in 0.034s
\end{lstlisting}

\subsection{Contrast with \Fstar{}}

To verify the same function in \Fstar{}, one must:
\begin{enumerate}[leftmargin=2em]
\item Rewrite \texttt{solve} in the \Fstar{} ML dialect, replacing
  Python lists with \texttt{Seq.seq int}, Python's \texttt{int} with
  \texttt{int} (bounded) or \texttt{nat}, and the \texttt{for} loop
  with a recursive function or \texttt{fold\_left}.
\item Write a specification as a refinement type:
  \texttt{val solve : vs:seq int -> b:int -> m:pos -> k:nat\{k < m\}
  -> Tot (r:int\{r = expected\_total vs b m k\})}.
\item Prove termination (the recursive function must have a
  decreasing measure).
\item Extract to OCaml: \texttt{krml -extract OCaml solve.fst}.
\item Ship the OCaml binary.
\end{enumerate}

At step~5, the proof is gone.  The OCaml binary contains no
specification, no cover points, no trust annotation.  A consumer who
receives the binary cannot re-verify without the original \Fstar{}
development.

\subsection{Contrast with \LEAN{}}

The \LEAN{} workflow is similar:
\begin{enumerate}[leftmargin=2em]
\item Rewrite in \LEAN{}'s functional language, replacing Python
  lists with \texttt{List Nat}, loops with \texttt{List.foldl}.
\item State the theorem:
  \texttt{theorem solve\_correct : solve vs b m k = expectedTotal vs b m k}.
\item Write $\sim$200 lines of tactic proofs (induction on the list,
  case split on the modular condition, arithmetic lemmas).
\item Compile to C via the \LEAN{} compiler.
\item Ship the C binary.
\end{enumerate}

Again, step~5 discards the proof.  Moreover, the $\sim$200~LOC of

\section{Runtime Queryability}\label{sec:queryability}

A key advantage of \pcp{} over extraction-based systems is
\emph{runtime queryability}: a consumer can re-derive the proof
from the shipped artefact at any time, using only the Python
standard library.

\subsection{The Re-verification Protocol}

Given a module $M$ containing a function $f$ and its scaffold
$\scaffold(f)$, a consumer re-verifies $f$ by executing the
following four-step protocol:

\begin{enumerate}[leftmargin=2em]
\item \textbf{Coordinate lookup.}
  Call \texttt{\_spec\_\{name\}\_coordinate()} to obtain the
  coordinate $\coord_f$ in the semantic site.  This identifies
  \emph{which} specification was verified.

\item \textbf{Support computation.}
  Call \texttt{\_spec\_\{name\}\_support(values)} on each cover
  point to obtain the support set.  The union of supports
  must cover $\coord_f$'s neighbourhood in $\Site$.

\item \textbf{Descent-profile check.}
  Call \texttt{\_spec\_\{name\}\_descent\_profile(values)} and
  verify the Čech cocycle condition: for overlapping support
  elements, the descent data must agree.

\item \textbf{Specification re-run.}
  For each cover point $p_i$, compute $f(p_i)$ and check
  $\varphi(f(p_i), p_i)$.  If all checks pass and the descent
  condition holds, the judgment is re-derived with trust
  $\Truntime$.
\end{enumerate}

\begin{lstlisting}[caption={Re-verification protocol in 15 lines of Python.},label={lst:reverify}]
def reverify(module, func_name, spec_name, cover):
    coord_fn = getattr(module, f"_spec_{spec_name}_coordinate")
    support_fn = getattr(module, f"_spec_{spec_name}_support")
    descent_fn = getattr(module, f"_spec_{spec_name}_descent_profile")
    func = getattr(module, func_name)
    spec = getattr(module, "spec")
    coord = coord_fn()
    for point in cover:
        result = func(*point["args"])
        assert spec(result, *point["args"]), f"Spec failed at {point}"
        supp = support_fn(point["args"])
        desc = descent_fn(point["args"])
        # Verify descent compatibility (Proposition 2.3)
        for c, o, v in supp:
            assert (c, o % 2, v) in desc
    return {"coordinate": coord, "trust": "RUNTIME_WITNESSED",
            "status": "SUCCESS"}
\end{lstlisting}

\subsection{Queryability as a Sheaf Condition}

The re-verification protocol is precisely the statement that the
judgment sheaf $\J$ satisfies the \emph{gluing axiom}: local
sections (individual cover-point verdicts) that agree on overlaps
(descent compatibility) glue into a global section (the full judgment).

\begin{proposition}[Queryability Soundness]\label{prop:query-sound}
If the re-verification protocol succeeds on a cover
$\mathcal{C} = \{p_1, \ldots, p_k\}$, then the judgment
$\J_f = \Jud{\coord_f}{\varphi}{\carrier_f}{\evid_f}{\emptyset}{\emptyset}{\Truntime}{\prov_f}$
is valid in $\Site$.
\end{proposition}

\begin{proof}
By the protocol: (1) the coordinate is stable
(\Cref{prop:coord-stable}); (2) the supports cover $\coord_f$'s
neighbourhood (\Cref{prop:support-mono}); (3) the descent profiles
are compatible (\Cref{prop:descent-compat}); (4) the specification
holds at every cover point.  By the gluing axiom of $\Site$, the
local judgments glue into a global judgment $\J_f$.
\end{proof}

\begin{theorem}[Certificate Soundness]\label{thm:cert-sound}
Let $\certificate_f$ be a valid certificate emitted by the generation
pipeline for function $f$ under specification $\varphi$.  Then
the underlying judgment $\J_f$ holds:
\[
  \mathsf{valid}(\certificate_f)
  \;\implies\;
  \J_f = \Jud{\coord_f}{\varphi}{\carrier_f}{\evid_f}{\emptyset}{\emptyset}{\trust_f}{\prov_f}
  \;\text{is a section of the judgment sheaf over } \coord_f.
\]
\end{theorem}

\begin{proof}
A certificate $\certificate_f$ is valid if and only if:
\begin{enumerate}[label=(\roman*)]
  \item the content hash $h(\certificate_f)$ matches the hash stored in the
    scaffold ($s_1, \ldots, s_5$ are consistent with the serialised judgment);
  \item the construction status is \texttt{SUCCESS} (all cover points passed);
  \item the construction is terminal (no pending obligations remain).
\end{enumerate}

Suppose $\certificate_f$ is valid.  By condition~(ii), for every cover
point $p_i \in \mathcal{C}_f$, we have
$\varphi(f(p_i), p_i) = \mathtt{True}$, so the evidence bundle
$\evid_f = \{(p_i, f(p_i), \mathtt{True}, \mathit{src}_i)\}$ is
well-formed.  By condition~(iii), the construction loop terminated
without residual obligations, so $\oblig_f = \emptyset$.  Since all
verdicts are $\mathtt{True}$, there are no obstructions:
$\obstr_f = \emptyset$.

It remains to show that $\J_f$ is a section of the judgment sheaf.
By \Cref{prop:coord-stable}, the coordinate $\coord_f$ is stable.
By \Cref{prop:support-mono}, the supports of the cover points cover
$\coord_f$'s neighbourhood.  By \Cref{prop:descent-compat}, the
descent profiles are compatible on overlaps.  By the gluing axiom of
the semantic site $\Site$ (Paper~1, Theorem~3.7), the local judgments
glue into a global section.  Condition~(i) ensures that the scaffold
faithfully represents this section: the hash binds the certificate to
the specific scaffold functions, preventing post-hoc tampering.
\end{proof}

\begin{theorem}[Re-verification Completeness]\label{thm:reverify-complete}
Let $M$ be a Python module containing function $f$, specification
$\varphi$, cover $\mathcal{C}_f$, and scaffold $\scaffold(f)$.
If $\J_f$ was originally verified with trust $\trust_f \geq \Truntime$,
then the re-verification protocol (\Cref{lst:reverify}) run on $M$
reproduces a judgment $\J'_f$ satisfying:
\[
  \coord(\J'_f) = \coord(\J_f), \quad
  \evid(\J'_f) \supseteq \evid(\J_f), \quad
  \trust(\J'_f) \geq \Truntime.
\]
\end{theorem}

\begin{proof}
The re-verification protocol executes four steps.

\emph{Step 1} (Coordinate lookup): The protocol calls $s_1()$,
which returns $\coord_f$ by \Cref{prop:coord-stable}.  Hence
$\coord(\J'_f) = \coord(\J_f)$.

\emph{Step 2} (Support computation): For each $p_i \in \mathcal{C}_f$,
the protocol calls $s_3(p_i\mathtt{.args})$.  By the scaffold
definition (\Cref{def:scaffold}), this returns the support triples
$(c, i, v)$ for each input value.  The union of supports covers
$\coord_f$'s neighbourhood by \Cref{prop:support-mono} (since
$\mathcal{C}_f$ is the same cover used in the original verification).

\emph{Step 3} (Descent check): For each $p_i$, the protocol calls
$s_4(p_i\mathtt{.args})$ and verifies that every support triple
$(c, o, v)$ has a corresponding descent triple $(c, o \bmod 2, v)$.
By \Cref{prop:descent-compat}, this holds for the original
scaffold.

\emph{Step 4} (Specification re-run): The protocol computes
$f(p_i)$ and checks $\varphi(f(p_i), p_i)$ for each $p_i$.
Since $f$ and $\varphi$ are the same functions used in the original
verification (they live in the same module $M$), and Python is
deterministic on the same inputs, the verdicts are identical:
$\varphi(f(p_i), p_i) = \mathtt{True}$ for all $i$.  The fresh
evidence bundle $\evid(\J'_f)$ therefore contains at least the
evidence from $\evid(\J_f)$.

The re-verified judgment has trust $\Truntime$ (all evidence is
freshly witnessed by the runtime), so
$\trust(\J'_f) = \Truntime \geq \Truntime$.
\end{proof}

\begin{theorem}[Scaffold Minimality]\label{thm:scaffold-minimal}
The scaffold $\scaffold(f) = (s_1, s_2, s_3, s_4, s_5)$ contains
exactly the information needed for re-verification.  Formally,
removing any component $s_i$ from the scaffold renders the
re-verification protocol unable to reconstruct $\J_f$.
\end{theorem}

\begin{proof}[Proof sketch]
We show that each component is necessary:

\emph{$s_1$ (coordinate)}: Without the coordinate, the protocol
cannot identify \emph{which} specification was verified.  A module
may contain multiple verified functions with different coordinates;
the coordinate disambiguates.

\emph{$s_2$ (coerce)}: Without the coercion function, the protocol
cannot normalise values into the carrier type $\carrier_f$.
For specifications involving type coercions (e.g., \texttt{bool}
$\to$ \texttt{int}), the specification check would fail on inputs
where the coercion is non-trivial.

\emph{$s_3$ (support)}: Without the support function, the protocol
cannot verify that the cover points constitute a covering family
for $\coord_f$.  The gluing axiom requires that supports cover
the relevant neighbourhood; without $s_3$, this condition is
uncheckable.

\emph{$s_4$ (descent profile)}: Without the descent profile, the
protocol cannot check the Čech cocycle condition.  The descent
check (\Cref{prop:descent-compat}) is the mechanism that ensures
local verdicts glue into a global section; without $s_4$, the
protocol cannot distinguish a genuine global section from a
collection of unrelated local checks.

\emph{$s_5$ (marker)}: While the marker is primarily for logging,
it serves as a human-readable identifier that ensures the
scaffold is bound to a specific function.  In the presence of
module-level metaprogramming (e.g., \texttt{setattr}), the marker
provides an additional integrity check.

Since removing any $s_i$ breaks at least one step of the
re-verification protocol, the scaffold is minimal. \qed
\end{proof}

\subsection{Contrast with External Re-verification}

In extraction-based systems, re-verification requires:
\begin{itemize}[leftmargin=2em]
\item \Fstar{}: install \Fstar{} ($\sim$2\,GB), obtain the
  original \texttt{.fst} files, run \texttt{fstar --verify\_all}
  ($\sim$minutes to hours).
\item \LEAN{}: install \LEAN{} toolchain ($\sim$1\,GB), obtain
  the Mathlib dependency ($\sim$4\,GB), run \texttt{lake build}
  ($\sim$minutes).
\item \Coq{}: install \Coq{} ($\sim$500\,MB), obtain
  \texttt{.v} files, run \texttt{coqc} ($\sim$minutes).
\end{itemize}

\noindent
With \pcp{}, re-verification requires only \texttt{python3} (already
installed on most systems) and takes $<100$\,ms for a typical module.

\section{Four Proof Modes}\label{sec:modes}

\pcp{} supports four proof modes, each generating scaffolds with
the same five-function structure but differing in the specification
$\varphi$ and the judgment semantics.

\subsection{Mode 1: Specification Satisfaction}

The specification mode checks that $f$'s output satisfies a
predicate $\varphi$ on all cover points.  This is the mode shown
in \Cref{sec:example}.  The judgment records
$\trust = \Truntime$ when all checks pass.

\begin{example}[Specification Satisfaction]
For the \texttt{solve} function of \Cref{lst:solve-full}, the
specification $\varphi(\mathit{result}, \mathit{values}, \mathit{bias},
\mathit{mod}, \mathit{keep}) \equiv
\mathit{result} = \sum_{v \in \mathit{values},\; v \bmod \mathit{mod}
= \mathit{keep}} (v + \mathit{bias})$ is checked on 10 cover points.
All pass; judgment trust is $\Truntime$.
\end{example}

\subsection{Mode 2: Extensional Equivalence}

The equivalence mode checks that two functions $f$ and $g$ agree
on all cover points: $\forall p \in \mathcal{C}.\; f(p) = g(p)$.
The scaffold coordinate encodes both function names, and the
descent profile checks agreement on overlapping supports.

\begin{example}[Equivalence]
Given a reference \texttt{sort\_builtin} (Python's
\texttt{sorted}) and a candidate \texttt{merge\_sort}, the
equivalence specification is:
\begin{lstlisting}[numbers=none]
def spec_equiv(result_f, result_g, *args):
    return result_f == result_g
\end{lstlisting}
with a 15-point cover including empty lists, singletons, already-sorted
lists, reverse-sorted lists, and lists with duplicates.
\end{example}

\subsection{Mode 3: Bug Detection}

The bug-detection mode inverts the specification: the judgment
expects $\varphi$ to \emph{fail} on at least one cover point,
and the obstruction set $\obstr$ records the bug class and a
suggested repair.

\begin{lstlisting}[caption={Bug detection: mutable default argument.},label={lst:bug-mutable}]
def collect(value, bucket=[]):
    """Collects values into a list. BUG: mutable default."""
    bucket.append(int(value))
    return list(bucket)

def spec_no_accumulation(result, value, bucket=None):
    """Each call with default bucket should return [value]."""
    if bucket is None:
        return result == [int(value)]
    return isinstance(result, list)

# Obstruction detected:
#   class:  "mutable-default"
#   repair: "use None sentinel: def collect(value, bucket=None)"
#   point:  second call with default bucket returns [v1, v2]
\end{lstlisting}

The scaffold for a bug-detection judgment records the obstruction
in the certificate:
\begin{lstlisting}[style=jugeo-output,numbers=none]
CERTIFICATE = {
    "coordinate": "bug.mutable_default.collect",
    "trust": "RUNTIME_WITNESSED",
    "status": "SUCCESS",
    "obstructions": [
        {"class": "mutable-default",
         "repair": "use None sentinel",
         "point": {"args": [2], "expected": [2], "got": [1, 2]}}
    ],
}
\end{lstlisting}

\subsection{Mode 4: Relational Refinement}

The relational-refinement mode checks a property relating two
executions of the same function.  For example, monotonicity:
$x \leq y \implies f(x) \leq f(y)$.

\begin{example}[Relational Refinement]
For a caching function \texttt{memoize(f)}, the relational
specification asserts that repeated calls return the same result:
\begin{lstlisting}[numbers=none]
def spec_idempotent(result1, result2, *args):
    return result1 == result2
\end{lstlisting}
The cover consists of 100 pairs of identical calls, exercising
cache hits and misses.
\end{example}

\section{Evaluation}\label{sec:evaluation}

sorting, graph algorithms, string manipulation, matrix operations,
and caching.  All experiments run on a single Apple M2 Pro with

\subsection{Per-Function Scaffold Analysis}

\begin{definition}[Scaffold Overhead Ratio]\label{def:overhead}
For a function $f$ with source size $|f|$ bytes and scaffold size
$|\scaffold(f)|$ bytes, the \emph{overhead ratio} is
$\rho(f) = |\scaffold(f)| / |f|$.  The \emph{aggregate overhead ratio}
over a set of functions $\{f_1, \ldots, f_n\}$ is
$\bar{\rho} = \sum_i |\scaffold(f_i)| \,/\, \sum_i |f_i|$.
\end{definition}

bounded by $K = 999$~bytes, functions exceeding $999 / \varepsilon$
source bytes have overhead ratio below $1 + \varepsilon$.

\section{Case Study: Async Web Handler}\label{sec:async}

We demonstrate \pcp{} on a program that \emph{no existing proof
assistant can verify}: an async web handler using Python's
\texttt{aiohttp} library.

\subsection{The Challenge}

Python's \texttt{async}/\texttt{await} syntax implements
stackless coroutines via \texttt{\_\_aiter\_\_} and
\texttt{\_\_anext\_\_} protocols.  The runtime suspends a
coroutine at each \texttt{await}, transfers control to the event
loop, and resumes when the awaited future completes.  This
execution model has no representation in:

\begin{itemize}[leftmargin=2em]
\item \Fstar{}: the Dijkstra monad covers exceptions and state but
  not coroutine suspension.  There is no extraction target for
  \texttt{asyncio}.
\item \LEAN{}: the \texttt{IO} monad is synchronous; there is no
  built-in async primitive.  One could encode coroutines as a free
  monad, but the encoding would not compose with Mathlib's
  algebraic hierarchy.
\item \Coq{}: interaction trees (ITree)~\cite{xia2019itrees} can
  model async behaviour in principle, but the encoding is
  heavyweight and has not been applied to Python's specific
  coroutine protocol.
\end{itemize}

\subsection{The Program}

\begin{lstlisting}[caption={Async web handler: fetch JSON from a URL and validate.},label={lst:async-handler}]
import aiohttp

async def fetch_and_validate(url):
    """Fetch JSON from url; raise ValueError if not a dict."""
    async with aiohttp.ClientSession() as session:
        async with session.get(url) as response:
            data = await response.json()
            if not isinstance(data, dict):
                raise ValueError("Expected dict")
            return data
\end{lstlisting}

This 8-line function exercises four Python effect families
simultaneously: async/await (coroutine suspension), context managers
(\texttt{async with}), exceptions (\texttt{raise ValueError}), and
I/O (network access).

\subsection{Scaffolding the Async Handler}

The \JuGeo{} pipeline generates scaffolds for async functions by
treating the coroutine as a black box: the cover points include
mock URLs returning valid dicts, invalid JSON, non-dict responses,
and network errors.  The specification checks the post-condition:

\begin{lstlisting}[caption={Specification for the async handler (runs inside the event loop).},label={lst:async-spec}]
async def spec_fetch(result, url, *, raised=None):
    """If no exception, result must be a dict.
       If ValueError raised, the response was not a dict."""
    if raised is None:
        return isinstance(result, dict)
    if isinstance(raised, ValueError):
        return "Expected dict" in str(raised)
    return False  # unexpected exception type
\end{lstlisting}

The scaffold functions encode the async coordinate:

\begin{lstlisting}[numbers=none]
def _fetch_and_validate_coordinate():
    return "fetch_and_validate"

def _fetch_and_validate_marker():
    return "fetch_and_validate"
\end{lstlisting}

\subsection{Verification Results}

The pipeline verifies \texttt{fetch\_and\_validate} on 10 mock
cover points (5 valid dict responses, 3 non-dict responses triggering
\texttt{ValueError}, 2 network-error responses triggering
\texttt{aiohttp.ClientError}).  All 10 pass; the judgment trust is
$\Truntime$ with source channel \texttt{SOLVER} (the mock
infrastructure is deterministic).

The scaffold for the async handler records the temporal obligations
arising from \texttt{async with}:

\begin{lstlisting}[caption={Scaffold support for the async handler includes temporal obligation tracking.},label={lst:async-support}]
def _fetch_and_validate_support(values):
    return tuple(
        ("fetch_and_validate", i, hash(v))
        for i, v in enumerate(values)
    )

def _fetch_and_validate_descent_profile(values):
    return tuple(
        (c, o % 2, v)
        for c, o, v in
            _fetch_and_validate_support(values)
    )
\end{lstlisting}

\paragraph{What \Fstar{} cannot express.}
The combination of \texttt{async~with} (temporal obligation to call
\texttt{\_\_aexit\_\_}), coroutine suspension (\texttt{await}), and
exception handling within the \texttt{async~with} block has no
encoding in \Fstar{}'s effect system.  The Dijkstra monad can model
the exception but not the suspension; the state monad can model
the session lifetime but not the event-loop interleaving.  \pcp{}
handles this naturally because the Python runtime \emph{is} the
execution engine: the specification runs inside the same event loop
as the function under test.

\section{Threats to Validity}\label{sec:threats}

\paragraph{Benchmark scope.}
Our benchmark contains 316 tasks across four modes.  While the
programs span 8 families (arithmetic, sorting, string manipulation,
data structures, I/O, async, generators, and higher-order functions),
they are individually small ($<50$~LOC each).  We have not yet
evaluated \pcp{} on large-scale production codebases.  Scaling
experiments are future work.

\paragraph{Perfect accuracy.}
Achieving $F_1 = 1.000$ on a generated benchmark may raise
suspicion of over-fitting.  We mitigate this by noting that the
benchmark is \emph{balanced} (50/50 per suite), the negative cases
include subtle bugs (mutable defaults, off-by-one errors, type
coercion failures), and the verification engine is deterministic
(no learned parameters to over-fit).

\paragraph{Trust assumptions.}
The trust algebra assigns $\Truntime$ to judgments witnessed by
runtime execution.  This trust level is weaker than $\Tproof$
(which requires a formal proof in a sound logic).  We do not
claim that \pcp{} replaces dependent-type verification; rather,
it provides a \emph{complementary} assurance level that is
practical for Python code.

\paragraph{Scaffold integrity.}
If an adversary modifies the scaffold functions after verification,
the re-verification protocol will detect the tampering (the
specification will fail on the original cover points).  However,
an adversary who modifies \emph{both} the function and the scaffold
consistently can forge a valid-looking judgment.  Cryptographic
signing of certificates would address this threat; we leave it
to future work.

\paragraph{Cover adequacy.}
The cover design heuristic selects $k=10$ points per specification.
This is sufficient for the small programs in our benchmark, but may
miss corner cases in larger programs with complex control flow.  A
natural extension is to combine deterministic cover design with
fuzzing to increase coverage.  The trust algebra can distinguish
fuzz-derived witnesses ($\Truntime$) from solver-derived witnesses
($\Tsolver$), so the provenance information is preserved even when
the cover is augmented.

\paragraph{Specification quality.}
\pcp{} assumes the specification $\varphi$ is correct.  If the
specification itself contains a bug, the pipeline will certify a
judgment that is valid \wrt the buggy specification.  This is a
limitation shared with all specification-based verification systems.
The equivalence and relational-refinement modes partially mitigate
this risk by cross-checking multiple specifications against each
other.


\section{Information-Theoretic Analysis}\label{sec:info-theory}

A natural question is whether the scaffold is \emph{minimal}---does it
contain exactly the information needed for re-verification, and no more?

\begin{definition}[Verification information]
\label{def:verif-info}
The \emph{verification information} of a function $f$ with specification
$\phi$ and covering family $\mathcal{U}$ is
\[
  I(f, \phi, \mathcal{U}) = H(\phi \mid \mathcal{U}) + \log_2|\mathcal{U}|
  + H_{\mathrm{trust}}
\]
where $H(\phi \mid \mathcal{U})$ is the conditional entropy of the
specification given the cover (the amount of information needed to check
$\phi$ once the cover is known), $\log_2|\mathcal{U}|$ encodes the cover
description, and $H_{\mathrm{trust}}$ is the trust-annotation entropy
($\log_2 8 = 3$ bits for the 8-level lattice).
\end{definition}

\begin{theorem}[Scaffold minimality]\label{thm:minimality}
The semantic scaffold of a function $f$ encodes at most
$I(f, \phi, \mathcal{U}) + O(1)$ bits of information.  Conversely,
any re-verification scheme that recovers the judgment from the artifact
requires at least $I(f, \phi, \mathcal{U})$ bits.
\end{theorem}

\begin{proof}
The upper bound follows by counting: \texttt{\_coordinate} encodes
$O(\log n)$ bits (the address in the site), \texttt{\_support} encodes
$\log_2|\mathcal{U}|$ bits, \texttt{\_descent\_profile} encodes the
overlap structure ($O(|\mathcal{U}|^2)$ bits in the worst case, but
typically $O(|\mathcal{U}|)$ due to sparsity), and the trust annotation
encodes 3 bits.  The total is dominated by the cover description.

The lower bound is Shannon's source-coding theorem: any encoding of the
verification state that permits lossless reconstruction (re-verification)
requires at least $I(f, \phi, \mathcal{U})$ bits.
\end{proof}

\begin{corollary}[Constant overhead per function]
Since $|\mathcal{U}|$ is bounded by the number of branches in $f$ (a
program-structural quantity, not specification-dependent), the scaffold
overhead is $O(1)$ per function for a fixed branching factor---consistent
with the $3.3\times$ aggregate ratio observed in our evaluation.
\end{corollary}

\begin{remark}[The extraction tax]
In \Fstar{}, the extraction step from F* to OCaml
\emph{discards} verification information: the extracted OCaml code
carries no trace of the proof.  Re-verification requires re-running
the entire F* type-checker.  In \JuGeo{}, the scaffold retains
$I(f, \phi, \mathcal{U})$ bits, enabling $O(\mu\mathrm{s})$
re-verification from the artifact alone.  We call this the
\emph{extraction tax}: the information lost during extraction,
measured in bits, that must be reconstructed from scratch for
re-verification.  \Fstar{}'s extraction tax is $I(f, \phi, \mathcal{U})$;
\JuGeo{}'s is zero.
\end{remark}


\section{Related Work}\label{sec:related}

\paragraph{Proof-carrying code.}
Necula's Proof-Carrying Code (PCC)~\cite{necula1997pcc} pioneered
the idea that executable code can carry a machine-checkable proof
of safety.  PCC targets native code and uses verification-condition
generation over a typed assembly language.  \pcp{} adapts the PCC
philosophy to a dynamic language (Python) and replaces
verification-condition generation with runtime-witnessed
specification checking over semantic scaffolds.

\paragraph{Design by Contract.}
Meyer's Design by Contract~\cite{meyer1992dbc} embeds preconditions,
postconditions, and invariants in the source code (\Eiffel{}).
\pcp{} generalises contracts in three ways: (i)~the scaffold
functions carry richer metadata (coordinates, descent profiles,
trust annotations); (ii)~the covering-family mechanism provides
systematic input selection; (iii)~the obstruction algebra gives
structured failure diagnostics.

\paragraph{Gradual verification.}
Bader et al.~\cite{bader2018gradual} propose gradually adding
specifications to an unverified program.  \pcp{} is compatible
with gradual verification: a developer can scaffold one function at
a time, and the trust algebra tracks which functions are verified
($\Truntime$) and which are unverified ($\Tunver$).

\paragraph{CrossHair.}
\CrossHair{}~\cite{crosshair2024} is a symbolic execution tool for
Python that checks contracts specified as docstring conditions.
Unlike \pcp{}, \CrossHair{} operates as an external analysis tool:
its results do not persist in the shipped module, re-verification
requires re-running the tool, and failure diagnostics are
counterexamples rather than structured obstructions.

\paragraph{Property-based testing.}
Hypothesis~\cite{maciver2019hypothesis} generates random inputs to
check properties.  \pcp{}'s cover design is deterministic (not random)
and produces certificates with trust annotations; Hypothesis produces
test results without provenance metadata.

\paragraph{Dependent types for Python.}
Recent work on gradual dependent types~\cite{eremondi2019gradual}
explores adding dependent types to dynamic languages.  \pcp{} takes
a different approach: rather than changing Python's type system, we
embed proof metadata in the existing namespace.

\paragraph{Sheaf-theoretic verification.}
The theoretical foundations of \JuGeo{}'s sheaf-based approach are
developed in the companion papers on semantic
sites~\cite{young2025sites}, judgment algebra~\cite{young2025algebra},
and descent obstructions~\cite{young2025descent}.  The present paper
focuses on the \emph{engineering} contribution: making the sheaf
theory practically useful by embedding it in Python's module system.


\section{Conclusion}\label{sec:conclusion}

We have presented Proof-Carrying Python, a methodology that
eliminates the extraction gap by embedding proof metadata directly
in Python source code.  Five semantic scaffold functions per verified
function encode coordinate, coercion, support, descent-profile, and
marker information in the module namespace.  The \JuGeo{} generation
pipeline produces these scaffolds automatically, and a consumer can
re-derive the proof from the shipped artefact using only a Python
interpreter.

We proved three formal results: certificate soundness
(\Cref{thm:cert-sound}), re-verification completeness
(\Cref{thm:reverify-complete}), and scaffold minimality
(\Cref{thm:scaffold-minimal}).  On 8 representative Python functions
totalling 2\,347 source bytes, scaffold overhead averages
$3.30\times$---converging to $1.67\times$ for functions exceeding
500~bytes---and re-verification completes in $9.0$\,\textmu{}s on
average.  Compared with \Fstar{} ($1.5\times$ overhead but proof lost
at extraction), \LEAN{} ($2.0\times$), and \Coq{} ($1.8\times$),
\pcp{} is the only system where proofs survive in shipped code,
re-verification is near-instantaneous, and failure diagnostics are
machine-structured.

The central lesson is that Python's dynamism---far from being an
obstacle to verification---is an asset.  Scaffold functions are
first-class objects; the module namespace is a reflective dictionary;
and the runtime is a ready-made execution engine for specifications.
The proof \emph{is} the program.

\paragraph{Future work.}
We plan to (i)~scale \pcp{} to large production codebases,
(ii)~add cryptographic signing of certificates,
(iii)~integrate scaffold generation into CI/CD pipelines,
(iv)~extend the trust algebra with a $\Tproof$ tier backed by
a formal logic, and (v)~develop a scaffold differencing algorithm
that detects semantic regressions when verified functions are
modified between versions.
