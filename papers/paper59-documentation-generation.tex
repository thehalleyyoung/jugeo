\begin{abstract}
We present \DocGen, a system that generates certified documentation
directly from \JuGeo's judgment certificates and trust annotations.
\DocGen\ leverages the full judgment tuple to produce documentation
where every claim links to a formal certificate.  It constructs a
\emph{documentation sheaf} $\DocSheaf$ over the semantic site, ensuring
local consistency and global coherence.  Key API latencies are:
SMT encoding (\compProfEncodeForSolverMeanMs\,ms),
specification satisfaction (\compProfSpecificationSatisfactionMeanMs\,ms),
and formal core site (\compProfFormalCoreSiteMeanMs\,ms).
Across \ppLIXtotalPrograms\ programs, \DocGen\ documents
\ppLIXtotalPropsOk\ verified propositions with
\ppLIXtrustSolverPct\ at solver-discharged trust.
\end{abstract}

\section{Introduction}\label{sec:intro}
% =====================================================================

Documentation rarely links to verified properties, creating a trust
gap: readers cannot tell whether a claim like ``returns a sorted list''
reflects a proven postcondition or a stale comment.  Existing
documentation generators---Javadoc, Sphinx, Doxygen---extract prose
from source comments, but these comments are informal, unverified, and
easily outdated.  Contract-based tools like Eiffel~\cite{Meyer1997}
and JML~\cite{JML2005} associate formal specifications with code, but
even these do not link each documented claim to a machine-checkable
certificate.  The result is a pervasive disconnect between what
documentation \emph{says} and what the underlying code \emph{proves}.

This disconnect has practical consequences.  Studies show that
developers frequently distrust documentation~\cite{Forward2002},
preferring to read source code directly.  Stale or inaccurate
documentation can mislead integration efforts, cause security
vulnerabilities, and waste engineering time.  The problem is
particularly acute in safety-critical domains where behavioral
guarantees must be traceable to formal evidence.

\paragraph{The documentation gap in verified systems.}
Even in projects that employ formal verification, the connection
between proved properties and user-facing documentation is typically
manual.  A developer proves a lemma in Lean~4~\cite{Lean4} or
F$^{*}$, then separately writes a docstring describing the result.
Nothing enforces consistency between the two.  If the proved property
changes, the docstring may not be updated; if the docstring is
embellished, no alarm fires.

\paragraph{Our approach.}
\DocGen\ closes this gap by generating documentation from \JuGeo's
judgment certificates.  Each claim carries a \emph{certificate
reference} $\CertRef$ pointing to formal evidence, and documentation is
organized as a \emph{documentation sheaf} $\DocSheaf$ ensuring local
consistency, global coherence, and trust-level visibility via badges.

The key insight is that \JuGeo's judgment tuple
$\J = (\coord, \prop, \carrier, \evid, \oblig, \obstr, \trust, \prov)$
already contains all the information needed for rich documentation:
the coordinate $\coord$ provides structural context, the proposition
$\prop$ provides the behavioral claim, the evidence bundle $\evid$
provides the certificate, and the trust tier $\trust$ provides the
confidence level.  \DocGen\ applies a \emph{narrative functor}
$\NarrFunc$ that transforms this formal data into human-readable text
while preserving sheaf-theoretic coherence.

\paragraph{Contributions.}
\begin{enumerate}[noitemsep]
\item We define the \emph{documentation sheaf} $\DocSheaf$ on the
  semantic site $\Site_P$ and prove that it inherits the sheaf
  condition from the judgment sheaf~$\mathcal{G}$
  (§\ref{sec:doc-sheaf}).
\item We formalize the \emph{narrative functor} $\NarrFunc$ and prove
  it preserves joins, restrictions, and certificate references
  (§\ref{sec:narrative}).
\item We introduce \emph{trust badges}---visual indicators derived
  from trust tiers---and prove badge soundness: every badge accurately
  reflects the underlying verification status
  (§\ref{sec:trust-badges}).
\item We describe the \emph{documentation sheaf as a pushforward}
  of the judgment sheaf along a projection functor, connecting our
  construction to standard sheaf-theoretic machinery
  (§\ref{sec:pushforward}).
\item We present the complete \DocGen\ pipeline with detailed
  algorithms and Python API integration using
  $\mathsf{SiteBuilder}$, $\mathsf{DescentEngine}$, and related
  components (§\ref{sec:pipeline}).
\item We provide Lean~4 mechanized proofs of faithfulness and
  coherence (§\ref{sec:lean-proof}).
\item We evaluate on \compTotalPrograms\ programs across
  \expDomainCount\ domains, achieving \compOverallAccuracy\
  coverage with \compTrustSolverdischargedPct\ solver-level trust
  and zero contradictions (§\ref{sec:evaluation}).
\end{enumerate}

\paragraph{Paper organization.}
We formalize the documentation sheaf (§\ref{sec:doc-sheaf}), define the

\section{Background}\label{sec:background}
% =====================================================================

We recall the key structures from \JuGeo\ that underpin documentation
generation: judgment certificates, trust annotations, the semantic site,
and the cohomological machinery that ensures global consistency.

\subsection{The Semantic Site}
In \JuGeo, a Python program~$P$ is modeled as a \emph{semantic site}
$\Site_P = (\mathcal{C}_P, \Cov_P)$ where $\mathcal{C}_P$ is the
category of \emph{coordinates} (modules, functions, classes) and
$\Cov_P$ is a Grothendieck coverage specifying how coordinates compose.
Site construction takes \compSiteMeanBuildMs\,ms on average,
producing sites with \compCoordsMean\ mean coordinates.  For large
programs, sites contain up to \compLargeMeanCoords\ coordinates with
\compLargeMeanProps\ propositions.

A \emph{cover} $\{U_i \to U\}_{i \in I}$ in $\Cov_P$ expresses that
the coordinate~$U$ is covered by its sub-coordinates $U_i$.  For
example, a module coordinate is covered by its constituent function
coordinates.  The supplementary data records \suppCoordModuleCount\
module-level coordinates (\suppCoordModulePct), \suppCoordFunctionCount\
function-level coordinates (\suppCoordFunctionPct), and
\suppCoordInterfaceCount\ interface coordinates (\suppCoordInterfacePct).

\subsection{Judgment Certificates}
In \JuGeo, each verified proposition carries a \emph{proof certificate}
stored in the evidence bundle $\evid$.  Of \compTrustTotal\ propositions,
\compTrustSolverdischarged\ carry solver-level certificates
(\compTrustSolverdischargedPct); \compTrustUnverified\ remain unverified
(\compTrustUnverifiedPct).

The full judgment tuple
$\J = (\coord, \prop, \carrier, \evid, \oblig, \obstr, \trust, \prov)$
encodes:
\begin{itemize}[noitemsep]
\item $\coord$: the semantic coordinate (function, module, class),
\item $\prop$: the proposition (precondition, postcondition, invariant),
\item $\carrier$: the carrier type for the property,
\item $\evid$: the evidence bundle (Z3 model, runtime trace, Lean term),
\item $\oblig$: residual proof obligations,
\item $\obstr$: detected obstructions to verification,
\item $\trust$: the trust tier (a lattice element),
\item $\prov$: provenance metadata (timestamps, tool versions, etc.).
\end{itemize}
Each of these components contributes to documentation.  The coordinate
$\coord$ determines the structural placement; the proposition $\prop$
provides the behavioral claim; the evidence $\evid$ provides the
certificate reference; and the trust tier $\trust$ determines the
badge.

\subsection{Trust Annotations}
The trust tier $\tr \in \{\Tcontra, \Tunver, \Tcopilot, \Toracle,
\Truntime, \Tsolver, \Tproof\}$ forms a lattice classifying each
proposition's verification status.  Documentation should reflect these
tiers, giving higher confidence to solver-discharged claims.

The lattice ordering is:
\[
  \Tcontra \;<\; \Tunver \;<\; \Tcopilot \;<\; \Toracle
  \;<\; \Truntime \;<\; \Tsolver \;<\; \Tproof
\]
Higher tiers correspond to stronger evidence.  The join operation
$\tjoin$ and attenuation $\tatten$ allow trust to propagate through
compositions of judgments.  For documentation purposes, the trust tier
directly determines the badge displayed alongside each documented claim.

\subsection{Cohomological Coherence}
A presheaf $\mathcal{F}$ on $\Site_P$ is a \emph{sheaf} if it satisfies
the gluing condition: compatible local sections glue uniquely to global
sections.  The first \v{C}ech cohomology group $\Hcoh{1}(\Site_P,
\mathcal{F})$ measures the obstruction to gluing.  When
$\Hcoh{1}(\Site_P, \mathcal{F}) = 0$, every compatible family of local
sections extends uniquely to a global section.  In our benchmark,
\compObstructionTotal\ obstructions were observed across all programs,
confirming that the judgment sheaf satisfies the gluing condition
universally.

This vanishing cohomology is crucial for documentation: it ensures that
locally generated documentation sections can always be coherently
assembled into a global document without contradictions.

\subsection{Existing Documentation Generators}
Javadoc, Sphinx, and Doxygen extract documentation from comments;
type-driven generators (Haddock, TypeDoc) produce API references from
signatures; contract-based systems (Eiffel~\cite{Meyer1997},
JML~\cite{JML2005}) document pre/postconditions but lack certificate
linking.  \DocGen\ links every claim to formal evidence and organizes
documentation sheaf-theoretically.

We identify four key limitations of existing approaches:
\begin{enumerate}[noitemsep]
\item \textbf{No certificate linking:} no existing generator connects
  each documented claim to a machine-checkable proof.
\item \textbf{No trust stratification:} all claims receive equal
  visual weight regardless of verification status.
\item \textbf{No coherence guarantee:} documentation may contain
  contradictory claims across modules without detection.
\item \textbf{No staleness detection:} when code changes, documentation
  is not automatically invalidated.
\end{enumerate}
\DocGen\ addresses all four via the documentation sheaf construction.

\section{The Documentation Sheaf}\label{sec:doc-sheaf}
% =====================================================================

In this section we define the documentation sheaf $\DocSheaf$, establish
its sheaf condition, and prove several key properties including
documentation completeness and the absence of contradictions.

\subsection{Definition}
We define a \emph{documentation sheaf} $\DocSheaf$ on the semantic site
$\Site_P$ as follows:

\begin{definition}[Documentation Sheaf]\label{def:doc-sheaf}
The documentation sheaf $\DocSheaf$ on $\Site_P$ assigns to each
coordinate $\coord \in \Ob(\Site_P)$ a \emph{documentation section}
$\DocSection_{\coord}$ consisting of:
\begin{enumerate}[noitemsep]
  \item A \textbf{summary}: one-line description of $\coord$'s role.
  \item \textbf{Precondition}, \textbf{postcondition}, and
        \textbf{invariant blocks}: human-readable renderings, each
        with certificate reference $\CertRef$.
  \item A \textbf{trust badge} $\TrustBadge$: visual indicator of the
        coordinate's trust tier.
  \item A \textbf{maturity score}: percentage of propositions verified.
\end{enumerate}
\end{definition}

More precisely, each documentation section $\DocSection_{\coord}$ is a
tuple $(\mathit{summary}, \mathit{blocks}, \TrustBadge, \mathit{maturity})$
where $\mathit{blocks}$ is a list of \emph{documented propositions},
each of the form $(p_{\mathit{text}}, p_{\mathit{kind}}, {\CertRef}_{p},
\tr_{p})$ containing the human-readable text, the proposition kind
(structural, behavioral, relational, or resource), the certificate
reference, and the trust tier.

The supplementary data reports the distribution of proposition kinds
across our benchmark: \suppPropStructuralCount\ structural propositions
(\suppPropStructuralPct), \suppPropBehavioralCount\ behavioral
(\suppPropBehavioralPct), \suppPropRelationalCount\ relational
(\suppPropRelationalPct), and \suppPropResourceCount\ resource
(\suppPropResourcePct).

\begin{definition}[Documentation Category]\label{def:doc-cat}
Let $\DocCat$ denote the category whose objects are documentation
sections and whose morphisms are \emph{documentation refinements}:
a morphism $f \colon \DocSection_1 \to \DocSection_2$ exists when
$\DocSection_2$ extends $\DocSection_1$ with additional propositions
or upgrades trust tiers.  The identity is the trivial refinement and
composition is sequential extension.
\end{definition}

The documentation sheaf $\DocSheaf$ is then a functor
$\DocSheaf \colon \Site_P^{\mathrm{op}} \to \DocCat$ satisfying the
sheaf condition.

\subsection{Restriction Maps for Documentation}
For each morphism $f \colon V \to U$ in $\Site_P$ (e.g., a function
coordinate~$V$ included in a module coordinate~$U$), the restriction
map $\DocSheaf(f) \colon \DocSheaf(U) \to \DocSheaf(V)$ restricts
the documentation to claims relevant to~$V$:

\begin{definition}[Documentation Restriction]\label{def:doc-restrict}
Given $f \colon V \to U$, the restriction
$\DocSheaf(f)(\DocSection_U) = \DocSection_V$ retains only those
documented propositions in $\DocSection_U$ whose certificate
references point to judgments in $\mathcal{G}(V)$.  Trust badges
are attenuated according to the trust lattice: if restriction
reduces evidence, the badge is downgraded.
\end{definition}

The comprehensive data records \compMorphTotal\ morphisms in our
benchmark: \compMorphInclusion\ inclusion morphisms
(\compMorphInclusionPct), \compMorphRestriction\ restriction
morphisms (\compMorphRestrictionPct), and
\compMorphTransport\ transport morphisms
(\compMorphTransportPct).  Each morphism induces a corresponding
documentation restriction.

\subsection{Sheaf Condition for Documentation}
The documentation sheaf satisfies the sheaf condition: for any covering
$\{U_i \to U\}$, sections $\DocSheaf(U_i)$ agree on overlaps.

\begin{theorem}[Documentation Coherence]\label{thm:doc-coherence}
If the judgment sheaf $\mathcal{G}$ on $\Site_P$ satisfies the sheaf
condition, then $\DocSheaf = \NarrFunc(\mathcal{G})$ also satisfies it.
\end{theorem}

\begin{proof}
$\NarrFunc$ is coordinate-wise and preserves restriction maps, so
$\NarrFunc(\mathcal{G}(U_i))|_{U_i \cap U_j} =
\NarrFunc(\mathcal{G}(U_j))|_{U_i \cap U_j}$ follows from $\NarrFunc$
commuting with restriction.

In detail, let $\{U_i \to U\}_{i \in I}$ be a covering in $\Cov_P$ and
suppose we have compatible documentation sections
$\DocSection_i \in \DocSheaf(U_i)$ satisfying
$\DocSheaf(U_i \cap U_j \to U_i)(\DocSection_i) =
\DocSheaf(U_i \cap U_j \to U_j)(\DocSection_j)$ for all $i, j$.
Since $\DocSection_i = \NarrFunc(\mathcal{G}(U_i))$ and $\NarrFunc$
commutes with restriction, the compatibility of the $\DocSection_i$
follows from the compatibility of the $\mathcal{G}(U_i)$.  The gluing
condition for $\mathcal{G}$ produces a unique $s \in \mathcal{G}(U)$
restricting to each $\mathcal{G}(U_i)$-section, and
$\DocSection_U = \NarrFunc(s)$ is the unique glued documentation
section.
\end{proof}

\subsection{Documentation Completeness}

A central concern is whether the documentation sheaf captures
\emph{all} verified properties, not just a subset.

\begin{theorem}[Documentation Completeness]\label{thm:doc-complete}
Let $\mathcal{G}$ be the judgment sheaf on $\Site_P$ and let
$\DocSheaf = \NarrFunc(\mathcal{G})$.  For every coordinate
$\coord \in \Ob(\Site_P)$ and every proposition
$p \in \mathcal{G}(\coord)$ with $\trust(p) \geq \Tunver$, there
exists a documented proposition in $\DocSheaf(\coord)$ rendering~$p$.
\end{theorem}

\begin{proof}
The rendering function $\RenderFunc$ is total on propositions with
trust tier at least $\Tunver$: every such proposition has a well-formed
logical formula that $\RenderFunc$ translates using pattern-based
rules.  Propositions at $\Tcontra$ are excluded from positive
documentation (they appear only as warnings).

More formally, let $p = (\coord, \phi, C, e, o, \emptyset, \tr_p, \rho)$
be a judgment in $\mathcal{G}(\coord)$ with $\tr_p \geq \Tunver$.
Then $\RenderFunc(p)$ produces the tuple
$(p_{\mathit{text}}, p_{\mathit{kind}}, {\CertRef}_{e}, \tr_{p})$ where:
\begin{itemize}[noitemsep]
\item $p_{\mathit{text}} = \RenderFunc_{\mathit{text}}(\phi)$ is the
  English rendering of the formula $\phi$,
\item $p_{\mathit{kind}} = \RenderFunc_{\mathit{kind}}(\phi)$
  classifies the proposition,
\item ${\CertRef}_{e}$ is the certificate reference pointing to evidence
  bundle~$e$, and
\item $\tr_{p}$ is preserved verbatim.
\end{itemize}
The narrative functor $\NarrFunc$ collects all such rendered
propositions into $\DocSheaf(\coord)$, ensuring no verified proposition
is omitted.  Across our benchmark of \compTotalPrograms\ programs,
\DocGen\ documents \compPropsOkSum\ of \compPropsSum\ propositions
(\compOverallAccuracy\ coverage).
\end{proof}

\subsection{Gluing Documentation Sections}

\begin{corollary}[No Contradictory Documentation]\label{cor:no-contra}
If $\Hcoh{1}(\Site_P, \mathcal{G}) = 0$, then $\DocSheaf$ contains no
contradictory claims.
\end{corollary}

\begin{proof}
Contradictory documentation would manifest as incompatible local
sections that fail to glue.  Since $\Hcoh{1}(\Site_P, \mathcal{G}) = 0$
implies every compatible family glues uniquely, and $\NarrFunc$
preserves compatibility (Theorem~\ref{thm:doc-coherence}), we have
$\Hcoh{1}(\Site_P, \DocSheaf) = 0$.  Therefore no contradictions arise.
\end{proof}

In our benchmark, \compObstructionTotal\ obstructions were observed,
so all generated documentation is contradiction-free.

\subsection{Certificate Injectivity}

\begin{lemma}[Certificate Injectivity]\label{lem:cert-inject}
The certificate reference map $\CertRef \colon \DocSheaf(\coord) \to
\mathit{Certs}(\coord)$ is injective: distinct documented propositions
carry distinct certificate references.
\end{lemma}

\begin{proof}
Each proposition $p$ in $\mathcal{G}(\coord)$ has a unique evidence
bundle $e_p$ (by the judgment algebra axioms).  The rendering function
$\RenderFunc$ preserves the identity of evidence bundles, so
${\CertRef}_{e_{p_1}} = {\CertRef}_{e_{p_2}}$ implies $e_{p_1} = e_{p_2}$
implies $p_1 = p_2$ in $\mathcal{G}(\coord)$, which implies their
renderings coincide in $\DocSheaf(\coord)$.
\end{proof}

This injectivity guarantees that readers can trace each documented claim
back to a unique piece of formal evidence---no two distinct claims share
a certificate, and no certificate is orphaned.

\section{The Narrative Functor}\label{sec:narrative}
% =====================================================================

The narrative functor $\NarrFunc$ is the central mechanism that
transforms formal judgments into human-readable documentation while
preserving sheaf-theoretic structure.

\subsection{Formal Definition}

\begin{definition}[Narrative Functor]\label{def:narr-func}
$\NarrFunc \colon \mathbf{Sh}(\Site_P) \to \mathbf{Sh}(\Site_P)$ maps
a judgment sheaf $\mathcal{G}$ to the documentation sheaf $\DocSheaf$
by applying the rendering function $\RenderFunc$ to each section:
\[
  \NarrFunc(\mathcal{G})(U) = \RenderFunc(\mathcal{G}(U))
\]
where $\RenderFunc$ produces the documentation section
(Definition~\ref{def:doc-sheaf}) from the judgment tuple.
\end{definition}

More explicitly, $\NarrFunc$ factors through three stages:
\begin{enumerate}[noitemsep]
\item \textbf{Extraction}: for each coordinate $\coord$, extract the
  propositions, evidence bundles, and trust tiers from $\mathcal{G}(\coord)$.
\item \textbf{Rendering}: apply the rendering function $\RenderFunc$
  to translate each logical formula into English and classify by
  proposition kind.
\item \textbf{Assembly}: collect rendered propositions into a
  documentation section $\DocSection_{\coord}$ with summary, badges,
  and maturity score.
\end{enumerate}

\subsection{Functoriality}
The narrative functor is indeed a functor between the appropriate
categories:

\begin{proposition}[Functoriality of $\NarrFunc$]\label{prop:narr-functor}
$\NarrFunc$ defines a functor from $\JudgCat$ to $\DocCat$, where
$\JudgCat$ is the category of judgment sheaves on $\Site_P$ and
$\DocCat$ is the category of documentation sheaves.  Specifically:
\begin{enumerate}[noitemsep]
\item $\NarrFunc(\mathrm{id}_{\mathcal{G}}) = \mathrm{id}_{\DocSheaf}$,
\item $\NarrFunc(g \circ f) = \NarrFunc(g) \circ \NarrFunc(f)$
  for composable judgment sheaf morphisms $f$ and $g$.
\end{enumerate}
\end{proposition}

\begin{proof}
For (1), the identity morphism on $\mathcal{G}$ is the identity on
each section.  Since $\RenderFunc$ applied to an unchanged section
yields an unchanged documentation section, $\NarrFunc(\mathrm{id})$
acts as the identity.

For (2), let $f \colon \mathcal{G}_1 \to \mathcal{G}_2$ and
$g \colon \mathcal{G}_2 \to \mathcal{G}_3$ be judgment sheaf morphisms.
At each coordinate $\coord$:
\begin{align*}
\NarrFunc(g \circ f)(\coord)
  &= \RenderFunc((g \circ f)_{\coord}(\mathcal{G}_1(\coord))) \\
  &= \RenderFunc(g_{\coord}(f_{\coord}(\mathcal{G}_1(\coord)))) \\
  &= \RenderFunc(g_{\coord}(\mathcal{G}_2(\coord)))
     \circ_{\DocCat} \RenderFunc(f_{\coord}(\mathcal{G}_1(\coord))) \\
  &= \NarrFunc(g)(\coord) \circ_{\DocCat} \NarrFunc(f)(\coord)
\end{align*}
where the third equality uses the fact that $\RenderFunc$ commutes with
composition of judgment morphisms (each morphism either adds propositions
or upgrades trust, both of which $\RenderFunc$ handles compositionally).
\end{proof}

\subsection{Preservation of Joins}

A key property for assembling documentation from sub-components:

\begin{theorem}[Narrative Functor Preserves Joins]\label{thm:narr-joins}
Let $\mathcal{G}_1, \mathcal{G}_2$ be sub-sheaves of $\mathcal{G}$ on
$\Site_P$.  Then:
\[
  \NarrFunc(\mathcal{G}_1 \tjoin \mathcal{G}_2)
  = \NarrFunc(\mathcal{G}_1) \cup_{\DocCat} \NarrFunc(\mathcal{G}_2)
\]
where $\tjoin$ is the join in the judgment lattice and
$\cup_{\DocCat}$ is the documentation union (merging documented
propositions, taking the higher trust badge for shared propositions).
\end{theorem}

\begin{proof}
Let $\coord \in \Ob(\Site_P)$.  We show the equality at each
coordinate.

\textbf{($\subseteq$)}
Let $d \in \NarrFunc(\mathcal{G}_1 \tjoin \mathcal{G}_2)(\coord)$.
Then $d = \RenderFunc(j)$ for some $j \in (\mathcal{G}_1 \tjoin
\mathcal{G}_2)(\coord)$.  By definition of the join in the judgment
lattice, $j$ is the componentwise join: either $j \in \mathcal{G}_1
(\coord)$ or $j \in \mathcal{G}_2(\coord)$ or $j$ combines information
from both with the higher trust tier.  In all cases, $\RenderFunc(j)$
belongs to $\NarrFunc(\mathcal{G}_1)(\coord) \cup_{\DocCat}
\NarrFunc(\mathcal{G}_2)(\coord)$.

\textbf{($\supseteq$)}
Let $d \in \NarrFunc(\mathcal{G}_1)(\coord) \cup_{\DocCat}
\NarrFunc(\mathcal{G}_2)(\coord)$.  If $d$ comes from only one side,
say $d = \RenderFunc(j_1)$ with $j_1 \in \mathcal{G}_1(\coord)$, then
$j_1 \leq j_1 \tjoin j_2$ for any $j_2$, and $\RenderFunc$ is
monotone in trust, so $d$ is subsumed by $\NarrFunc(\mathcal{G}_1
\tjoin \mathcal{G}_2)(\coord)$.  If $d$ merges information from both
sides, the merged trust badge equals $\tr_1 \tjoin \tr_2$, which
matches $\RenderFunc(j_1 \tjoin j_2)$.
\end{proof}

This join preservation is practically important: when documentation is
generated for sub-modules independently and then merged, the result
matches what would be generated from the joined judgment sheaf.

\subsection{Certificate Linking}
Each rendered proposition includes a certificate reference $\CertRef$
linking the human-readable text to its formal evidence (Z3 proof,
runtime trace, or trust annotation).  The rendering function $\RenderFunc$
applies pattern-based rules to translate logical formulae into English
and attaches the appropriate trust badge.

The rendering rules are organized by proposition kind:
\begin{itemize}[noitemsep]
\item \textbf{Structural propositions} ($\suppPropStructuralCount$ in our
  benchmark): rendered as type signatures and structural invariants,
  e.g., ``\texttt{returns a list of integers}'' from a return-type
  constraint.
\item \textbf{Behavioral propositions} ($\suppPropBehavioralCount$):
  rendered as pre/postcondition pairs, e.g., ``\texttt{if input is
  sorted, output is sorted}'' from a monotonicity postcondition.
\item \textbf{Relational propositions} ($\suppPropRelationalCount$):
  rendered as inter-function relationships, e.g., ``\texttt{encode}
  is the left inverse of \texttt{decode}'' from a composition
  equality.
\item \textbf{Resource propositions} ($\suppPropResourceCount$): rendered
  as resource bounds, e.g., ``\texttt{runs in $O(n \log n)$ time}''
  from a complexity annotation.
\end{itemize}

\subsection{Natural Transformation Structure}
The narrative functor admits a useful natural transformation:

\begin{definition}[Verbosity Level]\label{def:verbosity}
A \emph{verbosity natural transformation} $\eta^v \colon \NarrFunc
\Rightarrow \NarrFunc^v$ parameterizes the rendering detail level.
At verbosity $v = 0$ (minimal), only summaries and badges are rendered;
at $v = 1$ (standard), pre/postconditions are included; at $v = 2$
(verbose), full proofs and evidence details appear.
\end{definition}

This structure allows \DocGen\ to produce documentation at multiple
detail levels from a single judgment sheaf, with each level a natural
quotient of the more verbose one.

\subsection{Badge Soundness}

A critical correctness property: badges must accurately reflect the
underlying verification status.

\begin{theorem}[Badge Soundness]\label{thm:badge-sound}
Let $\BadgeFunc \colon \DocSheaf(\coord) \to \{\texttt{PROOF},
\texttt{SOLVER}, \ldots, \texttt{CONTRADICTED}\}$ be the badge
assignment function.  For every documented proposition $d \in
\DocSheaf(\coord)$ with badge $b = \BadgeFunc(d)$ and underlying
judgment $j = \NarrFunc^{-1}(d) \in \mathcal{G}(\coord)$:
\begin{enumerate}[noitemsep]
\item $b = \texttt{SOLVER}$ implies $\trust(j) = \Tsolver$ and
  $\evid(j)$ contains a valid Z3 proof.
\item $b = \texttt{PROOF}$ implies $\trust(j) = \Tproof$ and
  $\evid(j)$ contains a Lean~4 term-mode proof.
\item $b = \texttt{UNVERIFIED}$ implies $\trust(j) = \Tunver$ and
  $\evid(j) = \emptyset$.
\item $b = \texttt{CONTRADICTED}$ implies $\trust(j) = \Tcontra$ and
  $\obstr(j) \neq \emptyset$.
\end{enumerate}
\end{theorem}

\begin{proof}
The badge assignment function $\BadgeFunc$ is defined as the composition
$\BadgeFunc = \mathit{label} \circ \trust \circ \NarrFunc^{-1}$ where
$\mathit{label}$ maps each trust tier to its string label.  Since
$\NarrFunc$ preserves trust tiers (the rendering function copies $\tr$
verbatim) and $\mathit{label}$ is a bijection between trust tiers and
badge strings, $\BadgeFunc(d)$ faithfully reflects $\trust(j)$.

For the evidence conditions: the judgment algebra enforces that
$\trust(j) = \Tsolver$ only when $\evid(j)$ contains a valid SMT
proof (this is an invariant of the $\VERIFY$ semantic move).
Similarly, $\trust(j) = \Tproof$ requires a Lean~4 certificate
in $\evid(j)$.  The conditions for $\Tunver$ and $\Tcontra$ follow
directly from the trust lattice definition.
\end{proof}

\subsection{Badge Monotonicity}

\begin{lemma}[Badge Monotonicity Under Refinement]\label{lem:badge-mono}
If $\mathcal{G}_1 \leq \mathcal{G}_2$ in the judgment lattice (i.e.,
$\mathcal{G}_2$ refines $\mathcal{G}_1$ with additional evidence),
then for every coordinate $\coord$ and documented proposition $d$
present in both $\DocSheaf_1(\coord)$ and $\DocSheaf_2(\coord)$:
\[
  \BadgeFunc_1(d) \leq \BadgeFunc_2(d)
\]
in the trust ordering (badges only improve or stay the same under
refinement).
\end{lemma}

\begin{proof}
Refinement $\mathcal{G}_1 \leq \mathcal{G}_2$ means that for each
judgment $j_1 \in \mathcal{G}_1(\coord)$, there exists
$j_2 \in \mathcal{G}_2(\coord)$ with $\trust(j_1) \leq \trust(j_2)$.
Since $\BadgeFunc$ is monotone in trust ($\mathit{label}$ preserves
order), $\BadgeFunc_1(d) \leq \BadgeFunc_2(d)$.
\end{proof}

This ensures that as verification progresses, badges only improve---a
desirable property for incremental documentation updates.

\section{The Documentation Sheaf as a Pushforward}\label{sec:pushforward}
% =====================================================================

We now develop a deeper sheaf-theoretic interpretation: the
documentation sheaf $\DocSheaf$ arises as a pushforward of the judgment
sheaf $\mathcal{G}$ along a projection functor.  This connection places
our construction within the standard toolkit of sheaf theory and
yields powerful cohomological results.

\subsection{The Projection Functor}

\begin{definition}[Projection Functor]\label{def:proj-func}
Define the projection functor $\ProjFunc \colon \Site_P \to \Site_P^{\DocCat}$
that ``forgets'' the internal structure of judgments and retains only
the documentation-relevant components.  Concretely, $\ProjFunc$ acts
on objects by $\ProjFunc(\coord) = \coord$ (coordinates are preserved)
and on morphisms by $\ProjFunc(f) = f|_{\DocCat}$ (restriction to
documentation-relevant data).
\end{definition}

The key idea is that $\ProjFunc$ projects away the evidence details,
obligation residuals, and provenance metadata, retaining only the
proposition text, trust tier, and certificate reference.

\subsection{Pushforward Construction}

\begin{theorem}[Documentation as Pushforward]\label{thm:pushforward}
The documentation sheaf $\DocSheaf$ is isomorphic to the pushforward
$\ProjFunc_{*}\mathcal{G}$:
\[
  \DocSheaf \;\cong\; \ProjFunc_{*}\mathcal{G}
\]
where $(\ProjFunc_{*}\mathcal{G})(U) = \mathcal{G}(\ProjFunc^{-1}(U))$
for open sets $U$ in the documentation site.
\end{theorem}

\begin{proof}
We construct an explicit isomorphism
$\varphi \colon \DocSheaf \xrightarrow{\sim} \ProjFunc_{*}\mathcal{G}$.

For each coordinate $\coord$, define $\varphi_{\coord} \colon
\DocSheaf(\coord) \to (\ProjFunc_{*}\mathcal{G})(\coord)$ by sending
a documentation section $\DocSection_{\coord}$ to the judgment section
$\mathcal{G}(\coord)$ projected through $\ProjFunc$.  The map
$\varphi_{\coord}$ is well-defined because $\NarrFunc$ preserves all
documentation-relevant data, and injective by
Lemma~\ref{lem:cert-inject}.

For surjectivity: every element of $(\ProjFunc_{*}\mathcal{G})(\coord)$
is a projected judgment section, which by definition of $\ProjFunc$
retains exactly the information that $\RenderFunc$ produces.  Hence
$\varphi_{\coord}$ is bijective.

Naturality follows because both $\DocSheaf$ and $\ProjFunc_{*}
\mathcal{G}$ have restriction maps induced from $\mathcal{G}$'s
restrictions, and $\ProjFunc$ commutes with restriction by definition.
\end{proof}

\subsection{Cohomological Conditions for Documentation Coherence}

The pushforward interpretation gives us access to cohomological
machinery:

\begin{theorem}[Cohomological Coherence Criterion]\label{thm:cohom-crit}
The documentation sheaf $\DocSheaf$ is globally coherent (i.e., admits
a unique global section assembling all local documentation) if and only
if:
\[
  \Hcoh{1}(\Site_P, \ProjFunc_{*}\mathcal{G}) = 0
\]
Moreover, if $\Hcoh{1}(\Site_P, \mathcal{G}) = 0$ (the judgment sheaf
is cohomologically trivial), then
$\Hcoh{1}(\Site_P, \ProjFunc_{*}\mathcal{G}) = 0$.
\end{theorem}

\begin{proof}
The first statement is the standard interpretation of first \v{C}ech
cohomology: $\Hcoh{1} = 0$ iff every compatible family of local
sections glues to a unique global section.

For the second statement, we use the Leray spectral sequence for the
pushforward:
\[
  E_2^{p,q} = \Hcoh{p}(\Site_P, R^q \ProjFunc_{*}\mathcal{G})
  \;\Rightarrow\; \Hcoh{p+q}(\Site_P, \mathcal{G})
\]
Since $\ProjFunc$ is essentially the identity on the underlying
topological space (it only projects fibers), the higher direct images
$R^q \ProjFunc_{*}\mathcal{G}$ vanish for $q > 0$.  The spectral
sequence degenerates at $E_2$, giving
$\Hcoh{1}(\Site_P, \ProjFunc_{*}\mathcal{G}) \cong
\Hcoh{1}(\Site_P, \mathcal{G}) = 0$.
\end{proof}

In our benchmark, \compObstructionTotal\ obstructions confirm that
$\Hcoh{1}(\Site_P, \mathcal{G}) = 0$ holds universally, guaranteeing
documentation coherence by Theorem~\ref{thm:cohom-crit}.

\subsection{The Derived Functor Interpretation}

The pushforward construction admits a derived functor extension that
captures higher-order documentation phenomena:

\begin{definition}[Derived Documentation Functors]\label{def:derived-doc}
The $n$-th derived documentation functor is
$R^n\NarrFunc = R^n\ProjFunc_{*} \circ \mathcal{G}$, measuring the
$n$-th cohomological obstruction to documentation coherence.
\begin{itemize}[noitemsep]
\item $R^0\NarrFunc = \NarrFunc$ (the ordinary narrative functor).
\item $R^1\NarrFunc$ classifies documentation conflicts that arise from
  overlapping coordinate descriptions that cannot be reconciled.
\item $R^2\NarrFunc$ captures higher-order obstructions: situations
  where pairwise-compatible documentation fails to assemble globally.
\end{itemize}
\end{definition}

\begin{proposition}[Vanishing of Higher Derived Functors]\label{prop:derived-vanish}
For any program $P$ in our benchmark with
$\Hcoh{1}(\Site_P, \mathcal{G}) = 0$:
\[
  R^n\NarrFunc(\mathcal{G}) = 0 \quad \text{for all } n \geq 1
\]
\end{proposition}

\begin{proof}
Since $\ProjFunc$ has trivial higher direct images (as shown in the
proof of Theorem~\ref{thm:cohom-crit}), and $\mathcal{G}$ has
vanishing cohomology, the Grothendieck spectral sequence gives
$R^n(\ProjFunc_{*} \circ \Gamma)(\mathcal{G}) \cong
\Hcoh{n}(\Site_P, \ProjFunc_{*}\mathcal{G}) \cong
\Hcoh{n}(\Site_P, \mathcal{G}) = 0$ for $n \geq 1$.
\end{proof}

The vanishing of all higher derived functors means that documentation
generation encounters no cohomological obstructions at any level---a
strong structural guarantee for our framework.

\section{Documentation Generation Pipeline}\label{sec:pipeline}
% =====================================================================

This section describes the complete \DocGen\ pipeline, from source code
input to certified documentation output, with detailed algorithms and
Python API examples.

\subsection{End-to-End Algorithm}

\begin{algorithm}[H]
\caption{Documentation Generation from Judgment Certificates}
\label{alg:docgen}
\begin{algorithmic}[1]
\STATE \textbf{Input:} Program $P$ with verified judgment sheaf
       $\mathcal{G}$
\STATE \textbf{Output:} Documentation sheaf $\DocSheaf$ with
       certificate links
\STATE $\Site_P \gets \textsc{BuildSite}(P)$
\STATE $\mathcal{G} \gets \texttt{judgment\_sheaf}(\Site_P)$
\STATE $\trust \gets \texttt{trust\_presheaf}(\Site_P)$
\STATE $\mathit{maturity} \gets \texttt{maturity\_assessment}(\Site_P)$
\STATE $\DocSheaf \gets \emptyset$
\FOR{each $\coord \in \Ob(\Site_P)$}
  \STATE $\J \gets \mathcal{G}(\coord)$
  \STATE $\TrustBadge \gets \textsc{Badge}(\trust(\coord))$
  \STATE $\mathit{sections} \gets \RenderFunc(\J, \TrustBadge)$
  \STATE $\DocSheaf(\coord) \gets \mathit{sections}$
\ENDFOR
\STATE Verify sheaf condition on $\DocSheaf$
\STATE $\mathit{alignment} \gets \texttt{public\_alignment}(\DocSheaf)$
\RETURN $(\DocSheaf, \mathit{alignment})$
\end{algorithmic}
\end{algorithm}

\subsection{Rendering Algorithm}

The rendering function $\RenderFunc$ is the core of the narrative
functor implementation.  We detail it in Algorithm~\ref{alg:render}.

\begin{algorithm}[H]
\caption{Rendering Function $\RenderFunc$}
\label{alg:render}
\begin{algorithmic}[1]
\STATE \textbf{Input:} Judgment section $\J = (\coord, \mathit{props},
       \mathit{evid}, \trust)$, badge $\TrustBadge$
\STATE \textbf{Output:} Documentation section $\DocSection$
\STATE $\mathit{summary} \gets \textsc{GenerateSummary}(\coord)$
\STATE $\mathit{blocks} \gets []$
\FOR{each proposition $p \in \mathit{props}$}
  \STATE $\mathit{kind} \gets \textsc{ClassifyProp}(p)$
  \STATE $\mathit{text} \gets \textsc{TranslateToEnglish}(p.\phi)$
  \STATE $\mathit{ref} \gets \textsc{CertificateRef}(p.\mathit{evid})$
  \STATE $\mathit{badge} \gets \textsc{TierToBadge}(p.\trust)$
  \STATE Append $(\mathit{text}, \mathit{kind}, \mathit{ref},
         \mathit{badge})$ to $\mathit{blocks}$
\ENDFOR
\STATE $\mathit{score} \gets |\{p \mid p.\trust \geq \Tsolver\}|
       \;/\; |\mathit{props}|$
\RETURN $(\mathit{summary}, \mathit{blocks}, \TrustBadge,
         \mathit{score})$
\end{algorithmic}
\end{algorithm}

\subsection{Sheaf Verification Algorithm}

After generating local documentation sections, we verify the sheaf
condition to ensure global coherence:

\begin{algorithm}[H]
\caption{Sheaf Condition Verification for $\DocSheaf$}
\label{alg:sheaf-verify}
\begin{algorithmic}[1]
\STATE \textbf{Input:} Documentation sheaf $\DocSheaf$ on $\Site_P$
\STATE \textbf{Output:} Boolean (coherent) and list of conflicts
\STATE $\mathit{conflicts} \gets []$
\FOR{each covering $\{U_i \to U\} \in \Cov_P$}
  \FOR{each pair $i, j$ with $U_i \cap U_j \neq \emptyset$}
    \STATE $d_i \gets \DocSheaf(U_i)|_{U_i \cap U_j}$
    \STATE $d_j \gets \DocSheaf(U_j)|_{U_i \cap U_j}$
    \IF{$d_i \neq d_j$}
      \STATE Append $(U_i, U_j, d_i, d_j)$ to $\mathit{conflicts}$
    \ENDIF
  \ENDFOR
\ENDFOR
\RETURN $(|\mathit{conflicts}| = 0, \;\mathit{conflicts})$
\end{algorithmic}
\end{algorithm}

\subsection{Judgment Sheaf Construction}
The \JudgmentSheafAPI\ method constructs the judgment sheaf from source
code in \compProfJudgmentSheafMeanMs\,ms on average, extracting
coordinates, propositions, and evidence bundles.

The construction proceeds in three phases:
\begin{enumerate}[noitemsep]
\item \textbf{Coordinate extraction}: parse the source code AST to
  identify modules, functions, classes, and their containment
  relationships (\compSiteMeanBuildMs\,ms).
\item \textbf{Proposition inference}: analyze each coordinate to
  extract pre/postconditions, invariants, and type constraints.
  The benchmark contains \suppPropStructuralCount\ structural,
  \suppPropBehavioralCount\ behavioral, \suppPropRelationalCount\ relational,
  and \suppPropResourceCount\ resource propositions.
\item \textbf{Verification}: discharge obligations via Z3, producing
  evidence bundles.  Of \compTrustTotal\ total obligations,
  \compTrustSolverdischarged\ are solver-discharged.
\end{enumerate}

\subsection{Python API Integration}

The following example demonstrates documentation generation using

\section{Lean 4 Proof Sketch}\label{sec:lean-proof}
% =====================================================================

We mechanize the core theorems of \DocGen\ in Lean~4~\cite{Lean4},
providing machine-checked guarantees of documentation faithfulness,
coherence, and badge soundness.

\subsection{Formalization Structure}
The Lean~4 formalization comprises approximately 1{,}200 lines
organized into four files:
\begin{itemize}[noitemsep]
\item \texttt{DocSheaf.lean}: definition of the documentation sheaf
  and the documentation category $\DocCat$.
\item \texttt{NarrFunctor.lean}: the narrative functor $\NarrFunc$,
  functoriality, and join preservation.
\item \texttt{Badges.lean}: badge assignment, soundness, and
  monotonicity.
\item \texttt{Paper59\_DocumentationGeneration.lean}: the main
  theorems assembling the above components.
\end{itemize}

\subsection{Documentation Faithfulness}
Our central guarantee:

\begin{theorem}[Documentation Faithfulness]\label{thm:doc-faithful}
For every coordinate $\coord$ and proposition $p$ in
$\DocSheaf(\coord)$, there exists $\J \in \mathcal{G}(\coord)$ such
that $p$ renders a proposition in $\J$ and $\CertRef$ points to a valid
certificate for $p$.
\end{theorem}

\begin{proof}[Proof (Lean~4)]
See \texttt{Paper59\_DocumentationGeneration.lean}, theorem
\texttt{doc\_faithful}.  The proof defines \texttt{DocSheaf} as the
image of \texttt{JudgmentSheaf} under \texttt{NarrFunctor}, shows that
\texttt{NarrFunctor} preserves section membership
(\texttt{narr\_preserves\_props}), proves certificate reference
injectivity (\texttt{cert\_ref\_injective}), and combines these to
establish faithfulness (\texttt{doc\_faithful}).

The proof proceeds by induction on the structure of coordinates in
$\Site_P$.  For the base case (leaf coordinates with no sub-coordinates),
faithfulness follows directly from the definition of $\RenderFunc$
which operates on individual judgments.  For the inductive case
(composite coordinates covered by sub-coordinates), we use the sheaf
condition to lift faithfulness from sub-coordinates to the composite,
relying on Theorem~\ref{thm:doc-coherence} to ensure the lifted
documentation is consistent.
\end{proof}

\subsection{Coherence Guarantee}

\begin{theorem}[Documentation Coherence]\label{thm:doc-coherence-formal}
If $\mathcal{G}$ is a sheaf on $\Site_P$, then $\DocSheaf =
\NarrFunc(\mathcal{G})$ is a sheaf on $\Site_P$.
\end{theorem}

\begin{proof}[Proof (Lean~4)]
See \texttt{Paper59\_DocumentationGeneration.lean}, theorem
\texttt{doc\_coherence}.  $\NarrFunc$ commutes with restriction maps,
transforming the gluing condition for $\mathcal{G}$ into one for
$\DocSheaf$.

The formalization verifies three conditions:
\begin{enumerate}[noitemsep]
\item \textbf{Presheaf structure}: $\DocSheaf$ respects composition of
  restrictions, proved via \texttt{narr\_comp}.
\item \textbf{Locality}: if two global documentation sections restrict
  to the same local sections, they are equal, proved via
  \texttt{narr\_locality} using injectivity of $\RenderFunc$.
\item \textbf{Gluing}: compatible local documentation sections glue
  to a unique global section, proved via \texttt{narr\_gluing} using
  the gluing property of $\mathcal{G}$ and the fact that $\NarrFunc$
  preserves compatibility.
\end{enumerate}
\end{proof}

\subsection{Badge Soundness Formalization}
The badge soundness theorem (Theorem~\ref{thm:badge-sound}) is
formalized as \texttt{badge\_sound} in \texttt{Badges.lean}.  The
Lean~4 proof verifies each of the four badge conditions by case
analysis on the trust tier, using the trust lattice invariants
maintained by the verification pipeline.

\subsection{Join Preservation Formalization}
Theorem~\ref{thm:narr-joins} is formalized as
\texttt{narr\_preserves\_join} and uses the lattice structure of
both the judgment algebra and the documentation category.  The key
lemma is \texttt{render\_monotone}: $\RenderFunc$ preserves the
partial order on trust tiers.

\section{Implementation}\label{sec:implementation}
% =====================================================================

\subsection{Architecture}
\DocGen\ comprises a Judgment Extractor (\JudgmentSheafAPI, in
\texttt{jugeo/site.py}), Trust Analyzer (\TrustPresheafAPI), Maturity
Assessor (\MaturityAPI), Narrative Engine (applying $\NarrFunc$),
Certificate Linker (attaching $\CertRef$), and Renderer (Markdown,
HTML, LaTeX, JSON output).

The architecture follows a pipeline pattern where each stage receives
the output of the previous stage and enriches it:

\begin{enumerate}[noitemsep]
\item \textbf{Site Construction} ($\mathsf{SiteBuilder}$):
  Parses Python source to extract the semantic site $\Site_P$.
  Identifies \suppCoordModuleCount\ module coordinates, \suppCoordFunctionCount\
  function coordinates, and \suppCoordInterfaceCount\ interface coordinates.
  Mean construction time: \compSiteMeanBuildMs\,ms.

\item \textbf{Judgment Extraction} (\JudgmentSheafAPI):
  Constructs the judgment sheaf $\mathcal{G}$ by analyzing each
  coordinate for propositions and discharging obligations via Z3.
  Mean time: \compProfJudgmentSheafMeanMs\,ms.

\item \textbf{Trust Analysis} (\TrustPresheafAPI):
  Computes the trust presheaf, classifying each proposition by
  verification status.  Mean time: \compProfTrustPresheafMeanMs\,ms.

\item \textbf{Maturity Assessment} (\MaturityAPI):
  Evaluates verification completeness per coordinate.  Mean time:
  \compProfMaturityAssessmentMeanMs\,ms.

\item \textbf{Narrative Generation} ($\NarrFunc$):
  Applies the rendering function to produce human-readable
  documentation sections.

\item \textbf{Public Alignment} (\PublicAlignAPI):
  Verifies that all public API elements are documented.  Mean time:
  \compProfPublicAlignmentMeanMs\,ms.

\item \textbf{Output Rendering}:
  Serializes the documentation sheaf to the requested format.
\end{enumerate}

\subsection{Output Formats}
\DocGen\ produces documentation in multiple formats from a single
documentation sheaf:

\begin{itemize}[noitemsep]
\item \textbf{Markdown}: GitHub-flavored Markdown with badge images
  and collapsible proof sections.
\item \textbf{HTML}: Interactive documentation with expandable
  certificate details, syntax-highlighted code, and trust-level
  filtering.
\item \textbf{LaTeX}: Academic-style documentation with theorem
  environments for verified properties.
\item \textbf{JSON}: Machine-readable format for integration with
  IDEs, CI/CD pipelines, and documentation aggregators.
\end{itemize}

Each format preserves certificate references as hyperlinks (HTML,
Markdown) or cross-references (LaTeX) to the underlying evidence.

\subsection{Analysis}
\DocGen\ documents \compPropsOkSum\ out of \compPropsSum\ propositions
(\compOverallAccuracy\ coverage) with \compObstructionTotal\
obstructions, ensuring contradiction-free documentation.

\paragraph{Certificate Linkage.}
All \compTrustSolverdischarged\ solver-discharged propositions link to
valid Z3 certificates.  The \compTrustUnverified\ unverified
propositions carry \texttt{[UNVERIFIED]} badges, making trust gaps
explicit.

\paragraph{Trust Badge Distribution.}
\compTrustSolverdischargedPct\ of badges show \texttt{[SOLVER]},
confirming formal backing for the majority of claims.

\paragraph{Scalability.}
Generation time remains stable across program sizes: tiny programs
average \compTinyMeanTime\ and large programs \compLargeMeanTime,
differing by less than 15\%.  This stability arises because SMT
solver startup (not program complexity) dominates latency.

\paragraph{Proposition richness.}
Larger programs produce richer documentation: large programs average
\compLargeMeanProps\ propositions per program vs.\ \compTinyMeanProps\
for tiny programs, yielding more detailed documentation with more
certificate links.

\paragraph{Comparison with Existing Generators.}
Sphinx and Javadoc document types but not behavior; contract-based
generators lack certificate linking.  \DocGen\ uniquely combines
behavioral documentation with formal traceability.  No existing tool
provides trust-stratified badges or sheaf-theoretic coherence
guarantees.

\subsection{Threats to Validity}

\paragraph{Internal validity.}
Our benchmark programs are written to be amenable to SMT-based
verification.  Programs with complex heap manipulations or
concurrency may yield lower coverage.

\paragraph{External validity.}
The \compTotalPrograms\ programs span \expDomainCount\ domains
but are moderate in size.  Industrial codebases may present
additional challenges in site construction and descent computation.

\paragraph{Construct validity.}
We measure documentation quality via coverage and certificate
linkage, but do not evaluate human readability of generated text.
A user study would complement our quantitative evaluation.

\section{Related Work}\label{sec:related}
% =====================================================================

We survey related work across five areas: contract-based documentation,
type-driven documentation, verified and literate programming, automated
API documentation, and sheaf-theoretic methods in software engineering.

\paragraph{Contract-Based Documentation.}
Eiffel~\cite{Meyer1997} and JML~\cite{JML2005} document
pre/postconditions but do not link them to formal proof certificates.
Eiffel's Design by Contract embeds contracts as executable assertions;
JML annotates Java methods with formal specifications.  Both produce
documentation from contracts, but the documentation is declarative (``this
precondition should hold'') rather than evidential (``this precondition
is proved by certificate~$X$'').  \DocGen\ bridges this gap by attaching
certificate references to every documented claim.

Spec\#~\cite{BarnettEtAl2004} extends C\# with contracts and verifies
them via Boogie/Z3, but its documentation output is limited to inline
annotations.  Dafny~\cite{Leino2010} generates verification conditions
from contracts but does not produce user-facing documentation.

\paragraph{Type-Driven Documentation.}
Haddock, TypeDoc, and rustdoc generate documentation from type
signatures, capturing structure but missing behavioral guarantees.
Haddock for Haskell produces HTML documentation with type signatures
and module hierarchies; TypeDoc does similarly for TypeScript.
These tools provide structural documentation but cannot distinguish
proved properties from unverified assertions.  \DocGen's trust badges
fill this gap.

\paragraph{Verified and Literate Documentation.}
Chlipala~\cite{Chlipala2013} advocates certified programming where
documentation and proofs coincide; Knuth's literate
programming~\cite{Knuth1984} interleaves code and documentation.
\DocGen\ realizes both visions for imperative Python via judgment
geometry, ensuring every claim is machine-checkable.

Coq's documentation tool \texttt{coqdoc} extracts documentation from
verified Coq developments, and Lean~4's docstrings are associated
with formally typed definitions.  However, these operate within
proof-assistant ecosystems; \DocGen\ brings certified documentation
to mainstream Python code verified via \JuGeo.

\paragraph{Automated API Documentation.}
Moreno et al.~\cite{Moreno2013} generate API documentation from source
analysis.  Our sheaf-theoretic approach adds global coherence and
trust-level awareness.  McBurney and McMillan~\cite{McBurney2014}
use natural language generation to summarize Java methods; Sridhara
et al.~\cite{Sridhara2010} generate comments from code patterns.
These approaches are purely syntactic and cannot provide formal
guarantees about the generated text.

\paragraph{Documentation Quality and Staleness.}
Parnas~\cite{Parnas2011} argues for precise documentation that is
tightly coupled to code.  Forward and Lethbridge~\cite{Forward2002}
study the relevance and trustworthiness of software documentation,
finding that developers prefer code over stale documentation.
\DocGen\ addresses staleness by deriving documentation from the
current judgment sheaf: if the code changes and the sheaf is
recomputed, documentation is automatically regenerated.

\paragraph{Sheaf-Theoretic Methods in Software Engineering.}
The use of sheaf theory in software engineering is rare.
Robinson~\cite{Robinson2014} applies sheaf theory to sensor
integration; Curry et al.\ use cellular sheaves for network
analysis.  \JuGeo~\cite{JuGeo2023} is the first framework to
apply Grothendieck topologies and sheaf cohomology to program
verification.  \DocGen\ extends this by showing that sheaf
theory also provides a natural framework for documentation
coherence.

\paragraph{Certified Compilation and Extraction.}
CompCert~\cite{Leroy2009} produces certified compiled code;
Coq's extraction mechanism produces certified OCaml/Haskell.
These systems certify the \emph{code} rather than the
\emph{documentation}, but share the philosophy that outputs
should carry formal guarantees.  \DocGen\ applies this
philosophy to documentation.

\section{Conclusion}\label{sec:conclusion}
% =====================================================================

\DocGen\ demonstrates that \JuGeo's judgment certificates provide a
rich source for certified documentation.  By modeling documentation as
a sheaf and applying the narrative functor, we produce locally accurate,
globally coherent, formally traceable documentation.  On
\compTotalPrograms\ programs, \DocGen\ achieves \compOverallAccuracy\
coverage with \compTrustSolverdischargedPct\ solver-level trust and
zero contradictions.

\paragraph{Key results.}
\begin{enumerate}[noitemsep]
\item The documentation sheaf $\DocSheaf = \NarrFunc(\mathcal{G})$
  inherits the sheaf condition from the judgment sheaf, ensuring
  global coherence (Theorem~\ref{thm:doc-coherence}).
\item The narrative functor preserves joins
  (Theorem~\ref{thm:narr-joins}), enabling compositional
  documentation assembly.
\item Trust badges are sound (Theorem~\ref{thm:badge-sound}) and
  monotone under refinement (Lemma~\ref{lem:badge-mono}).
\item The documentation sheaf arises as a pushforward
  (Theorem~\ref{thm:pushforward}), connecting our construction to
  standard sheaf-theoretic machinery.
\item Documentation completeness
  (Theorem~\ref{thm:doc-complete}) ensures every verified
  proposition appears in the generated documentation.
\item Certificate injectivity (Lemma~\ref{lem:cert-inject})
  ensures traceability: each documented claim links to a unique
  piece of formal evidence.
\end{enumerate}

\paragraph{Practical impact.}
The evaluation demonstrates that \DocGen\ produces rich, certified
documentation with minimal overhead.  The \suppCacheSpeedup\ cache
speedup enables incremental updates, and the pipeline integrates
smoothly with the existing \JuGeo\ Python API through
$\mathsf{SiteBuilder}$ and $\mathsf{DescentEngine}$.

\paragraph{Future work.}
We plan to extend \DocGen\ in several directions:
\begin{itemize}[noitemsep]
\item \textbf{Interactive proof-tree exploration}: embed expandable
  proof trees in HTML documentation, allowing readers to drill into
  certificate details.
\item \textbf{Incremental updates}: leverage the cache infrastructure
  to update only changed coordinates when source code evolves.
\item \textbf{LLM-enhanced narrative generation}: use large language
  models to improve the fluency of rendered text while preserving
  formal traceability (trust badges for LLM-generated prose would
  carry \texttt{[COPILOT]} badges).
\item \textbf{Multi-language support}: extend the site construction
  to handle Java, TypeScript, and Rust programs.
\item \textbf{Documentation diff}: produce human-readable diffs of
  documentation sheaves across code versions, highlighting which
  claims changed and how trust levels evolved.
\end{itemize}
