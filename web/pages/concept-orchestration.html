The Geometry of Orchestration

Why research software drifts apart, and how descent prevents it.

🕑 25 min read Core Concept
📋
On this page: The co-evolution problem · Workspace site · Consistency as sheaf condition · Hallucination as H¹ · Staleness as stale sections · Specification drift · Trust algebra for claims · Semantic moves · Why geometry, not engineering

1. The Co-Evolution Problem

When an LLM generates a research repository, it must simultaneously produce four distinct artifacts: mathematical theory, executable code, benchmark evidence, and a paper. This is not four independent tasks. Every artifact makes implicit claims about the others, and those claims must hold globally at all times.

They routinely do not. The failure modes are well-known to anyone who has watched an LLM generate or modify a large research codebase:

hallucination

The paper claims F1 = 0.83 but the benchmarks show F1 = 0.71. The LLM wrote a number it expected to be true, not a number it measured.

theory–code gap

The code implements algorithm A (e.g., a greedy sweep) but the theory section describes algorithm B (e.g., a DP formulation). Both are locally coherent; globally they are inconsistent.

staleness

The paper cites benchmark results from an earlier version of the code. The code was updated in file 38; the paper still reflects file 17. The LLM's context did not include the update.

spec drift

The specification was implicitly relaxed mid-session to let the optimizer converge, but the paper still claims the original (tighter) guarantees. No one flagged the divergence.

The traditional diagnosis is that these are software engineering failures: missing tests, poor review practices, insufficiently disciplined prompting. That diagnosis is wrong, or at least incomplete. The real structure of the problem is geometric: the four artifacts are objects in a space, and consistency is a topological condition on that space. Recognizing this changes what tools you reach for.

💡

The key insight. Inconsistency between artifacts is not evidence of a bad prompt or a bad test suite. It is evidence that a section of the consistency sheaf failed to descend from the local level (each artifact separately correct) to the global level (all artifacts jointly consistent). The language of sheaf theory gives this failure a precise name and a precise classification.

2. The Workspace Site

Fix a research workspace. The workspace is a Grothendieck site \((\mathcal{W}, J_\mathcal{W})\) where the underlying category \(\mathcal{W}\) has four objects and six morphisms, and the topology \(J_\mathcal{W}\) encodes which collections of objects cover which other objects.

2.1 The Four Artifact Surfaces

The objects of \(\mathcal{W}\) are the four artifact surfaces of the workspace:

Definition 1 — Artifact Surfaces
\[ \mathrm{Ob}(\mathcal{W}) \;=\; \bigl\{\, \mathcal{T},\; \mathcal{R},\; \mathcal{E},\; \mathcal{P} \,\bigr\} \]
\(\mathcal{T}\)

Theory surface

Definitions, theorems, proofs. Everything that lives in the math layer: axioms, lemmas, formal specifications. Produced primarily by CONSTRUCT moves on the theory surface.

\(\mathcal{R}\)

Code surface

Python (or other) source files. The executable artifact that operationalizes the theory. Produced by CONSTRUCT moves on the code surface, constrained to implement \(\mathcal{T}\).

\(\mathcal{E}\)

Evidence surface

Benchmark outputs, test results, profiling data, ablation tables. Ground truth produced by actually running \(\mathcal{R}\). Cannot be fabricated: evidence sections carry RUNTIME_WITNESSED trust or lower.

\(\mathcal{P}\)

Claims surface

The paper, README, and any human-facing documentation. Claims about \(\mathcal{T}\), \(\mathcal{R}\), and \(\mathcal{E}\). Must be covered by all three other surfaces simultaneously.

2.2 The Six Semantic Morphisms

The morphisms of \(\mathcal{W}\) are six directed semantic dependency arrows. Each arrow asserts a specific obligation: that the target artifact is constrained by, derived from, or validated against the source artifact.

Definition 2 — Semantic Morphisms
\[ \mathcal{T} \xrightarrow{\;\text{impl}\;} \mathcal{R}, \qquad \mathcal{R} \xrightarrow{\;\text{eval}\;} \mathcal{E}, \qquad \mathcal{E} \xrightarrow{\;\text{report}\;} \mathcal{P} \] \[ \mathcal{T} \xrightarrow{\;\text{formalize}\;} \mathcal{P}, \qquad \mathcal{R} \xrightarrow{\;\text{demo}\;} \mathcal{P}, \qquad \mathcal{E} \xrightarrow{\;\text{validate}\;} \mathcal{T} \]
MorphismFromToSemantic obligation
impl \(\mathcal{T}\) \(\mathcal{R}\) Code must faithfully implement the theory. Every function mentioned in \(\mathcal{T}\) must correspond to a concrete implementation in \(\mathcal{R}\).
eval \(\mathcal{R}\) \(\mathcal{E}\) Evidence must be produced by executing the code, not by estimation or extrapolation. All benchmark numbers must be reproducible from \(\mathcal{R}\).
report \(\mathcal{E}\) \(\mathcal{P}\) Every quantitative claim in the paper must match a measured value in the evidence surface, within the stated experimental conditions.
formalize \(\mathcal{T}\) \(\mathcal{P}\) The paper's informal description of theorems must faithfully represent the formal statements in the theory surface.
demo \(\mathcal{R}\) \(\mathcal{P}\) Code listings, usage examples, and algorithm descriptions in the paper must match the actual implementation.
validate \(\mathcal{E}\) \(\mathcal{T}\) Empirical results can retroactively constrain the theory. If benchmark results contradict a theorem, the theorem must be revisited.

2.3 The Workspace Topology

The Grothendieck topology \(J_\mathcal{W}\) on \(\mathcal{W}\) specifies the covering families: which collections of objects jointly cover which objects. These covering families encode the consistency obligations.

Definition 3 — Workspace Covering Families
\[ J_\mathcal{W}(\mathcal{P}) \;=\; \bigl\{\{\mathcal{T},\, \mathcal{R},\, \mathcal{E}\}\bigr\} \] \[ J_\mathcal{W}(\mathcal{R}) \;=\; \bigl\{\{\mathcal{T}\}\bigr\} \] \[ J_\mathcal{W}(\mathcal{E}) \;=\; \bigl\{\{\mathcal{R}\}\bigr\} \] \[ J_\mathcal{W}(\mathcal{T}) \;=\; \bigl\{\{\mathcal{E}\}\bigr\} \]

Reading these in plain language: the claims surface \(\mathcal{P}\) is covered jointly by the theory, code, and evidence surfaces — every claim must trace to at least one of these three sources. The code surface is covered by the theory alone: theory is the unique source of truth for what the code should do. Evidence is covered by code: the only legitimate source of benchmark numbers is executing the implementation. And theory is covered by evidence: empirical results are the grounding condition for theoretical claims.

3. Consistency IS the Sheaf Condition

The workspace \((\mathcal{W}, J_\mathcal{W})\) is a site. Define the consistency sheaf \(\mathcal{F}_\mathcal{W}\): for each artifact surface \(S \in \mathrm{Ob}(\mathcal{W})\), the section \(\mathcal{F}_\mathcal{W}(S)\) is the set of semantic contracts that hold on \(S\) — propositions about the artifact's content that are currently verified.

The workspace is globally consistent if and only if the consistency sheaf satisfies descent on \((\mathcal{W}, J_\mathcal{W})\). Spelling this out for each covering family:

  • Claims are grounded (\(J_\mathcal{W}(\mathcal{P})\)): every section of \(\mathcal{F}_\mathcal{W}(\mathcal{P})\) — every claim in the paper — must be the restriction of a section from at least one of \(\mathcal{T}\), \(\mathcal{R}\), or \(\mathcal{E}\), and the restrictions must agree on overlaps. In English: every paper claim traces back to theory, code, or measured evidence, with no contradictions.
  • Code implements theory (\(J_\mathcal{W}(\mathcal{R})\)): the semantic contracts on the code surface must be restrictions of contracts from the theory surface along the impl morphism. Code that does something the theory does not specify, or fails to do something the theory requires, violates descent.
  • Evidence is reproducible (\(J_\mathcal{W}(\mathcal{E})\)): every benchmark datum must be a restriction from the code surface along the eval morphism. Numbers not derivable by running the code are not valid sections.
  • Theory is empirically grounded (\(J_\mathcal{W}(\mathcal{T})\)): theoretical claims must not contradict the measured evidence. When empirical results conflict with a theorem, the theorem is an inconsistent section and descent fails.
Theorem 1 — Consistency via Descent
\[ \text{Workspace is consistent} \;\;\Longleftrightarrow\;\; \mathcal{F}_\mathcal{W} \in \mathrm{Sh}(\mathcal{W}, J_\mathcal{W}) \]

i.e., \(\mathcal{F}_\mathcal{W}\) satisfies the descent condition for every covering family in \(J_\mathcal{W}\).

When descent fails on some covering family, the failure is not just a flag — it is an obstruction class in the Čech cohomology of the workspace. The degree of the cohomology class determines the type and severity of the inconsistency.

4. Hallucination as an H¹ Obstruction

Consider the following concrete situation. The code has been benchmarked; the evidence surface \(\mathcal{E}\) contains the measured section \(s_\mathcal{E} = \{\text{F1} = 0.71\}\). The LLM, in drafting the paper, writes \(s_\mathcal{P} = \{\text{F1} = 0.83\}\). It did this by pattern-matching from its training distribution, not by inspecting \(\mathcal{E}\).

In sheaf-theoretic language: we now have two local sections, \(s_\mathcal{E}\) and \(s_\mathcal{P}\), both individually valid, but they disagree on their intersection under the report morphism. The mismatch defines a 1-cochain in the Čech complex of the covering family \(\{\mathcal{E}, \mathcal{T}, \mathcal{R}\} \twoheadrightarrow \mathcal{P}\):

Hallucination as a 1-Cochain
\[ \alpha(\mathcal{E}, \mathcal{P}) \;=\; s_\mathcal{P}\big|_{\mathcal{E} \times_\mathcal{P} \mathcal{P}} - s_\mathcal{E}\big|_{\mathcal{E} \times_\mathcal{P} \mathcal{P}} \;=\; (0.83 \neq 0.71) \]

This 1-cochain \(\alpha\) is a cocycle: \(\delta \alpha = 0\) because the mismatch is self-consistent (it does not depend on how you traverse the covering). Therefore \([\alpha]\) defines a non-trivial class in \(\check{H}^1(\mathcal{U}_\mathcal{P}, \mathcal{F}_\mathcal{W})\). It cannot be resolved by refinement of the cover or by adjusting the topology — either the paper section or the evidence section must change. This is the formal sense in which hallucinated numbers are genuine obstructions, not merely warnings.

The compounding effect is equally precise. When the LLM uses F1 = 0.83 as an input to a later prompt (“given that we achieve F1 of 0.83, design an ablation study”), the fabricated number propagates through restriction maps: the new ablation section is a restriction of \(s_\mathcal{P}\), so it inherits the obstruction. The cohomological language captures exactly why this propagation is hard to undo after the fact — you cannot repair the downstream sections without first repairing the original cocycle.

⚠

H¹ obstructions do not resolve under re-prompting. Asking the LLM to “double-check the numbers” cannot fix a hallucination obstruction if the LLM's context still does not include the actual evidence. The geometric repair is: retrieve the measured section from \(\mathcal{E}\) and replace the paper section via a NORMALIZE move. See Section 8.

5. Staleness as Stale Sections

A more subtle failure mode arises not from fabrication but from temporal displacement. Suppose the LLM has processed files 1 through 20 of a 70-file repository, built a coherent local model, and now generates content based on that model. Files 21 through 70 may have invalidated sections that the LLM is treating as current.

In JuGeo, every section of the consistency sheaf carries a content hash: a digest of the artifact state at the time the section was computed. When a file in \(\mathcal{R}\) changes, all sections whose hash was computed over that file are marked stale. Stale sections are typed differently from current sections:

Section Validity Types
\[ \mathrm{Section}(S) \;=\; \mathrm{Current}(S, h) \;\sqcup\; \mathrm{Stale}(S, h_{\mathrm{old}}, h_{\mathrm{new}}) \;\sqcup\; \mathrm{Invalid}(S) \]

A stale section carries both the hash under which it was computed (\(h_{\mathrm{old}}\)) and the hash of the current state (\(h_{\mathrm{new}}\)). The type system enforces that stale sections cannot participate in descent without re-verification: a descent engine that attempts to glue a stale section with a current section produces a type error, not a silent incompatibility.

This matters because “refresh the context” is a heuristic, not a guarantee. An LLM instructed to refresh its context may or may not actually re-read the changed files, and there is no way to verify that it did. JuGeo's content-hash system makes the staleness condition mechanical and checkable: you can inspect the section types before running descent and know with certainty whether any stale sections are present.

⚠️

Staleness is the silent failure mode. Hallucination produces obviously wrong numbers; staleness produces plausibly-but-not-currently correct numbers. A section computed from file version 17 is valid for that version and may be numerically close to the result for version 38 — close enough to pass casual review but wrong enough to matter. The type-level distinction between Current and Stale sections is the only reliable way to catch this.

6. Specification Drift as Morphism Constraint Failure

Specification drift occurs when the effective specification governing the code is modified during an optimization session — the LLM relaxes a constraint to let the algorithm converge, but the paper still claims the original (tighter) guarantee. Neither the code nor the paper is individually inconsistent; the morphism between them has become invalid.

In the workspace site, a specification is a section of \(\mathcal{F}_\mathcal{W}(\mathcal{T})\). A specification change is a morphism \(\sigma \to \sigma'\) in the theory surface. For this morphism to be valid under the workspace topology, it must satisfy three conditions:

  1. Preservation. Existing coverage of \(\mathcal{R}\) by \(\mathcal{T}\) is not lost: if \(\sigma\) covered a code section \(r \in \mathcal{F}_\mathcal{W}(\mathcal{R})\), then \(\sigma'\) must also cover \(r\) or a replacement section \(r'\) that is compatible with \(r\) at their intersection.
  2. Proximity. The new specification \(\sigma'\) differs from \(\sigma\) by at most one axiom: \(d(\sigma, \sigma') \leq 1\) in the axiom-distance metric on \(\mathcal{F}_\mathcal{W}(\mathcal{T})\). This prevents silent “wholesale replacement” of specifications, which would invalidate the entire covering without triggering an obstruction.
  3. Demonstrability. At least one new section exists under \(\sigma'\): there is some \(r' \in \mathcal{F}_\mathcal{W}(\mathcal{R})\) that satisfies \(\sigma'\) but not \(\sigma\). A specification change that makes all existing sections invalid without producing any new ones is an obstruction, not a refinement.
Definition 4 — Valid Specification Change
\[ \sigma \xrightarrow{\text{valid}} \sigma' \;\;\Longleftrightarrow\;\; \begin{cases} \mathrm{Coverage}(\sigma, \mathcal{R}) \subseteq \mathrm{Coverage}(\sigma', \mathcal{R}) \\[4pt] d(\sigma,\, \sigma') \;\leq\; 1 \\[4pt] \exists\, r' \in \mathcal{F}_\mathcal{W}(\mathcal{R}) :\; r' \models \sigma',\; r' \not\models \sigma \end{cases} \]

When the LLM relaxes a specification without satisfying these conditions, the impl morphism \(\mathcal{T} \to \mathcal{R}\) is invalidated: the code surface is no longer covered by the theory surface because the theory has silently changed its requirements. Descent on \(J_\mathcal{W}(\mathcal{R})\) fails, and the paper's claims (which still reference the old \(\sigma\)) become a pair of incompatible sections — an H¹ obstruction between \(\mathcal{T}\) and \(\mathcal{P}\).

7. The Trust Algebra for Research Claims

Even when sections do not numerically contradict each other, they may carry different epistemic statuses that should not be conflated. JuGeo's trust algebra governs how trust levels combine when sections interact across morphisms.

For research artifacts, the three most relevant trust levels are:

RUNTIME_WITNESSED

Benchmark result

You ran the code and the output appeared in your terminal. The number is recorded in the evidence surface with a content hash and a timestamp. This is the highest achievable trust for empirical claims.

COPILOT_SUGGESTED

LLM's claim about that result

The LLM said “F1 = 0.83” in the paper draft. This is a claim about the evidence, not the evidence itself. Even if the LLM read the actual benchmark output, its section carries at most COPILOT_SUGGESTED trust until verified by descent.

These two trust levels are not interchangeable. The trust algebra defines a conservative join: when a paper section (COPILOT_SUGGESTED) and an evidence section (RUNTIME_WITNESSED) interact through a restriction map, the combined trust of the resulting section is:

Conservative Join in the Trust Algebra
\[ \mathrm{trust}(s_\mathcal{P} \wedge s_\mathcal{E}) \;=\; \min\bigl(\mathrm{trust}(s_\mathcal{P}),\; \mathrm{trust}(s_\mathcal{E})\bigr) \;=\; \mathrm{COPILOT\_SUGGESTED} \]

This is not a pessimistic heuristic — it is a soundness condition. An unverified paper claim cannot borrow trust from a verified benchmark. The conservative join prevents trust laundering: the claim “our system achieves F1 = 0.83” must itself be verified against \(\mathcal{E}\) before it can carry RUNTIME_WITNESSED trust, regardless of the trust level of the underlying benchmark.

Trust levels propagate contravariantly through restriction maps: if a section \(s_\mathcal{P}\) restricts along report to a section \(s_\mathcal{E}'\), and \(s_\mathcal{E}'\) disagrees with the measured \(s_\mathcal{E}\), then \(s_\mathcal{P}\) is immediately demoted to CONTRADICTED — the lowest trust level, indicating an active conflict with verified evidence.

Trust Demotion on Contradiction
\[ s_\mathcal{P}\big|_{\text{report}} \;\neq\; s_\mathcal{E} \;\;\Longrightarrow\;\; \mathrm{trust}(s_\mathcal{P}) \;\leftarrow\; \mathrm{CONTRADICTED} \]

8. Semantic Moves for Research

The orchestration loop that JuGeo runs over a research workspace is driven by semantic moves. A semantic move is an atomic operation on a specific artifact surface that changes the set of sections of the consistency sheaf. Each move type has a precise effect on the descent state.

CONSTRUCT /𝓣
Generate theory

Adds new sections to \(\mathcal{F}_\mathcal{W}(\mathcal{T})\): definitions, theorem statements, proof sketches. Does not affect \(\mathcal{R}\), \(\mathcal{E}\), or \(\mathcal{P}\) directly, but may invalidate existing impl sections in \(\mathcal{R}\) if the new theory is incompatible with the current implementation.

CONSTRUCT /ℛ
Generate code

Adds or replaces sections in \(\mathcal{F}_\mathcal{W}(\mathcal{R})\). Must respect the impl morphism constraint: new code sections must be covered by the current theory surface. If theory has not been updated to accommodate the new code, descent on \(J_\mathcal{W}(\mathcal{R})\) fails immediately.

VERIFY /ℰ
Run benchmarks

Executes the code and records measured results in \(\mathcal{F}_\mathcal{W}(\mathcal{E})\) with RUNTIME_WITNESSED trust. This is the only move that can add RUNTIME_WITNESSED sections. If the new measurements contradict existing theory sections, the validate morphism produces an H¹ obstruction between \(\mathcal{E}\) and \(\mathcal{T}\).

CHALLENGE /𝒫
Check claims against evidence

Compares each section of \(\mathcal{F}_\mathcal{W}(\mathcal{P})\) against its required restriction from \(\mathcal{E}\), \(\mathcal{T}\), and \(\mathcal{R}\). Produces an obstruction report without modifying any sections. Always idempotent. The adaptive strategy injects a CHALLENGE after every expansive move.

REPAIR
Fix obstructions

Given an obstruction class, REPAIR either modifies a section to eliminate the mismatch or adds a new section that resolves the cocycle. Repair is typed by obstruction degree: H⁰ repairs add missing sections; H¹ repairs reconcile conflicting sections at their intersection.

NORMALIZE /𝒫
Rewrite claims to match reality

Replaces COPILOT_SUGGESTED sections in \(\mathcal{F}_\mathcal{W}(\mathcal{P})\) with sections derived by restriction from \(\mathcal{E}\) or \(\mathcal{T}\). After NORMALIZE, the paper sections carry the trust level of their source, and descent on \(J_\mathcal{W}(\mathcal{P})\) is expected to succeed.

GLUE /𝓌
Attempt global descent

Runs the full descent engine on \((\mathcal{W}, J_\mathcal{W})\), checking all covering families simultaneously. Succeeds if and only if the workspace is globally consistent. On failure, returns the full obstruction report for all failing covering families. This is the terminal move in the orchestration loop.

The adaptive strategy is the default orchestration policy. It runs descent after every expansive move (CONSTRUCT, VERIFY) and automatically injects a CHALLENGE + REPAIR pair whenever an H¹ obstruction is detected. The loop continues until GLUE succeeds or the repair budget is exhausted.

Adaptive Orchestration Loop
\[ \text{loop:} \quad \text{Move} \;\xrightarrow{\text{descent}}\; \begin{cases} \text{continue} & \text{if } \mathcal{F}_\mathcal{W} \in \mathrm{Sh} \\[4pt] \text{CHALLENGE} + \text{REPAIR} & \text{if obstruction detected} \end{cases} \;\xrightarrow{\text{GLUE}}\; \checkmark \]

9. Why Geometry, Not Engineering

The engineering approach to keeping research artifacts consistent is to define a checklist: write tests that verify the paper's numbers against the benchmark outputs; write a CI step that checks the code matches the README; write a review protocol that catches theory-code gaps. This is the right approach for known consistency conditions.

The geometric approach is broader. It does not enumerate the conditions to check; it defines consistency as a property of the entire structure (sheafhood on the workspace site) and checks that property directly. The consequences of this difference are substantial:

Engineering approach
  • Checks the consistency conditions you thought to write tests for.
  • Novel drift patterns (new kinds of inconsistency) are not caught until a human notices and writes a new test.
  • Scales linearly in the number of conditions, but the number of ways four artifacts can be inconsistent grows combinatorially.
  • Cannot classify the severity or propagation of a failure — only detect or miss it.
  • Re-prompting as a repair strategy has no formal completion guarantee.
Geometric approach
  • Checks ALL overlaps in the covering families, not just the listed ones.
  • Novel drift is caught as a descent failure regardless of whether it matches a known pattern.
  • Scales with the number of covering families, which is fixed by the workspace structure.
  • Classifies failures as H⁰/H¹/H²/H∞ with propagation scores.
  • REPAIR moves have formal completion guarantees for H⁰ and H¹ obstructions.

The deeper point is that research software orchestration is not an unusual or exotic problem. It is the problem of maintaining a consistent global section of a functor over a site, and that problem has been studied extensively in algebraic geometry under the name of descent theory. JuGeo imports that machinery and applies it to a site where the objects are artifact surfaces and the morphisms are semantic dependencies — but the mathematics is the same.

In particular, the result that “a sheaf is determined by its local sections together with compatible gluing data” is not a metaphor here. It is a literal statement about the workspace: a globally consistent research repository is exactly a compatible family of local sections (one per artifact surface) together with compatible restrictions on the overlaps (the pairwise consistency of the cross-surface morphisms). When the LLM fails to maintain global consistency, it is precisely because it is working with local sections (each artifact in isolation) without enforcing the global gluing condition. The orchestration layer is the descent engine.
