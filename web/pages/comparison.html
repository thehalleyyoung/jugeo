JuGeo vs Lean 4, Coq & F*

JuGeo inherits crucial ideas from dependent types, refinement types, SMT integration, and user-defined effects, then places them inside a broader judgment-geometry stack for trust-carrying Python, web applications, and multi-agent verification. The result keeps the formal power while reducing foreign code rewrites, tactic burdens, binary trust models, and AI-unfriendly failure modes.

1 Overview

Lean 4, Coq, and F* are the three most production-ready dependently-typed proof assistants available today. Each has been used in landmark verification projects: seL4, CompCert, miTLS, HACL*, and Project Everest. They are powerful tools. They are also tools built for a different era.

JuGeo starts from a different design goal: verification should be a property of Python programs, not a parallel universe you extract code from. The theoretical substrate is sheaf-theoretic rather than simply type-theoretic, enabling a richer model of trust, evidence, and failure than any of the three competitors.

JuGeo's sheaf-theoretic model means that a proof is not a single closed term but a global section of a presheaf over a semantic site \(\mathcal{C}\). Partial evidence from different channels—SMT, runtime monitoring, LLM oracle, formal tactics, test coverage—are sections over open covers, and global consistency is the descent condition. This subsumes the purely type-theoretic models used by all three competitors.

2 The Problem with the Status Quo

All three systems share a common ancestor: Martin-Löf Type Theory. That ancestry brings extraordinary mathematical power, but also a set of design decisions that are actively harmful for modern software engineering.

3 The Same Proof in Lean 4, F*, and JuGeo

To make the comparison concrete, we implement the same specification in all three systems: a filtered affine sum over a list of integers. Given a list values, bias \(b\), modulus \(m\), and residue class \(k\), the function returns \[ S = \sum_{\substack{v \in \mathrm{values} \\ v \bmod m = k}} (v + b). \] We prove that the implementation equals this specification exactly.

Lean 4
Functional language, manual tactic proof, extracts to C via LLVM backend
Lean 4
theorem solve_eq_spec (values : List Int) (bias mod keep : Int) :
    solve values bias mod keep = spec values bias mod keep := by
  unfold solve spec; induction values with
  | nil => simp
  | cons v vs ih =>
      simp [List.foldl, List.filter]
      split
      · simp [*]; omega
      · exact ih
⚠
Cost: the entire program must be rewritten in Lean 4's functional subset. Python I/O, mutable state, exceptions, generators, and async are inaccessible. The omega call hits an SMT oracle with no trust accounting.
F*
ML-like syntax, recursive lemma with Dijkstra monad, extracts to OCaml or C
F*
let rec solve_correct (values: list int) (bias mod_ keep: int)
  : Lemma
      (ensures solve values bias mod_ keep = expected_total values bias mod_ keep)
      (decreases values) =
  match values with
  | [] -> ()
  | v :: vs -> solve_correct vs bias mod_ keep
⚠
Cost: once again the code must live in F*, not Python. The Lemma effect is a restricted monad; composing it with ST or Exn requires explicit monad transformers. Python's async with, metaclasses, and generators have no F* equivalent.
★ JuGeo
Plain Python — declare a cover + spec, the system discharges the proof
JuGeo / Python
def solve(values, bias, mod, keep):
    total = 0
    for value in values:
        if int(value) % mod == keep:
            total += int(value) + bias
    return total


def spec(result, values, bias, mod, keep):
    return (
        isinstance(result, int) and
        result == expected_total(values, bias, mod, keep)
    )
★
What JuGeo does automatically: (i) constructs a semantic site \(\mathcal{C}_{\mathtt{solve}}\) whose open covers correspond to the loop body and the conditional branch; (ii) dispatches the loop invariant to Z3; (iii) verifies the conditional path condition via SMT; (iv) assembles the global section via the descent/gluing map; (v) emits a trust certificate in the .jugeo proof-carrying annotation on the function. The programmer writes zero proof code.

Summary

In Lean 4 and F* the programmer must: (1) rewrite their code in a foreign language, (2) write a complete proof term or tactic script, and (3) manually compose effects. In JuGeo the programmer writes an ordinary Python function and a Python predicate; the system does the rest, with auditable trust provenance for every claim.

5 What F* Can't Express

F* is the closest competitor to JuGeo on the effects axis. The Dijkstra monad hierarchy gives F* the ability to reason about state, exceptions, and I/O in a single framework. But Python's async context manager idiom—where resource acquisition, body execution, and guaranteed cleanup must be reasoned about jointly, possibly across await suspension points—is fundamentally outside what F*'s effect system can express without custom-built monadic infrastructure.

  let* v = r.__aenter__ () in
  let* result =
    try_with (body ()) (fun exn ->
      let* _ = r.__aexit__ (Some exn) in raise exn) in

import jugeo as jg

@jg.cover
class AsyncDBConnection:
    """
    JuGeo models __aenter__/__aexit__ as
    an adjoint pair of restriction morphisms:
      ε : res ⊗ body → result
    Suspension points (await) become
    deferred fibre maps in the async site.
    """

    async def __aenter__(self):
        self.conn = await db.connect()
        return self.conn

    async def __aexit__(self, *exc):
        await self.conn.close()
        return False


@jg.spec(lambda result, conn:
    isinstance(result, list) and
    jg.trust(conn, jg.RUNTIME) >= 0.9)
async def fetch_all(query: str):
    async with AsyncDBConnection() as conn:
        return await conn.execute(query)

The fundamental issue is that F*'s Dijkstra monad models pre/post conditions on sequential computation. An async with block introduces a reentrant suspension boundary—the event loop can interleave other coroutines between __aenter__ and the body, and between the body and __aexit__. Modelling this correctly requires a concurrent separation logic or a fibred monad over the event-loop state, neither of which F* provides out of the box.

JuGeo's async semantic site \(\mathcal{C}_{\mathrm{async}}\) models suspension points as sheaf restriction maps along the time-ordered cover of the event loop. The descent condition then guarantees that the trust assembled at the outer level is coherent with what happens inside each suspension. This is not a workaround—it is the correct semantic model.

6 Why Proof-Carrying Python is Easier

The advantages of JuGeo's approach are not merely academic. Each of the following points represents a concrete reduction in the effort required to deploy formal verification in a real Python project.

1

Don't rewrite your code

In Lean 4, Coq, and F*, you cannot verify an existing Python codebase. You must rewrite it in the proof language. JuGeo annotates Python directly. A @jg.cover decorator and a @jg.spec predicate are all that is required. The implementation function is untouched.

2

Don't write tactic proofs

Lean 4 and Coq require the programmer to write a complete proof term or tactic script. F* requires a Lemma body. JuGeo's routing engine dispatches goals to the most appropriate channel automatically—Z3 for arithmetic, the runtime monitor for dynamic invariants, the LLM oracle for underspecified properties. The programmer writes a Python predicate, not a proof script.

3

Failure is actionable

When Lean says "tactic failed, unsolved goals", you receive a goal state and nothing else. When JuGeo detects an obstruction, it computes its class in \(H^1(\mathcal{C}, \mathcal{J})\), identifies the open set responsible, and returns a concrete repair morphism: "cover branch value % mod == 0 with an additional test case or SMT assertion". Failures drive development rather than blocking it.

4

Mixed evidence is natural

Real software has heterogeneous verification needs. Some properties are best checked by Z3; others by running tests; others by consulting an LLM. In Lean / Coq / F* you must commit to one regime per definition. In JuGeo all evidence sources are first-class channels, their trust scores compose via meet in \(\mathcal{T}\), and the result is a single graded judgment that reflects exactly how much confidence the system has.

5

Proof ships with code

JuGeo annotates each function with a proof-carrying annotation—a compact certificate that encodes the trust level, the evidence channels used, and the specification checked. This annotation travels with the function in its .jugeo sidecar or inline as a docstring tag. Downstream consumers can inspect or re-verify the certificate without re-running the full verification pipeline.

6

Concrete: what F* can't express

F*'s Dijkstra monad covers state, exceptions, and I/O. It cannot model Python's async with idiom, generator protocol, or metaclass semantics without custom effect infrastructure that must be rebuilt for each project. JuGeo provides these as first-class constructs, with formal semantics proven in Paper 07 and experimental validation in Papers 24–26.

Scaling argument

The proof effort in traditional proof assistants scales roughly as \(O(n^2)\) in the size of the specification: each new property must be proven compatible with all previously proven properties, and the tactic burden grows with the number of lemmas. JuGeo's sheaf model changes this to \(O(n)\): each new cover is proven locally on its own open set, and global consistency is established automatically by the descent condition. The programmer pays a constant overhead per new property, not a growing debt.

✓
Bottom line JuGeo does not ask you to choose between writing Python and writing proofs. It lets you write Python and get proofs—with richer trust semantics, better failure ergonomics, and broader language coverage than any existing proof assistant.
