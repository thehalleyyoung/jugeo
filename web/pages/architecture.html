System Architecture

JuGeo is organized as a strict-dependency DAG of ~960 Python modules across eleven layers, from an immutable mathematical kernel through to high-level orchestration and ideation.

Overview

Every JuGeo module obeys a strict rule: it may only import from layers strictly below it in the DAG. This guarantees that the dependency graph is acyclic and that the lowest layers (kernel, geometry, judgments) remain independently auditable and testable.

Layer Reference

kernel

jugeo.kernel (~60 modules)

The immutable mathematical foundation. Implements sets, presheaves, sheaf axioms, category-theoretic primitives, and the trust lattice. No external dependencies.

  • Sheaf & presheaf base classes
  • Trust lattice (MACHINE_VERIFIED, COPILOT_SUGGESTED, …)
  • Coverage relations and Grothendieck topologies
  • Immutable record types

geometry

jugeo.geometry (~75 modules)

Semantic sites, opens, covers, and the geometric structures used to model program state spaces. Implements the site construction algorithms.

  • Semantic site construction
  • Open set arithmetic (union, intersection, refinement)
  • Cover strategies (uniform, semantic, adaptive)
  • Cech nerve computation

judgments

jugeo.judgments (~90 modules)

The judgment layer defines every inference rule in the system. Satisfaction, equivalence, descent, refinement, and cohomological obstruction judgments are all constructed here.

  • Satisfaction, equivalence, refinement judgment forms
  • Descent conditions and gluing lemmas
  • Obstruction class computation
  • Judgment algebra operations

evidence

jugeo.evidence (~80 modules)

Evidence channels, trust ceilings, and evidence routing. Every piece of evidence entering the system has a source, a trust level, and a channel.

  • Evidence channel protocol
  • Mixed-evidence routing tables
  • Trust ceiling enforcement
  • Certificate issuance and validation

solver

jugeo.solver (~70 modules)

SMT solver integration. Wraps Z3, CVC5, and a native incremental solver. Handles encoding dispatch, incremental solving, and result interpretation.

  • Z3 and CVC5 adapters
  • Incremental push/pop interface
  • Solver result to certificate mapping
  • Timeout and budget management

encodings

jugeo.encodings (~110 modules, 18 sub-packages)

Translates judgments into SMT formulas. Eighteen sub-packages cover scalar types, collections, heap memory, tensors, theorems, and more. See the Encodings page for details.

  • Scalar refinement type encodings
  • Deduction rule encodings
  • Heap & aliasing encodings
  • Tensor quantifier encodings

python_runtime

jugeo.python_runtime (~85 modules)

Lifts Python semantics into the judgment layer. Handles CPython bytecode interpretation, type inference, effect analysis, import graph analysis, and async effects.

  • Python effect system (IO, State, Async, Exception)
  • Heap aliasing analysis
  • Import graph and dependency analysis
  • Metaobject protocol reflection

generation

jugeo.generation (~90 modules)

Implements the code generation pipeline: cover design, inhabitant fleets, construction loop, descent checking, and proof-carrying Python emit. See Code Generation.

  • Cover design strategies
  • Inhabitant fleet management
  • Construction loop (propose/normalize/compare/select)
  • PCP emitter and scaffold generator

orchestration

jugeo.orchestration (~100 modules)

High-level pipeline coordination: synthesis orchestrator, fleet management, semantic control, move selection, and frontier objective tracking. See Orchestration.

  • Synthesis orchestrator
  • Semantic move selection
  • Mixed-evidence routing
  • Frontier objective management

ideation

jugeo.ideation (~75 modules)

Theorem discovery, novelty search, theorem economics, and research assistance. The discovery engine can propose new mathematical conjectures from existing theorems. See Ideation.

  • Discovery engine
  • Theorem ecology management
  • Novelty scoring and ranking
  • Budget-constrained research planning

problem_modes

jugeo.problem_modes (~25 modules)

The top-level entry points for each proof mode. These modules wire together all lower layers to implement jugeo spec, jugeo equiv, jugeo bug, and jugeo refine. CLI parsing also lives here.

  • CLI argument parsing and validation
  • Mode dispatch and result formatting
  • Progress reporting and logging

Design Principles

Strict DAG enforcement

Import cycles are prevented by a CI check that runs on every commit. The check uses jugeo.analysis.import_graph to compute the full import graph and verifies it is a DAG. Any PR that introduces a cycle is automatically rejected. 

# Run the import graph check locally
python -m jugeo.analysis.import_graph --check-acyclic jugeo/

No upward imports

The kernel and geometry layers have no knowledge of Python, SMT, or generation. This means you can import jugeo.kernel and jugeo.geometry in a pure mathematical context, without pulling in Z3, the solver, or any LLM-related code.

Trust propagation

Every value in the system carries a trust level from the kernel's trust lattice. When values from different trust levels are combined, the result takes the minimum trust level of its inputs. This means a certificate is only as trustworthy as its weakest evidence source. 

from jugeo.kernel.trust import TrustLevel, meet

t1 = TrustLevel.MACHINE_VERIFIED
t2 = TrustLevel.COPILOT_SUGGESTED

result_trust = meet(t1, t2)
print(result_trust)  # TrustLevel.COPILOT_SUGGESTED  (lower)

Import Graph Analysis

JuGeo ships with a built-in import graph analyzer in jugeo.analysis.import_graph. You can use it to inspect the dependency structure of your own code and check for cycles. 

from jugeo.analysis import import_graph

# Analyze a module
graph = import_graph.analyze("mypackage/")
print(graph.node_count)      # number of modules
print(graph.edge_count)      # number of import edges
print(graph.is_acyclic())    # True if no cycles
print(graph.layer_count())   # number of topological layers
print(graph.critical_path()) # longest dependency chain

# Detect cycles
cycles = graph.find_cycles()
for cycle in cycles:
    print(" -> ".join(cycle))

# Generate a dot file for visualization
graph.to_dot("import_graph.dot")
⚠
Plugin authors: If you write a JuGeo plugin, you must not import from jugeo.orchestration or above in any module that you intend to contribute back to a lower layer. The import graph CI check will reject such contributions. Use the plugin API (jugeo.plugins) instead, which operates at the problem_modes layer.
