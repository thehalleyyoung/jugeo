How the Pipeline Works

The foundation pipeline coordinates five stages. The judgment geometry framework ensures that what the code does matches what the textbook says matches what the proofs formalize — because all artifacts are sections of the same sheaf, and descent catches any drift.

1

Ideate: Cross-Tradition Mathematical Synthesis

The engine samples from a catalog of 128 foundational mathematical fields (type theory, Poisson geometry, infinity categories, tropical geometry, etc.) and runs a binary tournament that forces cross-tradition pairings. An algebra field is paired with a geometry field, a logic field with an analysis field — maximizing the chance of a genuinely novel synthesis. Each pairing is judged on leverage, metaphor richness, transportability, proof density, novelty, and geometry fit.

2

Design: What Real Tool Does This Math Enable?

The winning synthesis is translated into a "killer application" — a concrete software tool that practitioners would actually use. "Poisson Geometry × Infinity Categories" becomes a toolkit for translating problems between Poisson bracket representations and higher-categorical homotopy models. The tool gets a name, a one-liner, target users, and CLI commands.

3

Generate: Pip-Installable Python Package

The LLM produces a complete Python package: core.py with structural types (dataclasses with proper typing, mathematical content in docstrings), operations.py with bridge operations, verification.py with Z3-backed invariant checking, examples.py with worked examples, cli.py with a real CLI entry point, and a pyproject.toml making it all installable.

4

Write: Comprehensive LaTeX Textbook

A full textbook for the synthesized field — not a stub, but a multi-chapter document with introduction, core theory, bridge theorems, applications, and proofs. Compiled to PDF via pdflatex. The textbook describes the same mathematics that the code implements and the Lean files formalize.

5

Verify: Lean Proofs + Z3 Ledger

Lean 4 files formalize the core theorems. The Z3 verification ledger records which computational invariants were checked. Both serve as evidence that the generated code is consistent with the generated theory — not just "it compiles" but "the structural invariants hold."

The Mathematical Synthesis

The ideation engine doesn't combine fields randomly. It enforces cross-tradition pairing: fields from the same mathematical tradition (e.g., two branches of algebra) are never paired, because the synthesis wouldn't be novel. Instead, the tournament pairs algebra with geometry, logic with analysis, topology with probability — producing bridge theorems that formally connect distant areas.

A real example from a successful run ("Poisson Geometry × Infinity Categories"):

From Poisson Geometry

Weinstein Splitting Theorem — Near any point \(x\) in a Poisson manifold \((M, \pi)\), local coordinates \((q_i, p_i, z_j)\) exist with \(\pi = \sum \partial/\partial q_i \wedge \partial/\partial p_i + \sum \phi_{ij}(z)\, \partial/\partial z_i \wedge \partial/\partial z_j\), separating symplectic and transverse directions.

From Infinity Categories

Joyal Model Structure — The category of simplicial sets carries the Joyal model structure where fibrant objects are quasi-categories and weak equivalences are categorical equivalences, Quillen-equivalent to the Bergner model structure on simplicial categories.

Bridge Theorem (Novel)

Poisson Structures on Simplicial Spaces — the synthesis produces new bridge theorems connecting Poisson brackets on manifolds with higher-categorical structure on their simplicial resolutions, enabling bidirectional problem translation between the two frameworks.

What the Generated Code Looks Like

This is real output from core.py of a successful run — not a template, but LLM-generated code that implements the synthesized mathematics:

python 
"""core.py -- Core types for Poisson Geometry x Infinity Categories.

Implements foundational structures from the synthesis:
- Weinstein Splitting (symplectic leaf decomposition)
- Joyal Model Structure (quasi-categories)
- Bridge: Poisson brackets on simplicial spaces
"""
from __future__ import annotations
from dataclasses import dataclass, field
from typing import Any, TypeVar
import uuid

T = TypeVar("T")

@dataclass
class SynthesisObject:
    """A structural object in the synthesized framework."""
    obj_id: str = field(default_factory=lambda: str(uuid.uuid4())[:12])
    level: int = 0
    tags: set[str] = field(default_factory=set)
    metadata: dict[str, Any] = field(default_factory=dict)

    def is_bridge(self) -> bool:
        """True if this object spans multiple constituent fields."""
        return len(self.tags) > 1

@dataclass
class MorphismSpace:
    """Structure-preserving maps between synthesis objects."""
    source: SynthesisObject
    target: SynthesisObject
    morphisms: list[dict[str, Any]] = field(default_factory=list)

    def compose(self, other: MorphismSpace) -> MorphismSpace:
        """Compose morphism spaces (category law)."""
        assert self.target == other.source
        composed = [{"via": [m, n]}
                    for m in self.morphisms for n in other.morphisms]
        return MorphismSpace(self.source, other.target, composed)

@dataclass
class PoissonBracket:
    """A Poisson bracket on a synthesis object."""
    base: SynthesisObject
    bracket_data: dict[str, Any] = field(default_factory=dict)

    def weinstein_split(self) -> tuple[Any, Any]:
        """Decompose into symplectic + transverse components."""
        symplectic = {k: v for k, v in self.bracket_data.items()
                      if v.get("type") == "symplectic"}
        transverse = {k: v for k, v in self.bracket_data.items()
                      if v.get("type") == "transverse"}
        return symplectic, transverse

How Consistency Is Maintained

The hard problem in research software isn't generating artifacts — it's keeping them consistent. When an LLM writes a textbook chapter, then separately generates code, then separately writes Lean proofs, the three can easily drift apart: the textbook claims a theorem that the code doesn't implement, or the code has a function that the Lean proofs don't formalize.

JuGeo treats the four artifact surfaces — Theory \(\mathcal{T}\), Code \(\mathcal{R}\), Evidence \(\mathcal{E}\), Claims \(\mathcal{P}\) — as coordinates in a workspace site. The consistency condition is the sheaf condition: local sections on each surface must agree on all overlaps. When the textbook says "Theorem 3.2 states \(X\)" and the Lean file proves \(Y \neq X\), that's a non-trivial class in \(H^1\) — a descent obstruction that the system catches and reports.

The pipeline enforces this by construction: the code is generated from the propositions, the textbook is generated from the propositions and code, and the Lean proofs formalize the same propositions. The Z3 verification ledger then checks that computational invariants in the code actually hold. The result is a repository where every claim traces back to evidence.

Programmatic Access

For building your own orchestration workflows, the research_orchestration module lets you model any multi-artifact project as a workspace site and check for drift:

python 
from jugeo.research_orchestration import (
    WorkspaceSite, ResearchOrchestrator, ResearchStrategy,
)

# Point the workspace at your actual project files
ws = WorkspaceSite.from_artifacts(
    theory=open("docs/theory.tex").read(),      # your theory
    code=open("src/checker.py").read(),          # your implementation
    evidence={"f1": run_benchmark()},            # live benchmark results
    claims=open("paper/main.tex").read(),        # your paper draft
)

# Does the paper match the code match the evidence?
report = ws.check_consistency()
if not report.consistent:
    for obs in report.obstructions:
        print(f"DRIFT DETECTED: {obs.description}")
        for hint in obs.repair_hints:
            print(f"  Suggested fix: {hint}")

# Or let the orchestrator auto-repair
orch = ResearchOrchestrator(ws, strategy=ResearchStrategy.ADAPTIVE)
result = orch.run()
print(f"Consistency: {result.final_consistency.consistency_rate:.0%}")
print(f"Hallucinations caught: {result.hallucinations_detected}")
📐

The key difference from manual checking: the workspace site doesn't just compare static strings. It extracts verifiable claims from each surface (numerical values from the paper, function signatures from the code, benchmark results from the evidence) and checks that they agree across all six morphisms. When you run benchmarks and the paper claims F1=0.83 but the evidence shows F1=0.71, that's caught as a numerical mismatch obstruction with a concrete repair hint.

Why This Matters

Traditional research software development requires months of manual coordination: revise the theory, update the code, re-run benchmarks, rewrite the paper, check the numbers, re-check the proofs. Every cycle risks introducing inconsistencies.

With jugeo foundation, you get a self-consistent research repository in seconds. The judgment geometry framework ensures:

  • Every claim in the paper traces to evidence. If the textbook says "Theorem 3.2," there's a Lean file that formalizes it and a Z3 entry that checks its computational content.
  • Every function in the code has a mathematical home. The propositions in core.py are the same propositions in the textbook and the Lean files.
  • Novel mathematics, not recombination. Cross-tradition pairing produces bridge theorems that don't exist in either parent field — genuinely new mathematical content.
  • Installable and usable. The output isn't a paper draft — it's a pip install-able toolkit with a CLI, ready for practitioners to use.
