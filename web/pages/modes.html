Proof Modes

JuGeo operates in four distinct verification modes. Each targets a different class of properties and generates a corresponding certificate embedded in the output Python module.

🕑 12 min read Reference
📋
On this page: Specification Satisfaction · Equivalence Checking · Bug Detection · Relational Refinement · Mode Summary

Every JuGeo invocation selects exactly one proof mode. The mode determines which judgment forms are constructed, how the SMT encoding is built, what certificate structure is emitted, and which scaffold functions appear in proof-carrying Python output. The four modes correspond to four fundamental properties in judgment geometry:

  • Does this function satisfy its specification? (Specification Satisfaction)
  • Are two implementations semantically equivalent? (Equivalence Checking)
  • Does this function contain a reachable bug? (Bug Detection)
  • Does one implementation refine another relationally? (Relational Refinement)
✓

Specification Satisfaction spec

Prove that an implementation satisfies a declarative specification expressed as pre/post-conditions and invariants.

What it does

In specification satisfaction mode, JuGeo constructs a satisfaction judgment \(\vdash_{\mathcal{S}} f : \sigma\) where \(f\) is the implementation and \(\sigma\) is the specification sheaf. The judgment holds when every open \(U\) in the cover of \(\sigma\) admits a section \(s_U\) such that \(f\big|_U \models s_U\).

Internally, JuGeo encodes preconditions into Z3 path constraints, encodes postconditions as verification conditions, and invokes the solver to discharge each VC. When all VCs are SAT-free, a certificate is emitted.

CLI command

# Basic usage
jugeo spec --target mymodule.py::compute_price --spec specs/pricing.yaml

# With explicit cover size
jugeo spec --target mymodule.py::compute_price \
           --spec specs/pricing.yaml \
           --cover-size 8 \
           --solver z3

# Generate proof-carrying Python
jugeo spec --target mymodule.py::compute_price \
           --spec specs/pricing.yaml \
           --emit-pcp \
           --output mymodule_verified.py

Python API

import jugeo

# Load specification from YAML
spec = jugeo.Spec.from_yaml("specs/pricing.yaml")

# Run verification
result = jugeo.verify_spec(
    target="mymodule:compute_price",
    spec=spec,
    cover_size=8,
    solver="z3",
)

print(result.status)        # "VERIFIED" | "REFUTED" | "TIMEOUT"
print(result.certificate)   # Certificate object
print(result.cover)         # List of open sets used
print(result.discharge_time_ms)

# Emit proof-carrying Python
if result.status == "VERIFIED":
    jugeo.emit_pcp(result, output="mymodule_verified.py")

# Inline decorator style
@jugeo.spec(
    pre=lambda x: x > 0,
    post=lambda x, r: r >= 0 and r <= x,
)
def compute_price(x: float) -> float:
    return x * 0.9

Equivalence Checking equiv

Prove that two implementations are semantically equivalent on all inputs, or produce a distinguishing counterexample.

What it does

Equivalence checking constructs a bisimulation judgment \(\vdash_{\mathcal{B}} f \sim g\) using a product cover. JuGeo builds a joint semantic site \(\mathcal{S}(f) \times \mathcal{S}(g)\) and checks that for every open \(U\) in the product cover, the sections of \(f\) and \(g\) agree: \(f\big|_U = g\big|_U\).

This is particularly useful for validating refactors — you can confirm that an optimized implementation is provably equivalent to a reference implementation without writing any specifications.

CLI command

# Compare two implementations
jugeo equiv --ref mymodule.py::sort_v1 --impl mymodule.py::sort_v2

# With input domain restriction
jugeo equiv --ref mymodule.py::sort_v1 \
            --impl mymodule.py::sort_v2 \
            --domain "len(xs) <= 100 and all(0 <= x <= 1000 for x in xs)"

# Compare across modules
jugeo equiv --ref legacy.py::compute \
            --impl optimized.py::compute \
            --emit-pcp --output equivalence_proof.py

Python API

import jugeo

result = jugeo.verify_equiv(
    ref="mymodule:sort_v1",
    impl="mymodule:sort_v2",
    domain=jugeo.Domain(
        constraints=["len(xs) <= 100", "all(0 <= x <= 1000 for x in xs)"]
    ),
)

print(result.status)          # "EQUIVALENT" | "NOT_EQUIVALENT" | "TIMEOUT"
if result.status == "NOT_EQUIVALENT":
    print(result.counterexample)  # Distinguishing input
    print(result.witness_ref)     # Output of ref on counterexample
    print(result.witness_impl)    # Output of impl on counterexample

# Decorator style
@jugeo.equiv_of("mymodule:sort_v1")
def sort_v2(xs: list[int]) -> list[int]:
    return sorted(xs)

Bug Detection bug

Search for reachable inputs that trigger assertion failures, exceptions, or property violations.

What it does

Bug detection mode constructs obstruction classes in the Cech cohomology \(\check{H}^1(\mathcal{U}, \mathcal{F})\) of the function's semantic sheaf. Non-trivial obstructions correspond to inputs where a local invariant fails to extend to a global section — i.e., bugs.

The engine performs a semantic-directed search, preferring paths through the cover that are most likely to contain obstructions. When a bug is found, it provides a concrete triggering input, a trace, and a ranked list of suggested fixes.

CLI command

# Basic bug scan
jugeo bug --target mymodule.py::process_data

# With property to violate
jugeo bug --target mymodule.py::process_data \
          --property "result is not None" \
          --property "len(result) == len(input)"

# Exhaustive search with timeout
jugeo bug --target mymodule.py::process_data \
          --exhaustive --timeout 60s \
          --suggest-fixes

Python API

import jugeo

result = jugeo.detect_bugs(
    target="mymodule:process_data",
    properties=[
        "result is not None",
        "len(result) == len(input)",
    ],
    exhaustive=False,
    timeout_s=30,
    suggest_fixes=True,
)

print(result.status)          # "BUG_FOUND" | "CLEAN" | "TIMEOUT"
if result.status == "BUG_FOUND":
    for bug in result.bugs:
        print(bug.description)
        print(bug.triggering_input)
        print(bug.trace)
        print(bug.suggested_fixes)   # List of patch suggestions

# Scan entire module
results = jugeo.scan_module(
    "mymodule",
    depth="functions",    # "functions" | "methods" | "all"
    suggest_fixes=True,
)
for fn_name, r in results.items():
    if r.status == "BUG_FOUND":
        print(f"{fn_name}: {len(r.bugs)} bug(s)")

Relational Refinement refine

Prove that one implementation is a relational refinement of another — a strictly stronger notion than equivalence.

What it does

Relational refinement constructs a descent judgment \(\vdash_{\mathcal{D}} f \sqsubseteq_R g\) where \(R\) is a relational specification. Unlike equivalence, refinement is asymmetric: \(f \sqsubseteq_R g\) means \(f\) implements every observable behavior of \(g\) and possibly fewer. This is the natural notion for stepwise refinement in program derivation.

The mode encodes the refinement relation as a sheaf morphism \(\phi: \mathcal{S}(g) \to \mathcal{S}(f)\) and checks that \(\phi\) is a valid morphism — i.e., sections descend correctly through the relation.

CLI command

# Prove f refines g under relation R
jugeo refine --concrete mymodule.py::sort_concrete \
             --abstract  mymodule.py::sort_abstract \
             --relation  "set(concrete) == set(abstract) and concrete == sorted(concrete)"

# With domain and emit
jugeo refine --concrete mymodule.py::sort_concrete \
             --abstract  mymodule.py::sort_abstract \
             --relation  specs/sort_relation.yaml \
             --domain    "all(isinstance(x, int) for x in xs)" \
             --emit-pcp  --output sort_proof.py

Python API

import jugeo

# Define refinement relation inline
relation = jugeo.Relation(
    name="sorted_refinement",
    conditions=[
        "set(concrete_out) == set(abstract_out)",   # same elements
        "concrete_out == sorted(concrete_out)",       # concrete is sorted
    ],
)

result = jugeo.verify_refinement(
    concrete="mymodule:sort_concrete",
    abstract="mymodule:sort_abstract",
    relation=relation,
    domain=jugeo.Domain(constraints=["all(isinstance(x, int) for x in xs)"]),
)

print(result.status)       # "REFINES" | "NOT_REFINES" | "TIMEOUT"
print(result.morphism)     # The descent morphism phi
print(result.certificate)  # Certificate object

# Check refinement chain: a refines b refines c
chain = jugeo.refinement_chain(
    ["mymodule:impl_v3", "mymodule:impl_v2", "mymodule:impl_v1"],
    relation=relation,
)
print(chain.is_transitive)  # True if all links verified

Mode Summary

The table below summarizes the key properties of each mode, the mathematical structure used, and when to choose it.

Mode CLI flag Judgment form Use when
spec Specification Satisfaction jugeo spec \(\vdash_{\mathcal{S}} f : \sigma\) You have a written specification (YAML / decorator) and want to prove the implementation meets it.
equiv Equivalence Checking jugeo equiv \(\vdash_{\mathcal{B}} f \sim g\) You refactored or optimized a function and want to confirm the new version behaves identically.
bug Bug Detection jugeo bug \(\check{H}^1(\mathcal{U},\mathcal{F}) \neq 0\) You want to find inputs that violate properties, trigger exceptions, or cause assertion failures.
refine Relational Refinement jugeo refine \(\vdash_{\mathcal{D}} f \sqsubseteq_R g\) You are deriving a concrete implementation from an abstract specification in a stepwise fashion.
💡
Tip: All four modes can emit proof-carrying Python via --emit-pcp. The emitted file contains scaffold functions (_coordinate, _support, _descent_profile) and a machine-readable certificate. See the Code Generation page for details.
